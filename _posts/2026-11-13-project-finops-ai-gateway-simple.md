## 이 프로젝트를 한 문장으로

회사의 직원들이 GPT나 Claude 같은 클라우드 AI를 쓸 때, 요청을 중간에서 관리하고 사용량과 비용을 기록하는 작은 시스템을 만들어 보는 프로젝트입니다.

여기서 클라우드 AI란 ChatGPT 앱이나 Claude 앱을 사람이 직접 사용하는 상황이 아닙니다. 우리 프로그램이 인터넷을 통해 OpenAI나 Anthropic의 API에 요청을 보내고, 모델의 답을 받아오는 방식입니다.

이 프로젝트에서는 유휴 인텔 맥북을 AI의 답을 직접 만드는 컴퓨터로 쓰지 않습니다. **요청을 받아 정리하고, 실제 답을 만들 AI로 전달하는 안내 데스크**처럼 사용합니다.

> 이 글은 아직 측정 결과를 주장하는 글이 아니라, 무엇을 만들고 어떻게 확인할지 설명하는 PoV 설계안입니다.

---

## 회사에서 어떤 문제가 생길 수 있을까?

일반적인 회사에서 여러 팀이 각자 AI API를 연결한다고 가정해 보겠습니다.

- 어떤 팀이 AI를 얼마나 썼는지 한눈에 보기 어렵습니다.
- 같은 종류의 요청에도 각자 다른 모델을 골라 비용이 달라질 수 있습니다.
- 한 프로그램의 오류나 반복 요청으로 사용량이 갑자기 늘 수 있습니다.
- 회사는 AI가 얼마나 도움이 됐는지, 비용을 들일 가치가 있는지 설명하기 어렵습니다.

그래서 AI 요청이 지나가는 한 곳을 두고, 사용량과 비용을 모아 보고, 정해 둔 한도를 적용해 보려 합니다.

    │ 유휴 인텔 맥북                │

맥북에는 게이트웨이 프로그램과 사용 기록을 보관하는 데이터베이스를 둡니다. AI 답변을 만드는 일은 OpenAI나 Anthropic API가 합니다.

## 각 부분을 쉬운 말로 설명하면

| 구성 요소 | 하는 일 |
| --- | --- |
| 직원 프로그램 | 요약이나 분류 같은 요청을 보내는 곳 |
| AI 게이트웨이 | 요청을 받아 적절한 AI API로 전달하는 중간 창구 |
| 클라우드 AI API | GPT나 Claude 모델에 요청을 보내고 답을 받는 통로 |
| 데이터베이스 | 어떤 팀이 얼마나 사용했는지 기록하는 장부 |
| 인텔 맥북 | 이 작은 시스템을 띄우고 시험하는 실험용 컴퓨터 |

게이트웨이 뒤에 데이터베이스를 두는 이유는 **사용 기록과 예산 한도를 관리하기 위해서**입니다. LiteLLM의 예산 및 가상 키 기능도 비용 기록을 위해 데이터베이스 설정이 필요하다고 안내합니다. 처음에는 맥북에 함께 띄운 데이터베이스로 시험하고, 실제 운영 환경에서는 별도로 관리되는 데이터베이스를 검토할 수 있습니다.

---

## 요청은 어떤 순서로 흘러갈까?

    1. 직원 프로그램이 게이트웨이에 요청을 보냅니다.
    2. 게이트웨이는 요청에 사용된 팀별 키를 확인합니다.
    3. 사용량과 예산 상태를 확인하고 요청을 기록합니다.
    4. 설정된 모델을 통해 GPT 또는 Claude API에 요청을 보냅니다.
    5. 클라우드 AI의 답을 게이트웨이가 받아 직원 프로그램에 전달합니다.
    6. 사용량과 비용 정보를 장부에 남깁니다.

팀별 키는 각 팀이 얼마를 썼는지 구분하기 위한 식별표와 같습니다. 실제 모델 회사의 비밀 API 키는 게이트웨이 쪽에 보관하고, 직원 프로그램에는 팀별로 발급한 키를 사용하게 설계합니다.

---

## 이 프로젝트에서 만들 기능

### 1단계: 요청을 중간에서 전달하기

직원 프로그램에서 게이트웨이로 요청을 보내고, 게이트웨이가 GPT나 Claude API를 호출한 다음 답을 돌려주게 합니다. 먼저 한 종류의 요청이 끝까지 잘 전달되는지 확인합니다.

### 2단계: 누가 얼마나 썼는지 기록하기

팀별 키를 만들고, 요청한 모델과 사용량, 응답 시간, 예상 비용을 기록합니다. 사용량과 비용은 모델과 API 요금에 따라 달라지므로, 실제 실험 날짜와 적용한 요금 기준도 함께 기록합니다.

### 3단계: 사용 한도 적용하기

팀에 시험용 예산 한도를 정하고, 한도에 도달했을 때 더 이상 요청을 받지 않거나 관리자 확인을 요구하도록 설정합니다. 한도 기능은 데이터베이스 설정을 포함해 실제로 작동하는지 확인해야 합니다.

### 4단계: 캐시는 나중에 선택적으로 추가하기

캐시는 전에 받은 답을 잠시 보관해, 같은 요청을 다시 보낼 때 재사용하는 기능입니다. 다만 표현이 비슷하다고 해서 항상 같은 답을 써도 되는 건 아닙니다. 우선 정확히 같은 요청을 다시 보낸 경우만 재사용하는 방식으로 시작하고, 시맨틱 캐시(뜻이 비슷한 질문도 같은 질문으로 판단하는 캐시)는 답이 잘못 재사용되지 않는지 평가한 뒤에 추가합니다.

## 무엇을 비교해서 성과를 보여줄까?

같은 질문 묶음을 준비해 두 가지 방식으로 실행합니다.

| 비교할 것 | 게이트웨이 없이 직접 호출 | 게이트웨이를 거쳐 호출 |
| --- | --- | --- |
| 요청이 처리됐는지 | 기록 | 기록 |
| 사용한 모델과 토큰 | 기록 | 기록 |
| 요청부터 답변까지 걸린 시간 | 기록 | 기록 |
| 비용 | 적용 요금으로 계산 | 적용 요금으로 계산 |
| 사용량 한도 작동 여부 | 해당 없음 | 시험 결과 기록 |

질문은 요약, 번역, 분류처럼 실제 회사에서 있을 법한 일반적인 업무로 구성합니다. 개인 정보나 회사 기밀은 테스트에 사용하지 않습니다.

캐시를 추가했다면 같은 요청을 반복해 캐시가 실제로 모델 호출을 줄였는지 측정합니다. 비용 절감률이나 지연 시간은 측정하기 전에는 알 수 없으므로, 결과를 만들어 쓰지 않고 실험 후에 기록합니다.

비용 절감 여부를 볼 때는 API 비용만 보지 않습니다. 게이트웨이와 데이터베이스를 운영하는 데 드는 비용도 고려해야 합니다. 작은 PoV에서는 비용 통제가 잘 되는지 실험하는 것이 목표이며, 항상 전체 비용이 줄어든다고 미리 가정하지 않습니다.

## 왜 유휴 인텔 맥북을 쓰나?

이 프로젝트에서 맥북은 무거운 AI 모델을 실행할 필요가 없습니다. 요청을 전달하고 사용 정보를 기록하는 게이트웨이를 실행하므로, 구형 컴퓨터로도 작은 시험 환경을 만들 수 있습니다.

다만 이 맥북 한 대는 실제 회사 서비스를 계속 운영할 서버로 볼 수 없습니다. 전원이 꺼지거나 인터넷 연결이 끊기면 요청도 멈추고, 여러 명이 쓰는 서비스에 필요한 백업과 장애 대응도 부족합니다. 따라서 이 프로젝트에서는 **설계와 실험을 보여주는 PoV 장비**로 사용합니다.

Docker Desktop으로 맥에서 컨테이너를 실행할 수 있지만, 설치 가능 여부는 맥의 macOS 버전과 메모리 사양에 따라 확인해야 합니다. Docker의 공식 설치 안내는 지원되는 macOS 버전과 최소 메모리 조건을 제시합니다.

---

## 안전하게 시험하기 위한 기본 원칙

- 실제 회사의 비밀 정보나 개인 정보를 프롬프트에 넣지 않습니다.
- OpenAI나 Anthropic의 비밀 API 키를 GitHub 저장소에 올리지 않습니다.
- 게이트웨이의 관리자용 키를 일반 사용자 프로그램에 넣지 않습니다.
- 팀별 키는 필요한 모델과 기능만 사용할 수 있도록 제한합니다.
- 요청 원문을 로그에 저장할지 신중히 결정하고, 필요하지 않으면 민감한 내용을 남기지 않습니다.
- 맥북의 게이트웨이를 인터넷 전체에 공개하지 않습니다. 외부에서 접근할 수 있게 하려면 인증과 암호화, 네트워크 보호를 별도로 설계해야 합니다.

게이트웨이를 둔다고 해서 데이터가 자동으로 안전해지는 것은 아닙니다. 직원이 보낸 요청은 GPT 또는 Claude API로 전달될 수 있으므로, 어떤 정보를 보낼지와 공급자 설정을 확인해야 합니다.

## 이 설계가 알려주는 것

이 PoV의 목표는 “맥북으로 AI를 만들었다”가 아닙니다. AI를 쓰려는 회사에 다음과 같은 질문을 하고 답을 확인하는 것입니다.

- 누가 AI를 사용하고 있나요?
- 어떤 모델이 요청을 처리하나요?
- 사용량과 비용을 팀별로 볼 수 있나요?
- 예산 한도를 실제로 적용할 수 있나요?
- 캐시를 쓰면 비용이나 응답 시간이 달라지나요?
- 실험용 맥북을 실제 서비스로 바꾸려면 무엇이 더 필요할까요?

이 질문에 설계도와 실제 측정 결과로 답할 수 있다면, 단순한 설치 경험보다 더 설득력 있는 SA 포트폴리오가 됩니다.
