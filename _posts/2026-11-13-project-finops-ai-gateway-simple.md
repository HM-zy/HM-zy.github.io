## 이 프로젝트를 한 문장으로

여러 팀이 GPT나 Claude를 업무 프로그램에서 사용할 때, 요청이 지나가는 중앙 창구를 만들어 **누가, 어떤 모델을, 얼마나 사용했고 비용이 얼마인지 확인하고 통제하는 방법**을 검증합니다.

이 글에서 말하는 GPT와 Claude는 직원이 ChatGPT나 Claude 앱에 직접 로그인해 쓰는 것이 아닙니다. 회사 프로그램이 OpenAI나 Anthropic의 API에 인터넷으로 요청을 보내고 답을 받는 방식입니다.

유휴 인텔 맥북은 답변을 직접 만드는 AI 컴퓨터가 아니라, 요청을 관리하는 **실험용 게이트웨이 서버**로 사용합니다. 실제 답변은 클라우드의 GPT 또는 Claude가 만듭니다.

> 이 글은 일반적인 회사 상황을 가정한 PoV 설계안입니다. 실제 구현 전이므로 비용 절감률, 응답 속도, 품질 점수는 주장하지 않습니다.

---

## 1. 회사에서 해결하려는 문제

일반적인 회사에서 고객 지원, 영업, 기획, 개발팀이 각자 AI 기능을 만들기 시작했다고 가정해 봅시다. 처음에는 각 프로그램이 바로 모델 회사의 API를 호출할 수 있습니다. 하지만 사용이 늘면 관리 문제가 생깁니다.

1. 어느 팀이 AI를 얼마나 쓰는지 한 곳에서 보기 어렵습니다.
2. 여러 프로그램이 서로 다른 모델과 설정을 사용해 비용과 품질을 비교하기 어렵습니다.
3. 잘못 작성한 자동화가 반복 호출을 일으켜 예상보다 많은 비용을 만들 수 있습니다.
4. 모델을 바꾸거나 비용을 줄였을 때 답변 품질이 유지되는지 확인하기 어렵습니다.
5. 한 팀이 전체 예산을 사용했을 때 요청을 제한할 기준이 필요합니다.

이 프로젝트에서는 AI 요청이 지나가는 중앙 창구를 두고, 사용량을 기록하고 예산 한도를 적용하며, 정해 둔 기준으로 모델 선택을 시험합니다.

## 3. 각 구성 요소는 무엇을 하나?

### 사용자/업무 프로그램

직원이 사용하는 웹 앱, 사내 도구, 또는 테스트용 스크립트입니다. 사용자는 “고객 문의를 요약해줘” 같은 요청을 입력합니다. 프로그램은 모델 회사 주소를 직접 사용하지 않고, 게이트웨이 주소로 요청을 보냅니다.

### AI 게이트웨이

여러 프로그램과 AI 공급자 사이에 놓이는 중앙 창구입니다. LiteLLM Proxy를 구현 후보로 사용합니다. 한 가지 요청 형식을 여러 공급자의 API에 연결하고, 팀별 키, 모델 별칭, 라우팅, 사용량 관리를 실험할 수 있습니다.

게이트웨이가 답변의 정확성을 자동으로 보증하는 것은 아닙니다. 잘못된 모델 선택, 캐시된 오답, 공급자 장애는 별도 정책과 평가가 필요합니다.

### 팀별 가상 키

가상 키는 게이트웨이가 발급하는 팀 또는 프로그램 식별용 키입니다. 예를 들어 지원팀과 영업팀에 서로 다른 키를 줍니다. 이 키로 사용량을 나누고 모델 접근을 제한할 수 있습니다.

OpenAI/Anthropic의 실제 비밀 키는 서버 측 설정에 두고, 사용자 프로그램에 넣거나 공개 저장소에 올리지 않습니다. 게이트웨이 관리자 키는 소수 관리자만 사용하도록 별도 관리합니다.

### PostgreSQL: 사용량과 예산 장부

PostgreSQL은 게이트웨이 설정, 키와 팀 정보, 비용 집계 등을 저장하는 데이터베이스 역할을 합니다. LiteLLM 문서 기준으로 가상 키 사용량 추적과 예산 기능은 데이터베이스 구성을 필요로 합니다. 따라서 “예산 한도 기능을 켰다”는 것만으로 충분하지 않고, 요청 시 한도가 실제로 적용되는지 테스트해야 합니다.

### Redis: 캐시를 선택할 때 쓰는 저장소

Redis는 응답을 잠시 보관해 같은 요청을 다시 처리하지 않아도 되게 할 수 있습니다. PoV 첫 단계에서는 필수가 아닙니다. 먼저 캐시 없이 비용과 품질의 기준선을 만들고, 이후 캐시를 추가해 효과와 부작용을 비교하는 편이 좋습니다.

### OpenAI/Anthropic API

실제 답변을 생성하는 모델 공급자입니다. 프로그램은 게이트웨이에 요청하지만, 게이트웨이는 요청을 정한 공급자의 API로 전달합니다. 따라서 인터넷 연결과 유효한 API 자격 증명이 필요하고, 공급자 요금과 데이터 처리 조건도 확인해야 합니다.

## 4. 요청 한 건은 어떤 순서로 처리되나?

예를 들어 영업팀 프로그램이 “이 회의 메모를 세 문장으로 요약해줘”라고 요청한다고 가정합니다.

1. **프로그램이 게이트웨이에 요청합니다.** 프로그램은 모델 이름 대신 “빠른 요약” 같은 사내 별칭을 요청할 수 있습니다.
2. **게이트웨이가 팀과 프로그램을 확인합니다.** 가상 키를 사용해 요청 주체를 확인합니다. 키가 유효하지 않으면 거절합니다.
3. **게이트웨이가 사용 정책을 확인합니다.** 팀이 허용된 모델을 요청했는지, 예산이나 분당 요청 한도에 도달했는지 확인합니다.
4. **캐시를 확인합니다.** 캐시 기능을 켠 경우, 재사용해도 안전한 기존 답이 있는지 검사합니다. PoV 초기에는 캐시를 끄거나 정확히 같은 요청만 대상으로 삼을 수 있습니다.
5. **게이트웨이가 모델을 선택합니다.** “빠른 요약” 별칭이 어떤 공급자와 모델로 연결되는지는 관리자가 설정한 정책에 따릅니다.
6. **선택한 공급자의 API를 호출합니다.** 예를 들어 GPT 또는 Claude API에 요청을 보내고 답을 기다립니다.
7. **게이트웨이가 응답과 사용 정보를 처리합니다.** 응답을 사용자 프로그램으로 돌려주고, 모델 이름, 요청 ID, 토큰 사용량, 지연 시간, 팀 식별자 등을 기록합니다.
8. **예산과 결과를 확인합니다.** 대시보드나 보고서에서 팀별 사용량을 살펴보고, 정한 한도가 동작했는지 확인합니다.

공급자가 요청을 받아들였더라도 응답 지연, 오류, 모델별 요금 변화가 생길 수 있습니다. 따라서 상태 코드와 실패 유형도 함께 기록해야 합니다.

## 5. 모델 라우팅은 어떻게 설계하나?

**라우팅**은 요청을 어떤 모델로 보낼지 정하는 일입니다. 여기서 중요한 것은 “복잡도를 알아서 판단해 가장 적합한 모델을 고른다”는 기능을 처음부터 가정하지 않는 것입니다.

PoV에서는 사람이 설명할 수 있는 단순한 정책으로 시작합니다.

| 사내 별칭 | 용도 예시 | 연결 방식 |
| --- | --- | --- |
| 빠른 요약 | 짧은 요약, 단순 분류 | 비용/응답시간 목표가 낮은 모델로 연결 |
| 정밀 분석 | 여러 조건을 비교하는 분석 | 품질을 우선하는 모델로 연결 |
| 기본 모델 | 별칭을 지정하지 않은 테스트 | 기본으로 정한 모델로 연결 |

이 표는 설계 예시이며, 실제 모델명과 가격은 실험 시점에 확인해서 설정합니다. 같은 공급자 안에서 모델을 나누거나 GPT와 Claude 중 하나를 선택할 수 있지만, 가격만으로 판단하면 안 됩니다. 더 싼 모델이 특정 업무에서 얼마나 잘 답하는지 평가해야 합니다.

다음 단계에서 분류기나 LLM을 사용해 “쉬운 요청/어려운 요청”을 자동으로 나누려면, 먼저 사람이 라벨을 붙인 질문셋을 만들고 라우팅 정확도와 오분류 비용을 확인합니다. 자동 라우팅이 비싼 모델로 보내야 할 요청을 값싼 모델로 잘못 보내면 답변 품질이 낮아질 수 있습니다.

## 6. 캐시는 비용을 어떻게 바꾸나?

캐시는 한 번 만든 답을 보관했다가 조건에 맞는 요청에 다시 사용하는 방법입니다.

### 정확히 같은 요청의 캐시

문자열과 설정이 정확히 일치하는 요청만 답을 재사용합니다. 오답을 엉뚱한 사용자에게 돌려줄 위험이 상대적으로 낮지만, 질문 문장이 조금만 바뀌어도 재사용되지 않습니다.

### 의미가 비슷한 질문의 시맨틱 캐시

“환불 규정은 뭐야?”와 “제품을 돌려보내려면 어떻게 해?”처럼 문장이 달라도 의미가 비슷한지 계산해 답을 재사용하려는 방식입니다. 유용할 수 있지만, 비슷해 보이는 질문에 서로 다른 답이 필요한 상황도 있습니다. 예를 들어 지역, 고객 등급, 날짜가 다르면 답이 달라질 수 있습니다.

따라서 의미 기반 캐시에는 아래 가드레일이 필요합니다.

- 비슷하다고 판단할 기준값(임계값)을 질문셋으로 조정합니다.
- 팀/테넌트, 언어, 모델 버전 등 구분 정보를 캐시 키에 포함합니다.
- 개인별 데이터, 최신 상태가 중요한 답, 권한에 따라 달라지는 결과는 캐시하지 않거나 별도 범위로 제한합니다.
- 만료 시간(TTL)을 설정하고, 정책이나 모델이 바뀌면 오래된 캐시를 무효화합니다.
- 캐시 적중률만 보지 않고, 캐시된 응답의 정확성도 사람이 검토합니다.

시맨틱 캐시는 임베딩 계산 비용과 저장소 운영 비용도 만들 수 있습니다. 캐시가 항상 공짜이거나 항상 비용을 절감한다고 가정하지 않고, 캐시 조회 비용까지 포함해 비교합니다.

## 7. 비용을 어떻게 계산하고 비교할까?

비용은 대략적으로 다음처럼 나눠 봅니다.

    전체 PoV 비용
    = GPT/Claude API 호출 비용
    + 임베딩 또는 캐시 조회 비용(사용할 때)
    + 게이트웨이/데이터베이스 운영 비용
    + 로그와 모니터링 비용

API 호출 비용은 보통 입력 토큰과 출력 토큰, 사용한 모델에 따라 달라집니다. 토큰은 모델이 문장을 처리할 때 나누는 텍스트 조각입니다. 같은 길이의 요청도 언어와 텍스트에 따라 토큰 수가 달라질 수 있습니다.

같은 질문셋을 사용해 아래 두 결과를 비교합니다.

- **기준선:** 프로그램에서 공급자 API를 직접 호출한 결과
- **게이트웨이 적용:** 같은 요청을 게이트웨이로 보내고, 예산·라우팅·캐시 정책을 적용한 결과

비교할 지표:

| 지표 | 확인하는 이유 |
| --- | --- |
| 총 호출 수와 실패 수 | 요청이 누락되거나 반복되지 않았는지 확인 |
| 입력/출력 토큰 | 실제 사용량을 파악 |
| 모델별/팀별 비용 | 비용이 어디서 발생했는지 확인 |
| 평균 및 P95 지연 시간 | 보통의 응답과 느린 요청을 함께 파악 |
| 캐시 적중률 | 반복 요청이 얼마나 재사용됐는지 확인 |
| 답변 품질 | 저렴한 모델/캐시로 바꿔도 업무 결과가 유지되는지 확인 |
| 한도 초과 차단 | 예산 정책이 의도대로 동작하는지 확인 |

절감률을 보고할 때는 계산식을 명시합니다.

    절감률 = (기준선 비용 - 최적화 후 전체 비용) / 기준선 비용 × 100

단, “최적화 후 전체 비용”에 게이트웨이, DB, 캐시 비용을 포함할지 프로젝트에서 먼저 정합니다. PoV에서는 API 비용이 줄어도 인프라 비용까지 합치면 전체 비용이 늘 수 있습니다. 실제 데이터를 얻기 전에는 절감률을 미리 쓰지 않습니다.

모델 가격은 바뀔 수 있으므로, 테스트 날짜, 공급자, 모델 버전, 적용한 가격표, 질문셋 버전을 결과와 함께 저장합니다.

## 8. 보안과 운영 설계

게이트웨이는 중앙 통제 지점이므로 자격 증명과 요청 데이터에 대한 기본 보호가 필요합니다.

### 키와 접근 권한

- 실제 공급자 API 키와 관리자 키는 환경변수나 비밀 저장소에서 주입합니다.
- 키를 소스 코드, GitHub, 이미지 캡처, 예제 설정 파일에 쓰지 않습니다.
- 팀별 가상 키는 필요 모델과 용도만 허용합니다.
- 키를 잃어버리거나 노출했을 때 비활성화하고 새 키를 발급하는 절차를 준비합니다.

### 네트워크

실험 초기에는 맥북 내부에서만 접근되도록 시작합니다. 다른 기기에서 접속하도록 열 경우, 사내/개인 네트워크 범위, 인증, HTTPS 암호화, 방화벽을 검토합니다. 공유기에서 임의로 포트를 인터넷 전체에 공개하지 않습니다.

### 로그와 개인정보

비용 분석에 필요한 메타데이터는 남기되, 프롬프트 전문이나 답변 전문은 꼭 필요한지 먼저 검토합니다. 저장해야 한다면 민감정보를 마스킹하고 접근 권한과 보존 기간을 정합니다. API 공급자에게 보낸 데이터의 저장/학습/보존 조건은 별도 확인이 필요합니다.

### 장애와 중복 호출

- 게이트웨이가 꺼지면 요청이 모두 멈출 수 있습니다. 이 구조는 단일 장애 지점입니다.
- 타임아웃과 재시도 횟수를 설정합니다. 재시도는 중복 호출과 추가 비용을 만들 수 있습니다.
- 공급자 장애 시 다른 모델로 자동 전환할 수 있지만, 답변 품질과 비용이 바뀌는 것을 기록해야 합니다.
- 한도 확인에 필요한 DB가 동작하지 않을 때 요청을 계속 허용할지 차단할지 결정합니다. 예산 통제를 보여주는 PoV에서는 동작을 명시적으로 시험합니다.

이 구성만으로 기업의 규정 준수나 데이터 보안이 보장되는 것은 아닙니다. 맥북은 PoV 장비이고, 실사용 전에는 조직의 보안/법무 요구사항을 따로 검토해야 합니다.

## 9. 단계별 구현 계획

### 1단계 — 직접 호출 기준선 만들기

일반적인 업무 질문을 20개 정도 준비하고, GPT 또는 Claude API를 직접 호출해 결과를 저장합니다. 질문, 사용 모델, 토큰, 비용, 응답 시간, 답변 품질을 기록합니다.

### 2단계 — 맥북에 게이트웨이 띄우기

게이트웨이와 PostgreSQL을 실험용 맥북에서 실행합니다. 처음에는 본인만 로컬에서 호출하도록 구성합니다. 요청이 게이트웨이에서 외부 API로 전달되고 답이 돌아오는 최소 경로를 확인합니다.

### 3단계 — 가상 키와 사용량 기록 추가

팀 또는 프로그램별 가상 키를 만들고, 키별 요청/토큰/비용 집계가 나뉘는지 확인합니다. 비밀 키가 로그나 저장소에 노출되지 않았는지도 살핍니다.

### 4단계 — 예산 한도 테스트

소액의 테스트 한도를 설정하고, 한도에 도달하기 전과 후의 요청이 어떻게 처리되는지 확인합니다. DB가 없거나 연결이 끊긴 상황에서 한도 검사가 어떻게 동작하는지도 문서화합니다.

### 5단계 — 모델 라우팅 비교

“빠른 요약”과 “정밀 분석” 같은 별칭을 설정하고 동일한 질문을 다른 모델로 처리합니다. 비용만이 아니라 정확성, 응답 시간, 실패율을 비교합니다.

### 6단계 — 캐시 실험

기준선과 게이트웨이 경로가 안정된 다음, 정확 일치 캐시부터 시험합니다. 필요하다면 별도 질문셋으로 의미 기반 캐시를 평가합니다. 캐시가 답을 잘못 재사용한 사례도 결과에 포함합니다.

### 7단계 — 운영/비즈니스 제안 정리

측정 결과, 제한점, 목표 사용량, 예상 운영 구성을 정리합니다. “맥북 한 대로 기업 서비스가 된다”고 제안하는 대신, PoV에서 확인한 원칙을 운영 환경으로 옮길 때 필요한 다중 게이트웨이, 관리형 DB, 모니터링, 비밀 관리, 네트워크 통제를 제안합니다.

## 10. 인텔 맥북이 맡는 범위와 실제 운영의 차이

인텔 맥북은 API 요청을 중계하고 데이터를 기록하는 작은 실험 노드로 쓸 수 있습니다. GPT나 Claude의 거대 모델을 맥북에 설치해 실행하는 것이 아닙니다.

실제 서비스에서는 노트북 대신 지속적으로 가동되고 장애 대응이 가능한 클라우드/사내 서버를 사용합니다. 여러 게이트웨이 인스턴스, 관리형 데이터베이스, 중앙 비밀 관리, 네트워크 접근 제어, 로그 모니터링을 추가해야 합니다. 이 PoV에서는 단일 노드의 한계를 일부러 문서화하고, 무엇을 바꿔야 확장 가능한지 설명하는 것도 결과물입니다.

## 11. 포트폴리오로 보여줄 산출물

- 일반적인 회사 상황과 요구사항
- 현재 구조와 제안 구조 아키텍처 그림
- 각 요청의 흐름과 데이터 경계
- 모델 라우팅/캐시/예산 정책 결정 기록
- 동일한 질문셋으로 얻은 비용·지연·품질 비교표
- 예산 초과, API 오류, 캐시 오답 등 실패 사례와 대응
- PoV 한계와 실제 운영 환경으로 확장할 때의 변경안
- 임원용 1페이지 요약: 문제, 제안, 측정 결과, 비용/위험, 다음 결정

이 프로젝트의 핵심은 특정 오픈소스를 실행한 사실이 아닙니다. **고객의 문제를 구체화하고, 설계 선택의 이유를 말하며, 측정 결과와 한계를 근거로 다음 결정을 제안하는 것**입니다.
