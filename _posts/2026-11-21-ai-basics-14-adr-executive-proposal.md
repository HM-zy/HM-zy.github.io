*"코딩은 잘 끝났는데, 이걸 C-Level 임원들에게 어떻게 보고하고 예산을 따내야 할까요?"*

솔루션즈 아키텍트(SA)의 가장 중요한 역할은 **기술을 비즈니스 가치로 번역하는 것**입니다. 임원은 파이썬 라이브러리 버전이나 임베딩 차원 수에 관심이 없습니다.

*"이걸 도입하면 우리 직원들의 업무 시간이 얼마나 줄고, 보안 위험은 어떻게 막았는가?"*를 단 1페이지로 설득하는 **아키텍처 의사결정 기록(ADR)과 PoV 제안서 작성법**을 정리합니다.

_기술 검증 결과를 '결재 가능한 1장'으로 압축하는 것이 PoV 보고의 마지막 단계_

## 📝 일상 비유: 요리 레시피 노트의 '왜'

집에서 김치찌개를 맛있게 끓였다고 합시다. 그런데 레시피 노트에 재료와 순서만 적어 두면, 6개월 뒤 돼지고기 대신 참치를 넣어도 되는지, 왜 굴소스를 넣었는지 아무도 모릅니다. **"왜 이 재료를 이 순서로 넣었는지"**를 한 줄 적어 둔 노트만이 다음 사람의 시행착오를 없애 줍니다.

ADR(Architecture Decision Record)이 정확히 그 노트입니다. "하이브리드 검색을 골랐다"는 **결과**만 남기면, 1년 뒤 담당자가 바뀌었을 때 같은 논의를 처음부터 다시 합니다. 반면 "순수 벡터 검색은 사규 조항 번호 검색에서 적중률이 떨어져서 탈락시켰다"까지 적혀 있으면, 그 결정은 **회사의 자산**이 됩니다.

PoV 보고서는 여기에 하나를 더합니다. 그 노트를 **돈을 쥔 사람의 언어**로 다시 쓴 1장이 필요합니다.

## 📄 임원용 1페이지 제안서의 5대 필수 구성 요소

1. **고객 문제 정의 (Pain Point)**
   - 현황: 사내 매뉴얼이 20여 개 시스템에 분산되어 신입 직원 온보딩 시 규정 탐색에 1일 평균 45분 소모. 월 1,200건의 단순 문의가 인사·총무팀에 몰립니다.
2. **기대 효과 및 정량적 ROI (Impact)**
   - 검색 소요 시간 단축: 45분 → 30초 (98% 단축).
   - 문의 건수 감소: 인사·총무팀 반복 규정 문의 40% 자동화 → 월 120시간 환산.
3. **아키텍처 선택 이유 (ADR: Trade-offs)**
   - 왜 순수 벡터 검색이 아닌 하이브리드(BM25 + Vector)인가? → 사규 조항 번호·제품 코드 같은 정확 일치 검색에서 적중률이 75%에서 95%로 개선되기 때문.
   - 왜 오픈소스 로컬 모델 대신 상용 API인가? → 엔터프라이즈급 긴 컨텍스트 처리와 PII 비학습(No-training) 보장.
4. **보안 및 규제 방어책 (Risk Mitigation)**
   - 직급별 RBAC 메타데이터 **사전 필터링**으로 기밀 문서 접근을 검색 단계에서 원천 차단(→ [13일차 RBAC 글](/posts/ai-basics-13-rbac-and-security/)).
   - 읽기 전용(Read-only) 격리 계정 사용, 답변마다 인용 문서 ID와 감사 로그 기록.
5. **다음 단계 파일럿 계획 (Next Steps)**
   - 1단계: 인사팀 30명 대상 2주간 베타 테스트 및 추가 질문셋 50개 검증.
   - 2단계: 적중률·응답시간·비용 3개 지표로 전사 확대 여부 판단.

**핵심은 순서입니다.** 임원은 3번(기술 선택)부터 읽지 않습니다. 1번(문제)과 2번(돈)에서 멈추면 3번은 읽히지 않습니다.

## ⚖️ '왜 이걸 골랐는가'를 방어하는 도구: 가중 평가표

ADR의 심장은 **대안 비교**입니다. 대안이 하나만 적힌 제안서는 제안서가 아니라 통보입니다. 실무에서는 대안별로 항목 점수(1~5)에 가중치를 곱해 총점을 냅니다.

| 평가 기준 | 가중치(임원·현업 관점) | A. 키워드 검색 | B. 순수 벡터 | C. 하이브리드+리랭킹 |
|---|---|---|---|---|
| 정확도 | 30% | 2 | 4 | **5** |
| 초기 구축 비용(높을수록 저렴) | 15% | 5 | 3 | 2 |
| 월 운영비(높을수록 저렴) | 20% | 5 | 3 | 2 |
| 응답 속도 | 15% | 5 | 4 | 3 |
| 보안·거버넌스 | 20% | 5 | 2 | **4** |

여기에 하나를 더 얹어야 진짜 실무입니다. **하드 게이트(hard gate)** — "답변 적중률 요구선을 못 넘으면 점수와 무관하게 탈락"처럼, 협상 불가능한 조건을 먼저 잘라내는 것입니다. 비용이 아무리 싸도 요구 정확도를 못 맞추면 도입할 수 없습니다.

## 💻 5분 실습: 가중 평가표로 ADR 초안까지 자동 생성하기

숫자를 손으로 계산하지 말고 코드로 돌려 봅시다. 이 실습은 **대안 평가 → 비용·효과 계산 → 1페이지 ADR 초안 생성**까지 한 번에 갑니다.

```python
# ── 1단계: 후보 대안과, 임원이 실제로 보는 평가 기준(가중치)
options = [
    {"name": "A. 키워드 검색(기존 DB)", "정확도": 2, "초기 구축 비용": 5, "월 운영비": 5, "응답 속도": 5, "보안·거버넌스": 5},
    {"name": "B. 순수 벡터 검색",       "정확도": 4, "초기 구축 비용": 3, "월 운영비": 3, "응답 속도": 4, "보안·거버넌스": 2},
    {"name": "C. 하이브리드 + 리랭킹",   "정확도": 5, "초기 구축 비용": 2, "월 운영비": 2, "응답 속도": 3, "보안·거버넌스": 4},
]

# 비용 항목은 "점수가 높을수록 싸다·빠르다"로 통일해 두면 계산이 단순해집니다
weights_executive = {"정확도": 0.30, "초기 구축 비용": 0.15, "월 운영비": 0.20, "응답 속도": 0.15, "보안·거버넌스": 0.20}
weights_finance   = {"정확도": 0.15, "초기 구축 비용": 0.30, "월 운영비": 0.30, "응답 속도": 0.15, "보안·거버넌스": 0.10}

MIN_ACCURACY = 4   # 하드 게이트: 정확도 요구선(5점 만점 중 4점) 미달 대안은 점수와 무관하게 탈락

def rank(weights):
    rows = []
    for opt in options:
        if opt["정확도"] < MIN_ACCURACY:
            rows.append((opt["name"], None, "(정확도 미달)"))
            continue
        score = sum(opt[c] * w for c, w in weights.items())
        rows.append((opt["name"], round(score, 2), ""))
    return sorted(rows, key=lambda r: (r[1] is None, -(r[1] or 0)))

for label, weights in [("임원·현업 관점(정확도·보안 우선)", weights_executive),
                       ("재무 관점(비용 우선)", weights_finance)]:
    print(f"\n📊 {label}")
    for name, score, note in rank(weights):
        print(f"  {name:<22} {('  —' if score is None else f'{score:.2f}')} {note}")

winner = rank(weights_executive)[0][0]
winner_finance = rank(weights_finance)[0][0]

# ── 2단계: 그 결정을 돈으로 번역하기 (TCO · ROI · 회수 기간)
monthly_questions = 30_000       # 월 질의 수
input_tokens, output_tokens = 8_000, 400      # 질의 1건당 토큰(검색 문맥 포함)
input_price, output_price = 3.0, 15.0         # $ / 100만 토큰 (가정치)
cache_hit_rate, cache_discount = 0.4, 0.1     # 반복 질문 40%는 캐시가 10% 비용으로 처리
usd_krw = 1_400

per_q_usd = (input_tokens * input_price + output_tokens * output_price) / 1_000_000
raw_monthly_usd = per_q_usd * monthly_questions
monthly_api_usd = raw_monthly_usd * (cache_hit_rate * cache_discount + (1 - cache_hit_rate))

saved_hours = 120                # 월 절감 업무 시간(문의 응대 자동화)
labor_saving_krw = saved_hours * 30_000
api_cost_krw = monthly_api_usd * usd_krw
net_krw = labor_saving_krw - api_cost_krw
build_cost_krw = 15_000_000      # PoV → 파일럿 구축비
payback = build_cost_krw / net_krw

print("\n💰 임원용 숫자 요약")
print(f"  질의 1건 원가   : ${per_q_usd:.4f}  → 캐시 적용 후 월 ${monthly_api_usd:,.0f} ({api_cost_krw:,.0f}원)")
print(f"  월 절감 인건비  : {labor_saving_krw:,.0f}원 ({saved_hours}시간)")
print(f"  월 순이익       : {net_krw:,.0f}원")
print(f"  구축비 회수     : {payback:.1f}개월")

# ── 3단계: 위 숫자로 1페이지 ADR 초안 자동 생성
adr = f"""# [ADR-001] 사내 지식 검색: {winner} 채택

## 1. 배경
- 사내 매뉴얼이 20여 개 시스템에 분산 → 규정 탐색 1일 45분, 월 1,200건 단순 문의

## 2. 검토한 대안 (하드 게이트: 정확도 {MIN_ACCURACY}점 미만 제외)
""" + "\n".join(f"- {n}: {'탈락 — ' + note if s is None else f'{s:.2f}점'}" for n, s, note in rank(weights_executive)) + f"""

## 3. 결정
- **{winner} 채택** — 정확도·보안 가중치가 높은 평가에서 최고점.
- 가중치를 비용 우선으로 바꾸면 1위는 {winner_finance}입니다
  → ADR에 '가중치를 왜 이렇게 두었는지'를 근거로 적어야 결재 후에 흔들리지 않습니다.

## 4. 비용·효과
- 월 절감 인건비 {labor_saving_krw:,.0f}원 / 월 API 비용 {api_cost_krw:,.0f}원
- 월 순이익 {net_krw:,.0f}원 → 구축비 {build_cost_krw:,.0f}원은 {payback:.1f}개월에 회수

## 5. 다음 단계
- 인사팀 30명 2주 베타 → 기준 질문 50개로 적중률 재측정 후 전사 확대 판단
"""

print("\n📄 자동 생성된 1페이지 ADR 초안")
print(adr)
```

**실행 결과 (직접 돌려서 확인한 값입니다)**

```
📊 임원·현업 관점(정확도·보안 우선)
  C. 하이브리드 + 리랭킹         3.45
  B. 순수 벡터 검색            3.25
  A. 키워드 검색(기존 DB)         — (정확도 미달)

📊 재무 관점(비용 우선)
  B. 순수 벡터 검색            3.20
  C. 하이브리드 + 리랭킹         2.80
  A. 키워드 검색(기존 DB)         — (정확도 미달)

💰 임원용 숫자 요약
  질의 1건 원가   : $0.0300  → 캐시 적용 후 월 $576 (806,400원)
  월 절감 인건비  : 3,600,000원 (120시간)
  월 순이익       : 2,793,600원
  구축비 회수     : 5.4개월
```

**체감 포인트 — 여기서 진짜 배울 것이 나옵니다.** 관점을 바꾸자 1위가 뒤집혔습니다. 현업 기준에서는 C(하이브리드)가, 재무 기준에서는 B(순수 벡터)가 이깁니다. 초보 SA는 이 표를 **하나만** 들고 갑니다. 그러면 임원이 "비용은 왜 이렇게 비싼 걸 골랐나"라고 물어오는 순간 답이 막힙니다.

잘하는 SA는 두 표를 다 들고 갑니다. 그리고 이렇게 말합니다. "비용 기준으로는 B가 낫습니다. 다만 이번 PoV의 하드 게이트는 적중률 95%였고, B는 87%에서 멈췄습니다. **요구선을 지키면서 비용이 다른 선택지가 없다는 것이 이 제안의 핵심**입니다." — 결재를 흔드는 건 최고 점수가 아니라, **모든 반론을 이미 계산해 뒀다는 신뢰**입니다.

**한 번 더 생각할 점**: B를 고르는 회사도 틀리지 않았을 수 있습니다. 적중률 요구선이 90%였다면 B가 정답입니다. 그래서 ADR에 **요구선(하드 게이트)을 누가, 언제, 왜 정했는지**를 반드시 남겨야 합니다. 요구선이 바뀌면 결론도 정당하게 바뀌기 때문입니다.

## ⚠️ 자주 하는 실수 3가지

1. **대안을 하나만 적는 제안서**: "이걸 하면 좋습니다"만 있는 문서는 비교의 근거가 없어 검토 단계에서 반려되기 쉽습니다. **최소 3개(기존 방식 유지 포함)**를 적고, 기존 방식을 이기는 이유를 씁니다.
2. **토큰 비용은 셈하면서 사람 시간은 안 세는 것**: PoV의 반대편은 늘 "그래서 몇 명, 몇 시간이 줄어드나"입니다. 인건비 환산(절감 시간 × 시급)과 회수 기간(payback)까지 넣어야 예산 논의가 시작됩니다.
3. **리스크를 숨기는 것**: "보안은 문제없습니다"는 임원에게 가장 불신을 주는 문장입니다. "권한 필터를 코드 한 곳에서 빼먹으면 유출된다 → 그래서 사전 필터를 DB 쿼리에 강제하고 감사 로그로 이중 확인한다"처럼 **남은 리스크 + 통제 수단**을 같이 씁니다.

## 🎯 Solution Architect 관점 한 줄 요약

> **"최고의 솔루션즈 아키텍트는 코드를 잘 짜는 사람이 아니라, 기술적 선택의 이유를 비즈니스 언어로 명확히 증명해 고객의 결재를 이끌어내는 사람이다."**

> PoV 보고 자리에서 임원이 던지는 후속 질문은 대개 세 가지입니다. ① 이 비용은 사용자가 늘면 어떻게 되나(단가·상한) ② 이 선택이 6개월 뒤 뒤집힐 여지는 무엇인가(가중치·요구선 변경) ③ 이 결정을 나중에 검증할 기록이 남는가(ADR·감사 로그). 이 세 질문에 1페이지로 답할 수 있으면, 기술 검증은 '결재되는 프로젝트'가 됩니다.
