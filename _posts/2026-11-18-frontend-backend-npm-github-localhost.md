*"npm, 프런트, 백, 서버, 파이썬이 다 섞여서 머리가 복잡해."*

오늘 저녁 두 시간 동안 터미널에서 벌어진 일을 그대로 적어 보면 이렇습니다.

1. 웹 화면을 띄우려고 `npm run dev`를 쳤더니 **`npm: command not found`**
2. `git pull`을 쳤더니 **`fatal: not a git repository`**
3. Node를 겨우 설치하고 다시 쳤더니 **`ENOENT: no such file or directory, open 'package.json'`**
4. 터미널을 두 개 켜라는 말에 **"왜 두 개를 켜? 왜 파이썬까지 같이 돌려?"**
5. 그리고 마지막 질문 — **"깃헙에서 그냥 돌리면 안 돼? API 키 발급받기가 귀찮아."**

결론부터 말하면, **이 다섯 개는 서로 다른 문제가 아니라 하나의 그림을 다섯 조각으로 본 것**입니다. 그 그림이 안 잡혀 있으면 명령어를 아무리 복사해 넣어도 다음 줄에서 또 막힙니다. 오늘 막힌 지점을 순서 그대로, 비유만으로 정리해 봅니다.

| # | 오늘 막힌 지점 | 한 줄 답 |
| --- | --- | --- |
| Q1 | 파일이 내 컴에도 있고 깃허브에도 있는 거야? | **창고(GitHub)와 작업실(내 맥북)**, 두 곳에 있는 게 정상 |
| Q2 | 코드를 깃허브에 올렸는데 왜 내 터미널에서 실행해? | **GitHub는 보관·공유용 창고지, 24시간 돌아가는 컴퓨터가 아니다** |
| Q3 | `not a git repository` / `package.json` 없다고 뜨는 이유 | **터미널의 '현재 위치'가 프로젝트 폴더 밖**이었다 |
| Q4 | 왜 터미널 2개에 npm이랑 파이썬을 둘 다? | **홀(프런트)과 주방(백엔드)이 원래 다른 프로그램** |
| Q5 | 깃헙에서 돌릴 순 없어? API 키는 왜 필요해? | **GitHub Pages는 인쇄된 책 전시관**, API 키는 외부 AI 회사에 내는 **출입증 + 과금 열쇠** |

## Q1. "파일이 내 컴에도 있고 깃허브에도 있는 거야?"

네, **두 곳에 다 있는 게 정상**입니다. 다만 두 곳의 역할이 다릅니다.

| | GitHub | 내 맥북 폴더 |
| --- | --- | --- |
| 비유 | **공용 창고 / 클라우드 원본** | **내 책상 위 작업실** |
| 역할 | 보관·공유·백업, 여러 사람이 같은 코드를 봄 | 실제로 열어서 고치고, 실행하고, 에러를 보는 곳 |
| 인터넷 | 필요함 | 필요 없음(이미 받아 뒀으면) |

그래서 오늘 했던 두 명령어의 차이는 이겁니다.

```bash
git clone https://github.com/.../repo.git   # 창고를 처음 통째로 복사 (책장째로 들여오기)
git pull origin main                        # 창고에 새로 들어온 것만 당겨오기 (새 책만 꽂기)
```

`git clone`은 **처음 한 번**, `git pull`은 **그다음부터 매번**입니다. 그리고 중요한 점 — `git pull`은 **내 작업실 파일을 덮어쓰는 게 아니라, 창고에 새로 생긴 변경만 가져와 합칩니다.** 내가 고친 파일이 있는데 창고도 바뀌었으면, Git이 "이 둘을 합쳐도 되겠냐"고 물어보거나 충돌을 알려 줍니다.

> 정리: **GitHub = 창고(원본), 내 폴더 = 작업실(사본 + 내 수정).** 오늘 `git pull`이 필요했던 이유는, 제가 새 코드를 창고에 올려 뒀는데 내 작업실은 어제 상태였기 때문입니다.

## Q2. "코드를 깃허브에 올렸는데, 왜 실행은 내 터미널에서 해?"

이게 오늘 가장 중요한 질문입니다. 답은 한 문장입니다.

> **GitHub는 코드를 보관하고 공유하는 창고이지, 프로그램을 24시간 돌려 주는 컴퓨터가 아닙니다.**

창고에 요리책을 넣어 둔다고 해서 저녁이 나오지는 않습니다. **요리책을 꺼내서, 주방이 있는 집에서 불을 켜야** 요리가 나옵니다. GitHub에 올린 코드도 마찬가지로, **누군가의 컴퓨터에서 실제로 실행해야** 화면이 뜨고 답이 나옵니다.

그 "누군가의 컴퓨터"는 두 가지 중 하나입니다.

| 방법 | 누가 실행하나 | 주소 | 지금 단계 |
| --- | --- | --- | --- |
| ① 내 맥북 | **내 컴퓨터** | `http://localhost:5173` | 오늘 하려던 것 (데모·개발용) |
| ② 클라우드 컴퓨터 | AWS·Render 같은 **남의 컴퓨터를 빌림** | `https://내서비스.com` | 나중에 외부에 공개할 때 |

오늘은 ①번입니다. 내 맥북에서 직접 띄워서, 면접관 앞에서 내 노트북 화면으로 보여 주는 것. ②번은 "불특정 다수가 접속하는 서비스"를 만들 때 하는 일이고, 그때는 빌린 컴퓨터가 24시간 켜져 있으므로 **요금과 보안 설정**이 따라옵니다.

그리고 여기서 자연스럽게 다음 질문이 나옵니다. **"그럼 블로그(`hm-zy.github.io`)는 왜 GitHub에 올리면 바로 열리는데?"** — 그건 **GitHub Pages가 '정적 페이지'만 무료로 띄워 주기 때문**입니다. 이 차이는 Q5에서 자세히 봅니다.

## Q3. `not a git repository`, `package.json`이 없다고 뜨는 이유

오늘 나온 두 에러는 **원인이 완전히 같았습니다.**

```bash
fatal: not a git repository (or any of the parent directories): .git
Error: ENOENT: no such file or directory, open 'package.json'
```

**터미널은 '지금 내가 어느 폴더에 서 있는지'를 기준으로 모든 명령을 실행합니다.** 마치 문서를 열지도 않고 "3페이지로 가"라고 말하는 것과 같습니다. 터미널이 홈 폴더(`/Users/hmshin`)에 서 있는데 `git pull`을 치면, 홈 폴더에는 `.git`이 없으니 "여긴 저장소가 아니다"라고 하는 것이고, `npm install`을 치면 `package.json`이 없으니 "그 파일이 없다"고 하는 것입니다.

**에러 메시지에 나오는 파일 이름이 곧 '찾는 위치'입니다.** `package.json`이 없다 = **폴더가 틀렸다**이지, 코드가 잘못된 게 아닙니다.

그래서 오늘 쓴 해결책이 이것이었습니다.

```bash
pwd     # 지금 어디에 서 있는지 확인
ls      # 이 폴더에 뭐가 있는지 확인 (package.json, .git 이 보여야 정상)

cd "$(find ~ -maxdepth 3 -name redhat-solution-sales-navigator -type d | head -n 1)"   # 알아서 찾아 들어가기
```

> **터미널 3종 세트: `pwd`(여기가 어디) → `ls`(뭐가 있나) → `cd`(거기로 들어가기).** 에러의 8할은 이 세 줄로 원인이 드러납니다.

그리고 오늘 마지막에 확인된 사실 — 이 맥북에는 그 프로젝트 폴더가 아예 없었습니다(다른 컴퓨터에 있었음). 그래서 `find`도 못 찾고 **홈 폴더에서 그대로 실행**돼 버린 것입니다. 이때 필요한 게 다시 Q1의 `git clone`입니다.

## Q4. 왜 터미널 2개? 왜 npm이랑 파이썬을 둘 다?

여기가 오늘의 핵심입니다. **하나의 웹 앱은 원래 두 개의 프로그램**입니다. 식당으로 바꿔 보면 딱 맞습니다.

| 식당 | 이 프로젝트 | 하는 일 | 주소 |
| --- | --- | --- | --- |
| **홀** (인테리어·메뉴판·버튼) | **프런트엔드** — React + Vite | 손님이 보고 누르는 화면을 그림 | `localhost:5173` |
| **주방** (요리하는 두뇌) | **백엔드** — Python `rag.server` | 공식문서를 찾고, 가드레일을 검사하고, AI에게 물어봄 | `localhost:8000` |
| **서빙 통로** | **Vite 프록시 (`/api`)** | 홀에서 받은 주문을 주방으로 넘김 | 5173 → 8000 |
| **홀 매니저 + 재료 배달** | **Node.js / npm** | 화면을 조립하는 도구를 돌리고, 필요한 라이브러리를 받아 옴 | — |
| **주방 도구함** | **Python + pip + `.venv`** | 파이썬 패키지를 담아 두는 전용 도구함 | — |

이 표에서 오늘의 에러들이 전부 설명됩니다.

- **`npm: command not found`** = **홀을 돌릴 매니저(Node.js)가 아직 안 깔려 있었다.** → `brew install node`
- **터미널 2개** = 홀과 주방은 **서로 다른 프로그램**이라 한 터미널에서 동시에 돌릴 수 없다. 한 터미널에서는 하나가 화면을 점유하고 계속 떠 있기 때문이다.
- **둘 다 켜야 하는 이유** = 홀만 켜면 메뉴판만 보이고, 주문을 넣어도 **주방이 꺼져 있어서** "서버 연결 실패"가 뜬다. 주방만 켜면 요리는 되는데 **보여 줄 홀이 없다.**

### 그럼 `localhost`는 뭔가?

> **맞습니다. `localhost`는 내 컴퓨터가 잠깐 '1인용 미니 서버'가 되는 것입니다.** `localhost`는 "이 컴퓨터 자신"을 가리키는 주소이고, `:5173`은 그 컴퓨터에서 열어 둔 **문 번호(포트)**입니다. 그래서 **나만 접속할 수 있고**, 그 터미널 창을 끄면(`Ctrl + C`) 그 순간 서버도 사라집니다. 옆자리 동료가 같은 주소를 쳐도 안 열립니다 — 동료의 `localhost`는 동료의 컴퓨터이기 때문입니다.

### `/api` 프록시는 왜 있나?

브라우저는 **보안상 다른 출처(포트가 다르면 다른 출처)로의 요청을 기본적으로 막습니다**(CORS). 그래서 화면은 **자기 짝(5173)에게만** 말하고, 5173이 뒤에서 조용히 8000으로 전달해 줍니다. 이게 서빙 통로, 즉 **프록시**입니다.

```js
// vite.config.ts — /api 로 시작하는 요청은 전부 주방(8000)으로 넘긴다
server: { proxy: { '/api': { target: 'http://127.0.0.1:8000' } } }
```

> SA 관점에서 이건 그냥 설정이 아니라 **아키텍처 결정**입니다. "브라우저는 단일 출처와만 대화하고, 서버 간 연결은 서버가 담당한다"는 원칙 — 실제 엔터프라이즈 구성(ALB → API → 모델 게이트웨이)에서도 똑같은 모양이 반복됩니다.

## Q5. "깃헙에서 그냥 돌리면 안 돼? API 키 발급이 귀찮아"

두 가지가 섞여 있는 질문이라 나눠서 답합니다.

### (1) GitHub Pages는 왜 RAG 서버를 못 돌리나

| | 블로그 (`hm-zy.github.io`) | RAG 서버 (`rag.server`) |
| --- | --- | --- |
| 결과물 | **미리 만들어 둔 HTML·CSS·JS 파일** | 요청이 올 때마다 **계산해서 답을 만드는 프로그램** |
| 비유 | **인쇄된 책을 전시관에 꽂아 둔 것** | **손님이 올 때마다 요리하는 주방** |
| GitHub Pages | ✅ 무료로 전시 가능 | ❌ 전시만 하지, 요리는 안 해 줌 |

GitHub Pages는 **파일을 그대로 보여 주는 창고**입니다. 반면 RAG 서버는 질문이 들어올 때마다 문서를 검색하고, 필요하면 외부 AI에게 묻고, 답을 조립합니다. **계속 떠 있으면서 계산하는 프로세스**는 정적 호스팅이 해 줄 수 없는 일입니다. 그래서 블로그는 GitHub에 올리면 열리고, RAG 데모는 내 컴퓨터(또는 빌린 클라우드 컴퓨터)에서 켜야 합니다.

### (2) API 키는 왜 필요하고, 왜 '출입증'인가

`ANTHROPIC_API_KEY`는 **외부 AI 회사(Anthropic) 서버에 말을 걸 때 내미는 출입증**입니다. 동시에 **과금 열쇠**입니다 — 누가 얼마나 썼는지 이 열쇠로 셈하기 때문에, 없으면 문 앞에서 막힙니다. (그래서 키는 절대 GitHub에 올리면 안 되고, `.env`나 환경변수로만 다룹니다.)

```bash
export ANTHROPIC_API_KEY=sk-ant-...   # 이 터미널 세션에서만 유효
.venv/bin/python -m rag.server
```

그런데 **키가 없어도 절반은 그대로 돌아갑니다.** 이게 이 프로젝트를 데모용으로 잘 만든 지점입니다.

| 기능 | 키 없이 | 키 있으면 |
| --- | --- | --- |
| 공식문서 검색(BM25) + 출처 `[doc_id]` | ✅ | ✅ |
| 가드레일 거절(가격 질문·범위 밖 질문) | ✅ | ✅ |
| 자연어 답변 생성(Claude 호출) | ❌ "키를 설정해 주세요" 안내 | ✅ |

> 오늘 키가 만료됐다면 **새로 발급받지 말고 키 없이 먼저 띄워 보는 것**이 순서입니다. 검색이 되고 거절이 되는 걸 눈으로 확인한 다음, "실제 답변까지" 보여 줘야 할 순간에만 키를 쓰면 됩니다.

## 내일 맥북에서 바로 띄우는 3단계 치트시트

> 아래 예시는 제가 만들던 Sales Navigator 데모 저장소 기준입니다. 이 저장소는 아직 **비공개(private)** 라서 제 계정으로 로그인한 상태에서만 열리니, 다른 분은 본인 저장소 이름으로 바꿔 읽어 주세요.

```bash
# 0. 창고에서 작업실로 (맥북에 폴더가 없을 때, 최초 1회)
git clone https://github.com/HM-zy/redhat-solution-sales-navigator.git
cd redhat-solution-sales-navigator
```

```bash
# 1. 터미널 1 — 주방(백엔드, 8000)
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m rag.build_corpus      # 공식문서 수집 (최초 1회만)
.venv/bin/python -m rag.server            # → http://localhost:8000
```

```bash
# 2. 터미널 2 — 홀(프런트엔드, 5173)   ※ Cmd + T 로 새 탭/창
cd redhat-solution-sales-navigator
npm install
npm run dev                               # → http://localhost:5173
```

```bash
# 3. 브라우저에서 열기
open http://localhost:5173
```

**막혔을 때 확인 순서 (이 순서만 기억하면 됩니다)**

1. **어디에 서 있나?** → `pwd`, `ls` (`.git`, `package.json`이 보여야 함)
2. **터미널이 2개 다 켜져 있나?** → 하나는 `rag.server`, 하나는 `npm run dev`
3. **`npm`이 없나?** → `brew install node`
4. **`localhost:5173`이 안 열리나?** → 터미널 2에 `Local: http://localhost:5173/`가 떠 있는지 확인
5. **화면은 뜨는데 "서버 연결 실패"인가?** → 터미널 1(8000)이 꺼져 있음

## 오늘의 다섯 문장

1. **GitHub는 창고, 내 폴더는 작업실.** 둘 다 있는 게 정상이고, `clone`은 최초 1회, `pull`은 그다음부터.
2. **창고는 코드를 보관하지, 실행해 주지 않는다.** 실행은 내 컴퓨터(`localhost`)이거나 빌린 클라우드 컴퓨터에서.
3. **터미널 에러의 절반은 '위치' 문제.** `pwd` → `ls` → `cd`, 그리고 에러에 나온 파일 이름이 곧 찾는 위치.
4. **홀(프런트)과 주방(백엔드)은 다른 프로그램**이라 터미널도 두 개. `localhost`는 내 컴퓨터가 잠깐 1인용 서버가 되는 것.
5. **GitHub Pages는 전시관, API 키는 출입증.** 키 없이도 검색과 거절은 돌아가니, 순서대로 하나씩 확인하면 된다.

에러 메시지는 혼내는 말이 아니라 **"지금 어디를 보고 있는지"를 알려 주는 안내판**입니다. 오늘 다섯 번 막힌 것도, 결국 같은 그림 하나를 다섯 각도에서 확인한 과정이었습니다.
