*"이 챗봇이 인사팀 문서를 영업팀한테 답해 주면 어떻게 됩니까?"*

이 질문 하나에 **인증·인가·암호화·키 관리·감사 로그**가 전부 걸려 있습니다. SA 면접에서도 보안은 단골이고, 특히 "RAG에서 문서 권한을 어떻게 통제했나"는 AI SA 지원자에게 거의 확정으로 나오는 질문입니다.

1. **인증(AuthN) vs 인가(AuthZ)** — 신분과 권한은 다르다

4. **대칭키 vs 비대칭키 · KMS** — 키를 어디에 두고 어떻게 돌리는가

7. **Secret Manager vs .env** — API 키를 어디에 두는가

## 🪪 1. 인증(AuthN) vs 인가(AuthZ): 신분과 권한

**일상 비유**: **인증은 신분증 검사**, **인가는 출입증 등급 확인**입니다. 신분증이 진짜임을 확인했다고 해서 서버실에 들어갈 수 있는 건 아닙니다. 사원증이 있어도(인증) 연구소 출입 권한(인가)이 없으면 문이 안 열립니다.

**핵심 원리**: 두 개념은 실패할 때 **응답 코드가 다릅니다**. 이 차이를 아는 것이 면접에서 실력을 보여 주는 지점입니다.

| 구분 | 질문 | 실패 시 응답 | 수단 |
| --- | --- | --- | --- |
| 인증 AuthN | "당신은 누구인가" | **401 Unauthorized** | 비밀번호, MFA, 인증서 |
| 인가 AuthZ | "당신은 이걸 할 수 있나" | **403 Forbidden** | 역할, 정책, 속성 |

> 이름이 함정입니다. **401 Unauthorized는 실제로는 인증 실패**입니다. 403이 인가 실패입니다.

**심층 방어(defense in depth)** 관점도 함께 기억합니다. 인증은 계층마다 반복됩니다 — 사용자 로그인, 서비스 간 mTLS, API 키, DB 자격 증명. "한 번 통과했으니 다 믿는다"가 사고의 시작입니다.

### 🎤 면접 30초 답변

> "인증은 사용자가 주장하는 신원이 진짜인지 확인하는 것이고, 인가는 인증된 주체가 특정 리소스에 특정 행위를 할 수 있는지 판단하는 것입니다. 그래서 토큰이 없거나 위조됐으면 401, 토큰은 유효하지만 권한이 없으면 403을 반환합니다. 실무에서는 인증을 통과했다고 내부 호출을 무조건 신뢰하지 않고, 서비스 간에는 mTLS나 서비스 토큰으로 다시 인증하고, 리소스 접근마다 인가를 재확인하는 심층 방어 구조를 씁니다."

### 🎯 SA 실무 포인트

**1) MFA는 "옵션"이 아니라 고객 보안 심사의 통과 조건입니다.**
관리자 콘솔·배포 파이프라인·클라우드 루트 계정은 MFA 필수로 제안하고, 문서에 "MFA 적용 계정 목록"을 표로 붙이면 심사가 빨라집니다.

**2) 인가 실패를 401로 뭉뚱그리면 운영이 망가집니다.**
401은 "다시 로그인" 흐름을 유발하고 무한 리다이렉트를 만들 수 있습니다. 403은 "권한 요청" 안내로 이어져야 합니다.

**3) 서비스 계정은 사람 계정과 분리하세요.**
사람 계정 키를 배치 작업에 쓰면 그 사람이 퇴사할 때 무엇이 멈출지 아무도 모릅니다. 서비스 계정 + 최소 권한 + 소유자 표기가 기본입니다.

## 🎫 2. OAuth 2.0 · OIDC · SSO(SAML) · JWT

**일상 비유**: OAuth는 **호텔 발렛 열쇠**입니다. 내 차 키(비밀번호)를 발렛 기사에게 주지 않고, "이 차만, 이 시간 동안" 주차할 수 있는 **제한된 열쇠**를 받아 씁니다. OIDC는 그 열쇠에 "내가 누구인지"가 적힌 **신분증**을 붙인 것이고, SSO는 호텔·레스토랑·라운지 어디서든 **같은 카드 한 장**으로 통과하는 것입니다.

**핵심 원리**: 네 가지를 구분해야 합니다.

| 이름 | 정체 | 하는 일 |
| --- | --- | --- |
| OAuth 2.0 | **인가** 프레임워크 | 제3자 앱에 제한된 접근 권한 위임 |
| OIDC | OAuth 위의 **인증** 계층 | ID 토큰(JWT)으로 사용자 신원 제공 |
| SAML 2.0 | XML 기반 SSO 표준 | 기업 IdP ↔ 앱 간 인증 연동 |
| JWT | 토큰 **형식** | 서명된 클레임 묶음 (자체 검증 가능) |

**Authorization Code + PKCE 흐름** (웹·모바일 표준)

1. 앱이 IdP로 리다이렉트 (`client_id`, `redirect_uri`, `code_challenge`)
2. 사용자가 IdP에서 로그인 (앱은 비밀번호를 **절대 보지 못함**)
3. IdP가 **일회용 code**를 돌려줌
4. 앱이 백채널에서 code + `code_verifier`로 토큰 교환
5. 받은 것: **access token**(API 호출용), **refresh token**(갱신용), **id token**(신원)

**JWT의 구조**는 세 조각입니다.

```text
header.payload.signature
{ alg, typ } . { sub, iss, aud, exp, scope } . HMAC/RSA 서명
```

**중요한 감각**: JWT는 **서명 검증만으로 위조를 막을 수 있지만, 취소(revocation)가 어렵습니다**. 발급하면 `exp`까지 유효합니다. 그래서 access token 수명을 짧게(5~15분) 두고 refresh token으로 갱신하며, 즉시 차단이 필요하면 블랙리스트나 세션 저장소를 둡니다.

### 🎤 면접 30초 답변

> "OAuth 2.0은 인가 프레임워크로, 사용자가 자기 비밀번호를 제3자 앱에 주지 않고 제한된 권한의 access token을 발급해 위임하는 구조입니다. 웹에서는 Authorization Code 흐름에 PKCE를 붙여 code 탈취를 막고, 토큰 교환은 백채널에서 합니다. OIDC는 OAuth 위에 인증 계층을 얹어 ID 토큰으로 사용자 신원을 전달하는 것이고, SAML은 기업 SSO에서 XML 기반으로 같은 역할을 합니다. JWT는 토큰 형식으로 서명 검증만으로 위조를 막을 수 있지만 발급 후 취소가 어렵기 때문에, access token 수명을 짧게 두고 refresh token으로 갱신하며 필요하면 블랙리스트를 둡니다."

### 🎯 SA 실무 포인트

**1) 고객사 IdP 연동은 프로젝트 리스크 1순위입니다.**
"SSO 연동" 한 줄이 실제로는 ① IdP 종류(Entra ID, Okta, Keycloak) ② 프로토콜(SAML vs OIDC) ③ 클레임 매핑(사번·부서·직급) ④ 그룹 동기화 주기 ⑤ 테스트 계정 확보로 쪼개집니다. 견적·일정에 이 5개를 명시적으로 넣지 않으면 나중에 전부 추가 공수가 됩니다.

**2) 클레임 매핑이 곧 권한 설계입니다.**
`department`, `groups`, `employeeType` 같은 클레임을 어떤 필드로 받을지 미리 합의해야 RAG 문서 필터를 만들 수 있습니다. 여기서 "부서 정보를 못 받는다"가 나오면 ABAC 설계가 무너지므로 **PoV 1주차에 확인**합니다.

**3) 토큰 수명과 사용자 경험은 트레이드오프입니다.**
5분짜리 토큰은 안전하지만 잦은 갱신이 필요하고, 모바일 백그라운드에서 갱신 실패가 로그아웃으로 보입니다. refresh token 회전(rotation)과 재사용 탐지로 균형을 잡습니다.

## 🗂️ 3. RBAC vs ABAC: 사내 RAG 권한 통제의 실제 구조

**일상 비유**: **RBAC은 직급별 출입증 색**입니다. 파란 카드는 3층까지, 빨간 카드는 전 층. **ABAC은 경비원이 상황까지 보는 것**입니다 — "이 사람은 인사팀이고, 지금은 근무시간이고, 이 문서는 인사 문서이므로 통과". 색만으로는 부족할 때 상황을 읽는 방식입니다.

**핵심 원리**: RBAC은 **역할**에 권한을 묶고, ABAC은 **속성**(사용자·리소스·환경)의 조합으로 판단합니다.

| 구분 | 판단 기준 | 장점 | 한계 |
| --- | --- | --- | --- |
| RBAC | 역할(부서·직급) | 단순, 감사·설명 쉬움 | 예외 상황·개별 문서 반영 어려움 |
| ABAC | 속성 조합(부서+문서등급+시간) | 세밀, 동적 | 정책 복잡, 테스트 어려움 |
| ReBAC | 관계(소유·공유) | 문서 단위 공유에 강함 | 그래프 관리 필요 |

### 사내 RAG에서 권한은 어디서 걸리는가

RAG 권한 통제는 **검색 전(pre-filter)** 과 **검색 후(post-filter)** 로 나뉘고, 이 차이가 답변 품질과 보안을 동시에 좌우합니다.

```text
[질문] → [권한 컨텍스트 확보(부서·문서 ACL)]
      → [벡터 검색 시 메타데이터 필터]  ← pre-filter (정답)
      → [LLM 프롬프트 조립] → [답변]
```

- **pre-filter(권장)**: 벡터 검색 단계에서 `department IN (...) AND classification <= user.clearance`를 강제. 검색 결과 자체에 권한 없는 문서가 없습니다.
- **post-filter(위험)**: 검색은 다 하고 결과에서 걸러냄. 상위 5개가 모두 걸러져 **답변이 빈약해지고**, 구현 실수 시 그대로 유출됩니다.
- **프롬프트 지시(금지)**: "권한 없는 문서는 인용하지 마" 같은 문장은 통제가 아닙니다. LLM은 지시를 무시할 수 있습니다.

### 🎤 면접 30초 답변

> "RBAC은 역할에 권한을 부여하는 방식이라 단순하고 감사에 유리하지만, 같은 부서 안에서도 문서별 예외를 반영하기 어렵습니다. ABAC은 사용자·리소스·환경 속성의 조합으로 판단해서 세밀한 통제가 가능합니다. 사내 RAG에서는 두 개를 섞습니다. 부서·직급 기반으로 검색 범위를 정하고, 문서마다 ACL 메타데이터를 붙여 벡터 검색 시점에 필터로 강제합니다. 핵심은 프롬프트로 통제하지 않고 **검색 전에 걸러내는 pre-filter** 방식이라는 점이고, 그래야 권한 없는 문서가 애초에 LLM 컨텍스트에 들어가지 않습니다."

### 🎯 SA 실무 포인트

**1) "권한 통제 했습니다"보다 "어디서 걸렀습니다"를 보여주세요.**
아키텍처 그림에 **필터가 걸리는 지점**을 표시하고, 감사 시 "이 질문으로 검색된 문서 목록"을 재현할 수 있어야 합니다. 이게 PoV 평가표에서 실제로 점수를 가르는 부분입니다.

**2) 문서 ACL은 원본 시스템이 진실입니다.**
SharePoint·Confluence·Drive의 권한을 복제하지 말고 **동기화**하세요. 복제하면 원본에서 권한이 바뀐 뒤에도 RAG가 옛 권한으로 답합니다. 동기화 지연(SLA)을 문서에 명시합니다.

**3) 권한 필터는 검색 품질을 떨어뜨립니다 — 미리 말해야 합니다.**
상위 후보 20개 중 15개가 권한 밖이면 실제 답변 근거는 5개뿐입니다. 후보 수(k)를 늘리거나 하이브리드 검색으로 보완하고, **"권한 없는 문서는 검색되지 않는다"는 트레이드오프**를 고객에게 정직하게 설명합니다.

## 🔑 4. 대칭키 vs 비대칭키 · KMS

**일상 비유**: **대칭키는 하나의 자물쇠와 열쇠**입니다. 빠르지만 열쇠를 건네는 순간이 위험합니다. **비대칭키는 자물쇠(공개키)와 열쇠(개인키)가 분리된 것**입니다. 자물쇠는 아무에게나 나눠 줘도 되고, 열쇠만 숨기면 됩니다. **KMS는 열쇠를 보관하는 은행 금고**입니다 — 열쇠를 꺼내 오지 않고, 금고 안에서 열고 닫게 합니다.

**핵심 원리**: 두 방식을 섞는 것이 **봉투 암호화(envelope encryption)** 입니다.

| 구분 | 속도 | 키 배포 | 쓰는 자리 |
| --- | --- | --- | --- |
| 대칭키 (AES) | 빠름 | 사전 공유 필요 | 대량 데이터 암호화 |
| 비대칭키 (RSA/ECC) | 느림 | 공개키 배포 자유 | 키 교환, 전자서명, 인증서 |

**봉투 암호화 순서**

1. 데이터마다 **DEK**(데이터 키, 대칭키)를 생성
2. DEK로 데이터를 암호화하고 저장
3. DEK 자체를 **KMS의 KEK**(마스터 키)로 암호화해 함께 저장
4. 조회 시 KMS에 복호화 요청 → DEK 획득 → 데이터 복호화

이 구조의 핵심은 **평문 키가 애플리케이션 메모리 밖으로 나오지 않고, KMS 접근 자체가 감사 로그에 남는다**는 점입니다. 키 교체(rotation)도 KEK만 바꾸면 되므로 대량 데이터를 다시 암호화하지 않아도 됩니다.

### 🎤 면접 30초 답변

> "대칭키는 같은 키로 암복호화를 해서 빠르지만 키를 안전하게 전달하기 어렵고, 비대칭키는 공개키로 암호화하고 개인키로 복호화해서 키 배포 문제를 해결하지만 연산이 느립니다. 실무에서는 둘을 섞은 봉투 암호화를 씁니다. 데이터는 데이터 키로 대칭 암호화하고, 그 데이터 키를 KMS의 마스터 키로 감싸 저장합니다. 애플리케이션은 KMS에 복호화를 요청해서 데이터 키를 받고, 그 요청은 감사 로그에 남습니다. 이렇게 하면 평문 마스터 키가 애플리케이션에 존재하지 않고, 키 교체도 마스터 키만 바꾸면 됩니다."

### 🎯 SA 실무 포인트

**1) 고객이 묻는 것은 암호화 알고리즘이 아니라 키 소유권입니다.**
"키를 우리가 관리할 수 있나"가 쟁점입니다. AWS KMS 기본 키 vs **BYOK(고객 관리 키)** vs **HYOK(외부 HSM)** 를 구분해 제시하고, 각각의 운영 부담(키 삭제 시 데이터 복구 불가, 교체 주기)을 함께 적습니다.

**2) 키 삭제는 되돌릴 수 없습니다.**
KMS 키 삭제 대기 기간(7~30일)을 두고, 삭제 권한을 아키텍처 검토 대상에 넣습니다. "실수로 키 지워서 백업까지 못 읽는" 사고가 실제로 있습니다.

**3) 암호화 대상 목록을 먼저 만드세요.**
저장 데이터(벡터 DB 포함), 백업, 로그, 모델 프롬프트·응답 캐시, 전송 구간. **벡터 임베딩도 원문을 복원할 수 있는 수준의 정보**라는 점을 잊으면 규제 검토에서 지적됩니다.

## 🖥️ 5. 터미널 · 셸 · 커널 · SSH · Bastion Host

**일상 비유**: 식당을 떠올려 봅시다. 손님(나)이 주문하는 **창구**가 터미널, 주문을 주방 언어로 바꿔 전달하는 **점원**이 셸, 실제로 요리를 만드는 **주방**이 커널입니다. **SSH는 남의 식당 주방에 들어가는 암호화된 전용 통로**이고, **Bastion은 그 통로가 지나야 하는 유일한 경비실**입니다.

| 역할 | 식당 비유 | 컴퓨터에서는 |
| --- | --- | --- |
| 주문 창구 | 내가 말하고 결과를 받는 창 | **터미널 (Terminal)** |
| 점원 | 주문을 주방 언어로 번역 | **셸 (Shell)** |
| 주방 | 실제로 요리를 만듦 | **커널 (Kernel)** |
| 전용 통로 | 암호화된 원격 접속 | **SSH** |
| 경비실 | 유일한 출입 경로 | **Bastion Host** |

### ① 터미널: 창일 뿐, 명령을 이해하지 못한다

터미널은 **키보드 입력을 글자로 받아 화면에 출력하는 UI 프로그램**입니다. 지금은 하드웨어 단말기를 흉내 낸 **터미널 에뮬레이터**(iTerm2, Windows Terminal, Alacritty)를 씁니다. `ls`가 무슨 명령인지 모릅니다.

SSH로 서버에 붙으면 서버 쪽에 **PTY(의사 터미널)** 가 생깁니다. 그래서 원격인데도 프롬프트가 뜨고, `Ctrl+C`가 동작하고, `vim` 같은 전체 화면 프로그램이 정상 실행됩니다.

### ② 셸: 명령어를 해석하는 인터페이스

셸은 입력 문자열을 **해석(parsing)** 해 프로그램을 실행하고, 커널에 **시스템 콜**로 요청합니다. `bash`, `zsh`, `PowerShell`이 셸입니다.

`ls`를 쳤을 때 실제로 벌어지는 일:

1. 환경변수 `PATH`를 뒤져 `/bin/ls` 실행 파일을 찾는다
2. `fork()`로 자신을 복제해 자식 프로세스를 만든다
3. 자식이 `execve("/bin/ls", ...)`로 `ls` 프로그램으로 갈아입는다
4. 결과가 표준출력으로 나오고 터미널 창에 그려진다

**셸도 그냥 프로그램 하나**입니다. 그래서 `zsh` 안에서 `bash`를 치면 셸 안에 셸이 뜨고, `exit`를 치면 그 창이 닫힙니다. 이름이 **shell(껍데기)** 인 이유는 커널이라는 알맹이를 감싼 껍데기이기 때문입니다.

### ③ 커널: 권한을 검사하고 실제로 실행한다

일반 프로그램은 디스크·메모리를 직접 만질 수 없습니다. `open()`, `read()`, `write()`, `fork()` 같은 **시스템 콜**로만 요청하고, 커널이 매번 **권한을 검사**합니다. `sudo`가 필요한 이유도, 컨테이너 격리가 커널 기능(namespace·cgroup) 위에 서 있는 이유도 이 경계 때문입니다.

```text
[내 키보드]
   ↓
[터미널 에뮬레이터]   ← 창(UI). 명령의 뜻은 모름
   ↓ 글자 전달 (PTY)
[셸: bash / zsh]      ← 해석, PATH 탐색, fork + execve
   ↓ 시스템 콜
[커널]                ← 권한 검사 후 실행
   ↓
[하드웨어: CPU · SSD · NIC]
```

### ④ SSH: 암호화된 원격 셸 (기본 포트 22)

SSH는 단순히 "암호화하는 기술"이 아니라, 접속 한 번에 **네 단계**를 밟습니다.

| 단계 | 하는 일 | 막는 위협 |
| --- | --- | --- |
| 키 교환 | ECDHE로 세션 대칭키 생성 (키는 전송 안 됨) | 도청, 과거 세션 복호화 |
| 서버 인증 | 호스트 키 서명, `known_hosts`와 비교 | 중간자 공격(MITM) |
| 사용자 인증 | 개인키 서명 → 서버가 공개키로 검증 | 무차별 대입, 키 탈취 |
| 세션 암호화 | 대칭키로 전 구간 + 무결성(MAC) | 변조 |

> **비대칭키는 문을 여는 데, 대칭키는 짐을 나르는 데 씁니다.** SSH도 TLS도 같은 구조입니다.

```bash
ssh-keygen -t ed25519 -C "haem@laptop"   # 1) 키 쌍 생성 (ed25519 권장)
cat ~/.ssh/id_ed25519.pub                # 2) 공개키만 서버에 등록
ssh -i ~/.ssh/id_ed25519 ec2-user@10.0.1.25
```

Bastion을 경유하는 구성은 `~/.ssh/config`로 단순화합니다.

```text
Host bastion
  HostName 1.2.3.4
  User ec2-user
  IdentityFile ~/.ssh/id_ed25519

Host app-*
  ProxyJump bastion
  User ec2-user
  IdentityFile ~/.ssh/id_ed25519
```

이제 `ssh app-01`만 쳐도 Bastion을 자동으로 거칩니다.

**비밀번호 인증 vs 공개키 인증**

| 항목 | 비밀번호 | 공개키 |
| --- | --- | --- |
| 네트워크로 오가는 것 | 비밀번호(터널 안) | **서명값** (개인키는 로컬) |
| 무차별 대입 | 취약 | 사실상 불가 |
| 추적·회수 | 공유 계정은 불가 | 키별 발급·회수로 추적 |
| 자동화 | 어려움 | 적합 |

### 🎤 면접 30초 답변 (터미널 · 셸 · SSH)

> "터미널은 입력을 받아 화면에 그리는 UI 프로그램이고 명령을 해석하지 못합니다. 셸은 그 뒤에서 명령을 해석해 프로그램을 실행하고 커널에 시스템 콜로 요청하는 인터페이스이고, 커널은 프로세스·메모리·파일·네트워크를 실제로 관리하며 유저 공간의 접근을 권한 검사합니다. SSH는 이 계층을 네트워크 너머로 안전하게 늘린 프로토콜로, 22번 포트를 쓰고 키 교환으로 세션 키를 만들고 호스트 키로 서버를 인증한 뒤 공개키 인증으로 사용자를 확인합니다. 개인키는 네트워크로 나가지 않고 서명만 전송되며, 운영 환경에서는 22번을 인터넷에 열지 않고 Bastion이나 Session Manager를 경유합니다."

### 🎯 SA 실무 포인트

**1) Bastion은 단일 장애점이자 단일 공격점입니다.**
Bastion 하나에 모두가 붙으면 그 서버가 뚫리면 끝이고, 그 서버가 죽으면 아무도 못 들어갑니다. 그래서 ① AZ 이중화 ② MFA ③ 세션 로깅 ④ 키 대신 단기 자격 증명(AWS SSM Session Manager는 인바운드 포트 없이 접속) ⑤ 명령 감사를 한 세트로 설계합니다.

**2) 폐쇄망에서는 키 배포가 설계 항목입니다.**
인터넷이 막힌 망에서는 `ssh-copy-id`도 메일도 못 씁니다. 점프 서버 경유 배포, 오프라인 매체 반입, 발급·회수 절차를 문서화합니다. "접속되게 해 주세요"가 아니라 **"누가 어떤 키로 어디까지"** 를 정의하는 일입니다.

**3) 자주 나오는 실무 함정 3가지**

| 증상 | 원인 | 조치 |
| --- | --- | --- |
| `UNPROTECTED PRIVATE KEY FILE` | 개인키 권한 과다 | `chmod 600 ~/.ssh/id_ed25519` |
| `HOST IDENTIFICATION HAS CHANGED` | 서버 재생성 또는 MITM | 지문 먼저 확인, 무조건 삭제 금지 |
| `no mutual signature algorithm` | OpenSSH 8.8+ SHA-1 `ssh-rsa` 비활성 | Ed25519 재발급 |

## 🚧 6. Zero Trust: "내부망이니까"를 버리는 원칙

**일상 비유**: 예전 사옥은 **1층 경비실만 통과하면 건물 안은 자유**였습니다. 제로 트러스트는 **모든 문마다 사원증을 다시 태그**하는 건물입니다. 회의실, 서버실, 자료실 각각 확인합니다.

**핵심 원리**: "네트워크 위치는 신뢰의 근거가 아니다"라는 전제에서 출발합니다. 세 가지 원칙으로 요약됩니다.

| 원칙 | 의미 | 구현 예 |
| --- | --- | --- |
| 명시적 검증 | 매 접근마다 신원·기기·맥락 확인 | MFA, 기기 상태, 조건부 접근 |
| 최소 권한 | 필요한 만큼만, 임시로 | JIT 권한, 짧은 토큰 수명 |
| 침해 가정 | 이미 뚫렸다고 가정하고 설계 | 마이크로 세그멘테이션, mTLS |

**전통 경계 vs 제로 트러스트**

| 항목 | 전통 경계 모델 | 제로 트러스트 |
| --- | --- | --- |
| 신뢰 근거 | 사내망 안 = 신뢰 | 매 요청 검증 |
| 이동 경로 | VPN 한 번 통과 후 자유 | 서비스 단위 통제 |
| 사고 영향 | 내부 전체 확산 | 구간 격리 |
| AI 서비스 | "내부 챗봇이니 괜찮다" | 에이전트·도구 권한까지 통제 |

### 🎤 면접 30초 답변

> "제로 트러스트는 네트워크 위치를 신뢰의 근거로 삼지 않는 보안 모델입니다. 내부망에서 온 요청도 매번 신원·기기 상태·맥락을 검증하고, 최소 권한을 임시로 부여하며, 이미 침해됐다고 가정하고 구간을 격리합니다. 구현은 MFA와 조건부 접근, 서비스 간 mTLS, 마이크로 세그멘테이션, 짧은 수명의 자격 증명으로 이뤄집니다. AI 시스템에서는 특히 중요합니다. 에이전트가 내부 도구를 호출하고 데이터를 읽을 수 있기 때문에, 에이전트가 가진 토큰의 범위를 사용자 권한으로 제한하고 호출마다 인가를 확인해야 합니다."

### 🎯 SA 실무 포인트

**1) AI 에이전트는 제로 트러스트의 최대 사각지대입니다.**
LLM이 DB를 조회하고 메일을 보내는 에이전트라면, 그 에이전트는 **사용자 권한을 위임받은 주체**입니다. "서비스 계정 하나로 모든 사용자 요청 처리"는 교과서적 위반입니다. 요청마다 사용자 컨텍스트를 전달(on-behalf-of 토큰)하고, 도구 호출마다 인가를 재확인합니다.

**2) 단계적 로드맵으로 제안하세요.**
한 번에 다 바꾸는 고객은 없습니다. ① 자산·흐름 식별 → ② MFA·조건부 접근 → ③ 서비스 간 mTLS → ④ 마이크로 세그멘테이션 → ⑤ 상시 검증. 이 5단계를 성숙도 표로 제시하면 "지금 어디까지 가능한가"를 합의할 수 있습니다.

## 🗝️ 7. Secret Manager vs .env: API 키를 어디에 두는가

**일상 비유**: `.env` 파일은 **책상 서랍에 둔 집 열쇠 메모**입니다. 편하지만, 파일을 복사하는 순간(깃허브 커밋, 슬랙 공유, 이미지 빌드) 열쇠도 같이 복사됩니다. **Secret Manager는 지문인식 금고**입니다 — 꺼내는 사람과 시점이 기록되고, 필요하면 즉시 잠급니다.

**핵심 원리**: `.env`는 **파일**이고 Secret Manager는 **서비스**입니다. 차이는 노출 경로와 회전 능력입니다.

| 항목 | `.env` 파일 | Secret Manager |
| --- | --- | --- |
| 저장 위치 | 코드 옆 파일, 컨테이너 이미지 | 암호화된 중앙 저장소 |
| 접근 통제 | 파일 권한 (사실상 전원) | IAM 정책, 세밀한 권한 |
| 감사 로그 | 없음 | 누가 언제 읽었는지 기록 |
| 교체(rotation) | 코드·재배포 필요 | 중앙에서 교체, 재시작만 |
| 유출 위험 | 커밋·이미지 레이어에 남음 | 짧은 수명 자격 증명 가능 |

**핵심 감각**: `.env`가 나쁜 게 아니라 **비밀을 파일에 두는 것**이 문제입니다. 특히 컨테이너 이미지에 `COPY .env`가 들어가면 그 이미지를 받은 누구나 키를 갖습니다. `.gitignore`는 로컬 실수를 막을 뿐, 이미지와 로그는 막지 못합니다.

### 🎤 면접 30초 답변

> ".env 파일은 비밀을 코드 저장소 옆 파일로 관리하는 방식이라 편하지만, 커밋이나 컨테이너 이미지 레이어에 섞여 유출될 수 있고 접근 감사도 없습니다. Secret Manager는 비밀을 암호화된 중앙 저장소에 두고 IAM으로 접근을 통제하며, 누가 언제 읽었는지 감사 로그를 남기고 교체도 중앙에서 처리합니다. 실무에서는 코드에는 비밀을 두지 않고 환경변수로 주입하되, 그 값의 출처를 Secret Manager나 IRSA 같은 워크로드 자격 증명으로 두고, 가능하면 장기 키 대신 수명이 짧은 토큰을 씁니다."

### 🎯 SA 실무 포인트

**1) LLM API 키는 고객사에서 가장 예민한 자산입니다.**
키 하나로 과금이 발생하고, 유출되면 조직 전체가 위험해집니다. 제안서에 **키 보관 위치, 주입 방식, 교체 주기, 유출 시 대응(즉시 폐기·재발급·사용 로그 소급)** 4가지를 명시하면 보안 심사에서 신뢰를 얻습니다.

**2) 게이트웨이 패턴으로 키를 한 곳에 모으세요.**
각 애플리케이션이 LLM 키를 직접 들면 키가 N개로 늘어납니다. **AI 게이트웨이**가 키를 보관하고 내부 앱은 게이트웨이 토큰만 쓰게 하면, 키 회전·비용 집계·차단이 한 지점에서 됩니다.

**3) 로그에 비밀이 새는 경로를 막으세요.**
프롬프트 로그, 에러 스택, 프록시 액세스 로그에 `Authorization` 헤더가 찍히는 사고가 흔합니다. 마스킹 규칙과 로그 보존 정책을 함께 설계합니다.

## 📜 8. 감사 로그(Audit Log) & 데이터 레지던시(Data Residency)

**일상 비유**: 감사 로그는 건물의 **CCTV 기록**입니다. 사고가 난 뒤에 "누가 언제 어디로 들어갔나"를 되짚는 유일한 수단입니다. 데이터 레지던시는 **"이 서류는 반드시 국내 금고에만 보관"** 이라는 규정입니다.

**핵심 원리**: 규제 산업에서 감사 로그는 "있으면 좋은 것"이 아니라 **요건**입니다.

| 항목 | 최소 기록 내용 |
| --- | --- |
| 누가 | 사용자 ID, 서비스 계정, IP |
| 언제 | 타임스탬프(UTC), 요청 ID |
| 무엇을 | 조회·수정한 리소스 ID, 질의 내용 |
| 결과 | 성공·실패, 차단 사유 |

**AI 시스템에서 감사 로그가 특히 요구되는 것**: ① 어떤 질문이 ② 어떤 문서를 근거로 ③ 어떤 모델이 ④ 어떤 답변을 생성했는지. 이 4개가 있어야 "왜 이런 답이 나왔나"를 소급해 설명할 수 있습니다.

**데이터 레지던시**는 데이터가 **물리적으로 어느 국가·리전에 저장·처리되는지**를 규정합니다. 국내 고객사는 "국내 리전에서만 처리, 국경 밖 전송 금지"를 요구하는 경우가 많습니다.

| 요구 | 설계 대응 |
| --- | --- |
| 데이터가 국내에만 | 리전 고정, 크로스 리전 복제 금지 |
| 국외 모델 API 금지 | 사내 구축 모델 또는 국내 리전 엔드포인트 |
| 학습 재사용 금지 | no-training 옵션, 리텐션 0 설정 확인 |
| 삭제 요구권 | 데이터 카탈로그·삭제 파이프라인 |

### 🎤 면접 30초 답변

> "감사 로그는 누가 언제 무엇을 했는지 재구성할 수 있게 하는 기록으로, 규제 산업에서는 설계 요건입니다. AI 시스템에서는 질문·검색된 문서·사용 모델·생성 답변을 함께 남겨야 답변의 근거를 소급해 설명할 수 있습니다. 데이터 레지던시는 데이터가 물리적으로 어느 리전에 저장·처리되는지를 규정하는 요구로, 국내 리전 고정과 크로스 리전 복제 금지, 국외 API 호출 금지로 대응합니다. 이 두 가지는 보안이 아니라 컴플라이언스 요건이기 때문에, 아키텍처 초기에 리전·리텐션·삭제 정책을 확정하지 않으면 나중에 구조를 다시 짜야 합니다."

### 🎯 SA 실무 포인트

**1) 감사 로그는 쓰기 전용·별도 저장소에 둡니다.**
애플리케이션이 자기 로그를 수정·삭제할 수 있으면 감사 로그가 아닙니다. WORM(한 번 쓰면 수정 불가) 스토리지, 별도 계정, 보존 기간(예: 1년/3년)을 명시합니다.

**2) 개인정보가 로그에 들어가는 순간이 위험합니다.**
프롬프트에 고객 이름·주민번호가 들어갈 수 있습니다. **저장 전 마스킹**과 원문 보관이 필요한 경우의 암호화·접근 통제를 분리해 설계합니다. "로그는 다 남기면 좋다"가 오히려 위반이 됩니다.

**3) 리전 선택은 모델 선택보다 먼저입니다.**
"이 모델이 좋다"로 시작하면 나중에 "이 모델은 국내 리전이 없다"로 프로젝트가 멈춥니다. **데이터 주권 → 리전 → 사용 가능한 모델** 순서로 결정합니다.
