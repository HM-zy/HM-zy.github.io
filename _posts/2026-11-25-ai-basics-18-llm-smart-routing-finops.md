*"월말에 청구서를 열어봤더니 예상의 네 배가 나왔습니다. 원인은 하나였습니다. 모든 요청이 가장 비싼 모델로 가고 있었습니다."*

AI 서비스 비용은 **모델 단가 × 토큰 양**으로 결정됩니다. 그런데 우리 서비스에 오는 요청의 70%는 *"이번 달 매출 얼마야?"* 처럼 경량 모델로도 충분한 질문입니다. **모든 질문에 가장 비싼 모델을 쓰는 것은, 세 정거장 가는 길에 매번 택시를 타는 것**과 같습니다.

---

## 🚕 택시와 버스 사이: 라우팅은 '요청을 분류하는 정책'이다

- **일상 비유**: 세 정거장은 버스로 충분하고, 공항은 버스로 무리입니다. **거리를 보고 교통수단을 고르는 것**이 라우팅입니다.
- **핵심 원리**: 요청의 **복잡도 신호**(길이, 도구 필요 개수, 멀티턴, 추론 유도 표현)를 점수화해 **경량·중형·대형** 모델로 보내고, 경량 모델의 답이 불안하면 **상위 모델로 재시도(escalation)** 합니다.

이 계층을 만드는 컴포넌트를 **FinOps 게이트웨이** 또는 **LLM 게이트웨이**라고 부릅니다. 애플리케이션은 게이트웨이에만 요청하고, 어떤 모델로 보낼지는 게이트웨이가 정합니다. 덕분에 앱 코드를 고치지 않고 정책만 바꿔 비용을 조정할 수 있습니다.

---

## 🧭 네 가지 라우팅 신호

| 신호 | 어떻게 판단하나 | 예 |
| --- | --- | --- |
| **규칙 기반** | 키워드·길이·정규식 | "요약", "번역" → 경량 / "설계", "근거", "트레이드오프" → 대형 |
| **분류기** | 작은 모델이 난이도 라벨을 붙임 | `simple / medium / complex` 3-class |
| **도구 필요성** | 도구 호출 개수·멀티턴 수 | 3개 이상 도구 조합 → 대형 |
| **예산·지연** | 팀별·기능별 남은 예산, SLA | 야간 배치 → 저가 모델 / 실시간 → 지연 우선 |

실무에서는 **규칙 + 분류기 하이브리드**가 가장 흔합니다. 규칙만 쓰면 표현이 조금만 바뀌어도 오분류하고, 분류기만 쓰면 설명 가능성이 떨어집니다(장애 때 디버깅이 어려움).

## 📊 정책 표 예시

| 등급 | 판단 예시 | 보내는 곳 | 기대 효과 |
| --- | --- | --- | --- |
| **Simple** | FAQ, 요약, 번역, 정형 추출, 1턴 | 경량 모델 | 비용 최소, 지연 최소 |
| **Medium** | 사내 문서 RAG 답변, 2~3턴 대화, 짧은 도구 1~2개 | 중형 모델 | 품질·비용 균형 |
| **Complex** | 다단계 추론, 코드 생성·리뷰, 도구 3개 이상, 8K 토큰 이상 | 대형 모델 | 정확도 우선 |

주의: 위 표는 **정책 예시**이고, 실제 결정은 **골든셋으로 측정한 정확도**가 합니다. 라우팅 후 정확도가 떨어졌다면 아낀 돈보다 잃은 신뢰가 큽니다.

## 💻 5분 실습: 라우터 + 절감률 계산 55줄

요청 1,000건을 가정하고, "전부 대형 모델"과 "라우팅 적용"의 비용을 직접 비교합니다.

```python
import random

# 비교용 가정 단가 ($/1M tokens, 입력·출력) — 실제 단가는 각 벤더 공식 가격표로 바꿔 넣으세요
PRICES = {"small": (0.15, 0.60), "medium": (2.50, 10.0), "large": (15.0, 60.0)}

HARD = ["설계", "근거", "트레이드오프", "코드", "여러 단계", "비교해서", "증명"]
EASY = ["요약", "번역", "정리해줘", "몇 개", "언제", "어디"]

def route(prompt, in_tok, n_tools=0, turn=1):
    score = 0
    if in_tok > 4000: score += 2
    if n_tools >= 3:   score += 2
    elif n_tools >= 1: score += 1        # 도구가 필요한 질문은 최소 중형
    if turn >= 3:      score += 1
    score += sum(1 for s in HARD if s in prompt)
    score -= 0.5 * sum(1 for s in EASY if s in prompt)
    if score >= 3:   return "large"
    if score >= 0.5: return "medium"
    return "small"

def cost(tier, in_tok, out_tok):
    p_in, p_out = PRICES[tier]
    return in_tok / 1_000_000 * p_in + out_tok / 1_000_000 * p_out

random.seed(7)
samples = [
    (("이번 달 서울 매출 요약해줘", 300, 150, 0, 1), 40),
    (("이 문서 3줄로 요약", 1800, 200, 0, 1), 15),
    (("계약서 조항 중 위약금 부분 정리해줘", 2500, 600, 1, 2), 25),
    (("재고 3개 테이블 비교해서 발주 필요 수량 계산하고 근거를 설명해줘", 5200, 900, 4, 3), 10),
    (("RAG 아키텍처를 트레이드오프 근거와 함께 설계해줘", 900, 1200, 0, 4), 10),
]
# 실제 트래픽과 비슷하게 단순 질문이 많도록 가중 추출
requests = random.choices([s[0] for s in samples], weights=[s[1] for s in samples], k=1000)

routed_total, baseline_total, counts = 0.0, 0.0, {"small": 0, "medium": 0, "large": 0}
for prompt, tin, tout, tools, turn in requests:
    tier = route(prompt, tin, tools, turn)
    counts[tier] += 1
    routed_total += cost(tier, tin, tout)
    baseline_total += cost("large", tin, tout)

# 경량 모델 답변이 불안해 상위로 재시도하는 비율 12% 가정
ESCALATION, EXTRA = 0.12, cost("medium", 800, 400)
routed_total += counts["small"] * ESCALATION * EXTRA

print("📊 라우팅 분포:", counts)
print(f"전부 대형 모델: ${baseline_total:,.2f}")
print(f"라우팅 적용   : ${routed_total:,.2f}")
print(f"절감률        : {(1 - routed_total / baseline_total) * 100:.1f}%")
print(f"요청당 평균   : ${baseline_total/1000:.3f} → ${routed_total/1000:.3f}")
```

실행하면 라우팅 분포(단순 589 / 중형 208 / 대형 203)와 함께 이 예시 설정에서의 절감률이 약 **49%**로 나옵니다. 요청 구성(가중치)만 바꿔도 숫자가 달라지니, 실제 트래픽 로그로 다시 계산해 보세요.

**여기서 느껴야 하는 것**: 코드에서 바뀐 것은 단 한 줄, `route()`가 고른 티어뿐입니다. 모델을 바꾸는 일은 쉽고, **요청을 제대로 분류하는 정책을 만드는 일이 어렵습니다**. 그리고 재시도(escalation) 비용을 계산에 넣어야 실제 청구서와 맞습니다. 라우팅은 공짜 절감이 아니라 **오분류 위험을 사는 거래**입니다.

## ⚠️ 라우팅이 망하는 세 가지 방식

1. **정확도 검증 없이 켠다** — 골든셋 30문항으로 티어별 정확도를 비교하고, 저티어 정확도가 기준 미달이면 그 유형은 상위 티어로 고정합니다.
2. **라우팅 근거를 남기지 않는다** — "왜 이 요청이 경량으로 갔는가"를 로그에 남겨야 오분류를 고칠 수 있습니다(20일차 관측성).
3. **비용만 보고 캐시를 빼먹는다** — 같은 질문이 반복되는 서비스라면 라우팅보다 캐싱 효과가 큽니다(19일차).
