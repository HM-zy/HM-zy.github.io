고객사 화상회의에서 이런 질문이 나옵니다.

*"저희는 인터넷이 아예 안 뚫린 망인데, 이 AI 서비스는 어떻게 붙이죠?"*

이 한 문장에 **DNS, 포트, 방화벽, 프록시, Private Link**가 다 들어 있습니다. SA 면접에서도 똑같이 물어봅니다. "브라우저에 주소를 치면 무슨 일이 일어나나요?"는 네트워크 전부를 30초에 압축해 보라는 질문이고, "L4와 L7 차이가 뭐죠?"는 아키텍처 판단력을 보는 질문입니다.

이 글은 SA 실무에서 실제로 말하게 되는 순서대로 8개 묶음으로 정리했습니다.

1. **DNS · IP · MAC · 포트 · 방화벽** — 주소를 찾고, 문을 두드리고, 문지기를 통과하는 기본기 (+ 주소창에 URL을 쳤을 때의 6단계 전체 흐름)
2. **TCP 3-Way Handshake · Keep-Alive** — 연결을 맺고 유지하는 비용
3. **HTTP/HTTPS · TLS 핸드셰이크 · mTLS** — 내용을 감추고, 서로의 신분을 확인하는 법
4. **CORS** — 브라우저가 그리는 경계선
5. **L4 vs L7 로드밸런서 · 리버스 프록시 · API 게이트웨이** — 트래픽을 나누고 통제하는 지점
6. **REST vs gRPC vs WebSocket vs SSE** — REST API(자원 경로·메서드·JSON)와 LLM 스트리밍까지 포함한 통신 방식 선택
7. **VPC · 서브넷 · VPN · NAT 게이트웨이** — 클라우드에 우리만의 건물 짓기
8. **Private Link / Private Endpoint** — 인터넷을 열지 않고 외부 SaaS 붙이기

## 🧭 1. DNS · IP · MAC · 포트 · 방화벽: 주소 → 문패 → 문 → 문지기

**일상 비유**: **DNS는 내비게이션 검색**, **IP는 도로명 주소**, **포트는 건물의 호수**, **방화벽은 로비 경비원**입니다. "강남역 2번 출구"라고 검색하면(DNS) 실제 좌표(IP)가 나오고, 그 건물 몇 층 몇 호(포트)로 가야 하며, 경비원(방화벽)이 출입 명단에 없으면 로비에서 막힙니다.

### ① DNS: 이름을 숫자로 바꾸는 계층 구조

**핵심 원리**: 사람이 외우는 이름(`api.company.com`)을 컴퓨터가 쓰는 IP로 바꾸는 분산 데이터베이스입니다. 한 대가 다 아는 게 아니라 **위임(delegation)** 구조로 나뉘어 있습니다.

```text
브라우저 → OS 캐시 → 리졸버(통신사/사내 DNS)
   → 루트 네임서버 → .com TLD → company.com 권한 네임서버
   → "이 이름의 IP는 10.0.3.14" 회신 (TTL 동안 캐시)
```

| 레코드 | 역할 | 예시 |
| --- | --- | --- |
| A / AAAA | 이름 → IPv4 / IPv6 | `api` → `10.0.3.14` |
| CNAME | 이름 → 다른 이름(별칭) | `www` → `company.com` |
| MX / TXT | 메일 서버 / 도메인 소유 검증 | SPF, DKIM |
| NS | 이 도메인을 관리하는 네임서버 | Route 53, Cloudflare |

**핵심 감각**: DNS는 **TTL만큼 캐시**됩니다. 그래서 장애 조치(failover) 때 "DNS 바꿨는데 왜 아직 옛 서버로 가지?"가 생깁니다. TTL은 짧을수록 전환이 빠르고, 길수록 쿼리 비용과 지연이 줄어듭니다.

### ② IP와 CIDR: 주소를 블록으로 다루기

**핵심 원리**: IP는 네트워크의 주소이고, `/24` 같은 **CIDR** 표기는 "앞 24비트는 네트워크, 나머지 8비트는 호스트"라는 뜻입니다. `/24`는 256개, `/16`은 6만 5천 개 주소 블록입니다.

| 구분 | 대역 | 쓰는 곳 |
| --- | --- | --- |
| 사설 IP (A) | `10.0.0.0/8` | 사내망, 클라우드 VPC |
| 사설 IP (B) | `172.16.0.0/12` | Docker 기본 브리지 등 |
| 사설 IP (C) | `192.168.0.0/16` | 가정용 공유기 |
| 공인 IP | 그 외 | 인터넷에서 직접 라우팅되는 주소 |

사설 IP는 인터넷에서 직접 갈 수 없습니다. 밖으로 나갈 때 공인 IP로 바꿔 주는 장치가 **NAT**(7번 항목)입니다.

### ③ MAC 주소: IP는 집 주소, MAC은 문패

**일상 비유**: IP 주소가 **집 주소**라면 MAC 주소는 **그 집 현관의 문패**입니다. 집 주소는 이사 가면 바뀌지만, 문패는 그 사람(기기)을 따라다닙니다. 택배 기사(라우터)는 주소로 건물을 찾고, 건물 안에서는 문패로 정확한 사람을 찾습니다.

**핵심 원리**: MAC(Media Access Control) 주소는 **랜카드·와이파이 칩에 제조할 때 새겨지는 48비트 물리 주소**입니다. 16진수 12자리(`00:1A:2B:3C:4D:5E`)로 쓰고, **앞 6자리(24비트)가 제조사(OUI)**, 뒤 6자리가 그 제조사의 일련번호입니다. 같은 네트워크(브로드캐스트 도메인) 안에서만 의미가 있습니다.

| 구분 | IP 주소 | MAC 주소 |
| --- | --- | --- |
| 정체 | 논리 주소 (L3, 네트워크 계층) | 물리 주소 (L2, 데이터링크 계층) |
| 생김새 | `10.0.3.14`, `2001:db8::1` | `00:1A:2B:3C:4D:5E` (48비트) |
| 부여 | DHCP·수동 설정 — 바뀔 수 있음 | 제조 시 고정 (앞 6자리 = 제조사) |
| 도달 범위 | 라우터를 넘어 전 세계 어디로든 | **같은 망 안에서만** |
| 비유 | 집 주소 | 문패 |

**ARP: IP에서 MAC을 찾는 절차.** IP만 알아서는 실제 프레임을 보낼 수 없습니다. 같은 망에 "이 IP 누구세요?"를 **브로드캐스트**(ARP request)로 뿌리고, 해당 기기가 자기 MAC으로 응답(ARP reply)하면 그 결과를 ARP 캐시에 몇 분간 저장합니다. 목적지가 다른 망이면 내 PC는 **게이트웨이의 MAC**으로 보내고, 라우터가 다음 홉마다 이 과정을 반복합니다.

```text
[내 PC] --ARP: 10.0.3.14 누구세요?--> (브로드캐스트)
[서버]  <--ARP: 제 MAC은 00:1A:2B:3C:4D:5E--
→ ARP 캐시에 저장 → 그 MAC으로 이더넷 프레임 전송
```

**핵심 감각**: MAC은 **신분증이 아닙니다**. 소프트웨어로 바꿀 수 있어서(MAC spoofing) MAC 필터링은 보안 통제가 아니라 편의 기능입니다. 반대로 "같은 서브넷이면 라우터를 안 거친다"는 사실은 장애 진단에 그대로 쓰입니다 — 같은 서브넷끼리는 ARP로 직접 통신하므로 보안 그룹·NAT가 개입하지 않고, 서브넷이 다르면 라우팅 테이블과 방화벽이 개입합니다.

> **면접 한 줄**: "IP는 목적지를 찾는 논리 주소, MAC은 같은 망 안에서 기기를 찾는 물리 주소이고, 둘을 잇는 것이 ARP입니다. MAC은 위조가 가능하므로 '전달'에 쓰이고, 인증·인가는 IP·토큰·인증서로 합니다."

### ④ 포트: 한 IP 안의 여러 서비스 구분자

**핵심 원리**: IP가 건물 주소라면 포트는 **호수**입니다. 0~65535번이 있고, 1023번 이하는 잘 알려진(well-known) 포트입니다.

| 포트 | 서비스 | SA가 자주 만나는 상황 |
| --- | --- | --- |
| 80 / 443 | HTTP / HTTPS | ALB 인바운드, 80→443 리다이렉트 |
| 22 | SSH | 점프 서버에서만 열어야 함 |
| 5432 / 3306 | PostgreSQL / MySQL | 앱 서브넷에서만 접근 허용 |
| 6379 | Redis | 캐시 — 절대 인터넷 노출 금지 |
| 9092 | Kafka | 브로커 간 통신, AZ 내부 |

### ⑤ 방화벽: 상태를 기억하는가, 못 하는가

**핵심 원리**: 클라우드에서 가장 많이 헷갈리는 지점입니다. **보안 그룹(SG)은 상태 저장(stateful)** 방식이라 인바운드만 열면 응답은 자동으로 나갑니다. 반면 **네트워크 ACL(NACL)은 상태 비저장(stateless)** 이라 인바운드·아웃바운드를 **양쪽 다** 열어야 하고, 규칙은 **번호 순서대로** 평가되며 첫 매치에서 멈춥니다.

| 구분 | 보안 그룹 (SG) | 네트워크 ACL |
| --- | --- | --- |
| 적용 단위 | 인스턴스 / ENI | 서브넷 |
| 상태 기억 | 있음 (응답 자동 허용) | 없음 (양방향 명시) |
| 규칙 종류 | 허용만 | 허용 + 거부 |
| 쓰는 자리 | 세밀한 서비스 간 통제 | 서브넷 단위 차단선(백업) |

### 🗺️ 한눈에: 주소창에 URL을 치면 생기는 일 (6단계)

면접 단골 질문입니다. 위의 ①~⑤와 뒤의 2·3번 항목을 한 장으로 붙이면 이렇게 됩니다. "그다음엔?" "TLS는 언제 붙나?" "DNS는 몇 번 일어나나?" 같은 꼬리질문은 이 사다리만 있으면 막히지 않습니다.

| # | 단계 | 실제로 하는 일 | 실패하면 보이는 화면 |
| --- | --- | --- | --- |
| 1 | 주소창 입력 · 엔터 | URL을 스킴·호스트·경로로 분해, 캐시·HSTS 확인 (http면 https로 승격) | 오타 시 검색 결과, `ERR_INVALID_URL` |
| 2 | DNS 조회 | 호스트 → IP (OS 캐시 → 리졸버 → 루트 → TLD → 권한 NS) | `DNS_PROBE_FINISHED_NXDOMAIN` |
| 3 | TCP 3-Way Handshake | 443 포트로 SYN → SYN-ACK → ACK | `ERR_CONNECTION_TIMED_OUT`(방화벽·라우팅), `ERR_CONNECTION_REFUSED` |
| 4 | TLS 핸드셰이크 | 인증서 검증 + ECDHE로 세션 키 합의 (TLS 1.3 = 1-RTT) | `ERR_CERT_DATE_INVALID`, 사내 프록시 SSL 검사 |
| 5 | HTTP 요청 · 응답 | `GET /` + Host·Cookie·Authorization → 상태 코드 + 헤더 + 본문 | 401/403/404/500, 502·504, CORS 에러 |
| 6 | 브라우저 렌더링 | HTML 파싱 → CSS·JS·이미지 추가 요청 → 레이아웃·페인트 | 흰 화면, 깨진 레이아웃 |

**핵심 감각**: 2~4단계는 **한 번만** 하고, 페이지에 딸린 리소스 수십 개는 **같은 연결을 재사용**해서 가져옵니다(keep-alive, HTTP/2 다중화). 그래서 "첫 화면이 느리다"와 "버튼을 눌렀는데 반응이 느리다"는 원인이 다릅니다 — 전자는 DNS·TCP·TLS, 후자는 서버 처리·쿼리·LLM 지연입니다. 두 번째 방문부터는 DNS 캐시와 TLS 세션 재개로 2~4단계가 거의 사라집니다.

> **비유로 마무리**: **2번은 전화번호부에서 번호 찾기**, **3번은 전화 걸어 "여보세요"까지**, **4번은 우리끼리만 쓸 암호 정하기**, **5번은 용건 말하기**, **6번은 들은 내용을 공책에 정리해 보여주기**입니다.

**한 단계 더**: HTTP/3는 TCP 대신 QUIC(UDP) 위에서 TLS를 함께 처리해 첫 연결부터 1-RTT, 재방문은 0-RTT로 시작합니다. 사내망에서 "우리 프록시는 HTTP/3를 못 씁니다"가 나오면 HTTP/2로 내려가는 협상이 필요합니다.

### 🎤 면접 30초 답변 (주소를 입력하면 무슨 일이?)

> "브라우저가 `api.company.com`을 입력받으면 먼저 DNS로 IP를 조회합니다. OS 캐시에 없으면 리졸버를 거쳐 루트 → TLD → 권한 네임서버 순으로 위임을 따라가 A 레코드를 받습니다. IP를 얻으면 443번 포트로 **TCP 3-way handshake**를 맺고, 그 위에서 **TLS 핸드셰이크**로 서버 인증서를 검증하고 세션 키를 만든 뒤에야 HTTP 요청을 보냅니다. 이때 각 단계마다 방화벽이 출발지·목적지·포트를 검사하고, 클라우드 보안 그룹은 상태 저장이라 응답 트래픽은 자동으로 허용됩니다."

### 🎯 SA 실무 포인트

**1) DB 보안 그룹은 "IP 대역"이 아니라 "다른 보안 그룹"으로 참조하세요.**
`10.0.3.0/24`처럼 대역으로 열면 그 서브넷의 모든 것이 들어옵니다. `sg-app`을 소스로 지정하면 앱 서버 교체·오토스케일링에도 규칙을 고칠 필요가 없고, "DB는 앱에서만"이 문서가 아니라 설정으로 증명됩니다.

**2) 폐쇄망에서는 DNS가 설계 산출물입니다.**
인터넷 DNS를 못 쓰는 망에서는 사내 DNS에 어떤 존을 두고, 임시 검증용 도메인을 어디까지 열어 줄지가 협의 항목입니다. 클라우드에서는 **프라이빗 호스팅 존**(Route 53 private zone)으로 공인 DNS에 이름을 노출하지 않고 내부 이름을 해석합니다.

**3) TTL은 가용성 SLA와 직결됩니다.**
장애 조치 시나리오에서 "DNS 전환 3분 내"라고 약속하려면 TTL을 60초 이하로 두고, 실제로 그 값을 검증해야 합니다. 반대로 TTL이 길면 전환은 느리지만 DNS 쿼리 비용·지연은 줄어듭니다.

## 🔌 2. TCP 3-Way Handshake · Keep-Alive: 연결을 맺고 유지하는 비용

**일상 비유**: 전화를 걸 때 바로 말하지 않습니다. **"여보세요?"(SYN) → "네, 들려요"(SYN-ACK) → "네, 알겠습니다"(ACK)** 로 통화로를 확인한 뒤에야 본론을 말합니다. 그리고 통화를 끊지 않고 계속 이야기하는 것이 **Keep-Alive**입니다. 매번 끊고 다시 걸면 인사에만 시간이 다 갑니다.

**핵심 원리**: TCP는 연결 지향이라 데이터를 보내기 전에 양쪽의 순서 번호(sequence number)를 합의합니다.

| 단계 | 방향 | 의미 |
| --- | --- | --- |
| SYN | 클라이언트 → 서버 | "내 시작 번호는 x, 연결하자" |
| SYN-ACK | 서버 → 클라이언트 | "x+1 확인, 내 시작 번호는 y" |
| ACK | 클라이언트 → 서버 | "y+1 확인" — 이후 데이터 전송 |
| FIN / ACK ×2 | 양방향 | 종료는 4단계(각 방향을 따로 닫음) |

**핵심 감각**: handshake는 **왕복 1회(RTT 1회)** 를 씁니다. 여기에 TLS 1.2 핸드셰이크 2-RTT가 더해지면 첫 요청 전에 이미 3-RTT가 지나갑니다. 그래서 **연결을 재사용하는 것(keep-alive)** 이 성능 설계의 기본입니다.

- HTTP/1.1: `Connection: keep-alive`로 연결을 재사용하지만, 한 번에 한 요청(파이프라이닝은 사실상 사장).
- HTTP/2: **하나의 TCP 연결에 여러 스트림을 다중화(multiplexing)** — keep-alive의 진화형.
- TCP keep-alive: 유휴 연결이 방화벽·NAT의 세션 테이블에서 지워지지 않도록 주기적 탐침을 보냅니다.

### 🎤 면접 30초 답변

> "TCP는 데이터를 보내기 전에 3-way handshake로 양쪽 순서 번호를 합의합니다. 클라이언트가 SYN을 보내고, 서버가 SYN-ACK로 응답하고, 클라이언트가 ACK를 보내면 연결이 성립합니다. 이 과정이 왕복 한 번을 쓰기 때문에 연결을 매번 새로 맺으면 지연이 누적됩니다. 그래서 HTTP는 keep-alive로 연결을 재사용하고, HTTP/2는 한 연결에 여러 스트림을 다중화합니다. 다만 로드밸런서의 유휴 타임아웃이 애플리케이션의 keep-alive 주기보다 짧으면, 이미 닫힌 연결로 요청을 보내 502나 504가 간헐적으로 발생합니다."

### 🎯 SA 실무 포인트

**1) 간헐적 502/504의 절반은 타임아웃 불일치입니다.**
ALB의 유휴 타임아웃(기본 60초)이 앱이나 클라이언트의 keep-alive보다 짧으면, LB가 조용히 닫은 연결을 클라이언트가 재사용하다 실패합니다. **"LB 타임아웃 > 앱 keep-alive > 클라이언트 keep-alive"** 순서로 설계하는 것이 정석입니다.

| 증상 | 흔한 원인 | 조치 |
| --- | --- | --- |
| 60초마다 딱 한 번씩 502 | ALB 유휴 타임아웃이 앱 keep-alive보다 짧음 | 앱 keep-alive를 60초 미만(예: 50초)으로 |
| 긴 LLM 응답이 504 | 응답이 LB 타임아웃 초과 | 스트리밍(SSE)으로 전환, 타임아웃 상향 |
| NAT 경유 연결이 끊김 | NAT 게이트웨이 유휴 만료(약 350초) | 앱 레벨 keep-alive 주기 조정 |

**2) 프라이빗 서브넷에서 나가는 트래픽은 NAT를 거칩니다.**
외부 LLM API를 호출하는 앱이 프라이빗 서브넷에 있으면 NAT 게이트웨이를 통과합니다. 여기서 **처리량·시간당 요금**이 붙고, AZ 하나에 NAT를 두면 그 AZ 장애 시 통신이 끊깁니다. "인터넷이 필요한가?"를 먼저 묻고, 필요 없다면 8번 항목(Private Link)으로 대체합니다.

## 🔒 3. HTTP/HTTPS · TLS 핸드셰이크 · mTLS

**일상 비유**: HTTP는 **엽서**입니다. 경로의 모든 우체국이 내용을 읽을 수 있습니다. HTTPS는 **봉인 봉투**이고, mTLS는 봉투에 **보내는 사람과 받는 사람의 신분증을 둘 다 넣는** 방식입니다.

**핵심 원리**: HTTPS는 HTTP를 TLS 위에 올린 것입니다. TLS는 세 가지를 보장합니다 — **기밀성**(암호화), **무결성**(변조 감지), **상대 인증**(인증서).

| 단계 | TLS 1.2 | TLS 1.3 |
| --- | --- | --- |
| 핸드셰이크 왕복 | 2-RTT (재개 시 1-RTT) | **1-RTT** (재개 시 0-RTT) |
| 키 교환 | RSA 또는 ECDHE | ECDHE만 (전방 비밀성 필수) |
| 암호 스위트 | 협상 항목 많음 | 단순화·안전한 것만 |
| 상태 | 여전히 지원 | 권장 기본값 |

핸드셰이크의 실제 순서는 이렇습니다.

1. **ClientHello** — 지원 암호 목록, **SNI**(어느 도메인인지), ALPN(h2/http1.1)
2. **ServerHello + 인증서** — 서버가 인증서 체인을 보냄
3. **검증** — 클라이언트가 체인을 루트 CA까지 확인하고 도메인 일치·유효기간을 검사
4. **키 교환(ECDHE)** — 세션마다 새 대칭키 생성 (키 자체는 전송되지 않음)
5. **Finished** — 이후 애플리케이션 데이터를 대칭키로 암호화

> **비대칭키는 문을 여는 데, 대칭키는 짐을 나르는 데 씁니다.** 인증서 검증과 키 교환은 느린 비대칭 연산으로, 실제 데이터는 빠른 대칭키(AES-GCM, ChaCha20)로 처리합니다.

### 단방향 TLS vs mTLS

| 구분 | 단방향 TLS | mTLS |
| --- | --- | --- |
| 서버가 클라이언트를 확인 | 안 함 (비밀번호·토큰으로 별도 인증) | **인증서로 확인** |
| 클라이언트가 서버를 확인 | 인증서로 확인 | 인증서로 확인 |
| 대표 용도 | 일반 웹/API | 서비스 간 통신, 제로 트러스트, B2B 연동 |
| 운영 부담 | 인증서 갱신 1개 | 양쪽 인증서 발급·회수·만료 관리 |

### 🎤 면접 30초 답변

> "HTTPS는 HTTP를 TLS로 감싼 것이고, TLS는 기밀성·무결성·상대 인증을 제공합니다. 핸드셰이크는 ClientHello로 암호 방식과 SNI를 알리고, 서버가 인증서 체인을 보내면 클라이언트가 루트 CA까지 검증한 뒤 ECDHE로 세션 키를 합의합니다. TLS 1.2는 2-RTT, TLS 1.3은 1-RTT로 줄었고 ECDHE만 허용해 전방 비밀성을 보장합니다. mTLS는 여기에 클라이언트 인증서 검증을 더한 것으로, 서비스 간 통신에서 '네트워크 안에 있으니 믿는다'를 버리고 **양쪽 신원을 매 연결마다 증명**하는 제로 트러스트의 기반이 됩니다."

### 🎯 SA 실무 포인트

**1) TLS를 어디서 끊을지가 설계 결정입니다.**
ALB에서 종료하면 뒤쪽 구간은 평문이라 WAF·L7 라우팅이 쉬운 대신, 내부 구간 암호화가 필요하면 별도 정책이 필요합니다. 반대로 L4(NLB)에서 **TLS passthrough**하면 종단 간 암호화는 유지되지만 내용 기반 라우팅·WAF를 못 씁니다. 금융·공공 고객은 "구간별 암호화"를 요구하니 이 지점을 그림으로 보여줘야 합니다.

**2) 인증서 만료는 100% 사람 실수로 터집니다.**
ACM, cert-manager 같은 자동 갱신을 기본으로 두고, 만료 30일 전 알림을 모니터링에 넣습니다. 사내 프록시가 TLS를 가로채는(SSL inspection) 환경에서는 **사내 루트 CA를 신뢰 저장소에 넣지 않으면** SDK가 인증서 검증 실패로 죽습니다 — 사내 LLM 연동 PoV에서 가장 자주 밟는 지뢰입니다.

**3) 최소 버전 정책을 문서에 박으세요.**
TLS 1.0/1.1 비활성, 취약 암호 스위트 차단, HSTS 적용. "보안 요구사항 충족"이라는 문장보다 **"TLS 1.2 이상만 허용, 스캔 결과 A등급"** 처럼 검증 가능한 형태로 적는 것이 고객 보안팀과 이야기할 때 훨씬 빠릅니다.

## 🌐 4. CORS: 브라우저가 그리는 경계선

**일상 비유**: 아파트 단지에 **외부인 출입 허가 명단**이 있습니다. 경비원(브라우저)은 다른 단지 사람이 우리 단지 시설을 쓰려 하면 명단을 확인하고, 명단에 없으면 들여보내지 않습니다. 중요한 건 **경비원이 우리 단지 소속**이라는 점입니다 — 서버가 아니라 브라우저가 막습니다.

**핵심 원리**: 브라우저는 **동일 출처 정책(Same-Origin Policy)** 을 지킵니다. 출처(origin)는 **프로토콜 + 호스트 + 포트** 세 가지가 모두 같아야 같습니다. `https://app.company.com`에서 `https://api.company.com`을 호출하면 포트·호스트가 달라 **다른 출처**입니다.

이때 서버가 응답 헤더로 "이 출처는 허용"이라고 알려 주는 것이 CORS입니다.

| 상황 | 브라우저 동작 |
| --- | --- |
| 단순 요청 (GET, 단순 헤더) | 바로 보내고, 응답 헤더를 보고 **결과를 노출할지 결정** |
| 프리플라이트 필요 (PUT, 커스텀 헤더, JSON) | 먼저 `OPTIONS`로 허용 여부를 물어봄 |
| 허용 안 됨 | 서버는 200을 줬어도 브라우저가 **응답을 버리고 콘솔 에러** |

주요 헤더는 네 개만 기억하면 됩니다.

- `Access-Control-Allow-Origin` — 허용 출처 (또는 `*`)
- `Access-Control-Allow-Methods` / `-Headers` — 허용 메서드·헤더
- `Access-Control-Allow-Credentials` — 쿠키·인증 헤더 포함 허용
- `Access-Control-Max-Age` — 프리플라이트 결과 캐시 시간

**핵심 함정**: `Allow-Origin: *`와 `Allow-Credentials: true`는 **함께 쓸 수 없습니다**. 쿠키 기반 세션을 쓰는 사내 앱에서 이 조합을 시도하면 계속 실패합니다.

### 🎤 면접 30초 답변

> "CORS는 브라우저의 동일 출처 정책을 서버가 선택적으로 완화하는 장치입니다. 출처는 프로토콜·호스트·포트의 조합이라, 프론트와 API 도메인이 다르면 다른 출처가 됩니다. PUT이나 JSON 요청처럼 프리플라이트가 필요한 경우 브라우저가 먼저 OPTIONS로 허용 여부를 확인하고, 서버가 Allow-Origin 같은 헤더로 응답해야 실제 요청 결과가 노출됩니다. 중요한 건 **CORS가 서버 보안 통제가 아니라는 점**입니다. 브라우저가 강제하는 것이라 curl이나 서버 간 호출에는 아무 영향이 없고, 실제 접근 통제는 인증·인가로 해야 합니다."

### 🎯 SA 실무 포인트

**1) "CORS 에러"를 서버 장애로 오진하지 마세요.**
브라우저 콘솔의 CORS 에러는 대개 **서버가 정상 응답한 뒤** 브라우저가 버린 것입니다. 서버 로그에는 200이 찍힙니다. 이걸 모르면 장애 대응에서 엉뚱한 곳을 봅니다.

**2) 사내 LLM 게이트웨이는 프론트 도메인이 여러 개입니다.**
업무 포털, 사내 앱, 신규 PoV 화면이 각각 다른 도메인이면 허용 출처를 목록으로 관리해야 합니다. 여기에 인증 헤더를 쓰면 와일드카드가 막히므로 **허용 출처 명시 + credentials 허용** 조합이 필요합니다. API 게이트웨이에서 공통 처리하는 것이 정석입니다.

**3) 스트리밍(SSE) 응답에서 CORS 헤더가 빠지면 조용히 실패합니다.**
프리플라이트는 통과했는데 스트림이 안 흐르면, 스트리밍 응답에도 동일한 CORS 헤더가 붙었는지, 중간 프록시가 버퍼링하지 않는지 확인합니다.

## ⚖️ 5. L4 vs L7 로드밸런서 · 리버스 프록시 · API 게이트웨이

**일상 비유**: **L4는 택배 분류장**입니다. 겉봉의 주소만 보고 어느 지역으로 보낼지 정합니다 — 빠르고 내용은 모릅니다. **L7은 우체국 창구 직원**입니다. 내용물과 서류를 읽고 "이건 계약서니까 법무팀, 이건 청구서니까 회계팀"처럼 **내용에 따라** 보냅니다.

**핵심 원리**: L4는 IP·포트·프로토콜만 보고 TCP/UDP 연결을 분배합니다. L7은 HTTP를 해석해 **경로·호스트·헤더·쿠키**로 라우팅하고 TLS 종료·WAF·압축·캐시까지 합니다.

| 구분 | 보는 정보 | 대표 기능 | 제품 예 |
| --- | --- | --- | --- |
| L4 | IP·포트·TCP/UDP | 고속 분배, TLS passthrough | AWS NLB, LVS |
| L7 | HTTP 경로·호스트·헤더 | TLS 종료, 경로 라우팅, WAF | AWS ALB, NGINX, Envoy |
| API 게이트웨이 | API 키·토큰·쿼터 | 인증, 사용량 제한, 키 발급, 로깅 | Kong, Apigee, AWS API GW |

**리버스 프록시**는 L7 계층의 대표 구현입니다. 클라이언트는 프록시만 보고, 실제 서버는 뒤에 숨습니다. NGINX가 정적 파일을 서빙하면서 API 요청만 뒤로 넘기는 구성이 전형입니다.

**API 게이트웨이 vs 로드밸런서**: 둘 다 앞단에 있지만 목적이 다릅니다. 로드밸런서는 **"어디로 보낼까"**, 게이트웨이는 **"누가 얼마나 쓸 수 있나"** 입니다. 멀티테넌트 LLM 서비스라면 테넌트별 API 키·토큰 쿼터·모델 라우팅이 필요하므로 게이트웨이가 필수입니다.

### 🎤 면접 30초 답변

> "L4 로드밸런서는 IP와 포트, TCP 수준 정보만 보고 연결을 분배하기 때문에 빠르고 TLS를 그대로 통과시킬 수 있습니다. L7 로드밸런서는 HTTP를 해석해서 경로나 호스트 헤더로 라우팅하고, TLS 종료·WAF·압축 같은 기능을 제공합니다. 리버스 프록시는 L7에서 서버를 뒤에 숨기고 앞단에서 요청을 중계하는 구조이고, API 게이트웨이는 여기에 인증·쿼터·키 관리 같은 정책을 얹은 것입니다. 그래서 gRPC처럼 HTTP/2를 이해해야 하는 트래픽은 L7이 필요하고, 종단 간 암호화가 규제 요건이면 L4 passthrough를 선택합니다."

### 🎯 SA 실무 포인트

**1) gRPC는 L7을 골라야 합니다.**
HTTP/2를 이해하지 못하는 L4는 h2 프레임을 그냥 흘려보낼 수는 있어도 경로 라우팅·헬스체크가 안 됩니다. 내부 마이크로서비스 통신을 gRPC로 설계했다면 ALB(HTTP/2)나 Envoy 기반 메시를 전제로 해야 합니다.

**2) "비용 때문에 L4"를 습관적으로 고르지 마세요.**
NLB가 시간당 저렴해 보여도, WAF·경로 라우팅·인증을 애플리케이션에 직접 구현하면 유지비가 더 큽니다. 반대로 초당 수십만 연결의 순수 TCP 트래픽이면 L7은 병목이 됩니다.

**3) 게이트웨이에서 남기는 로그가 곧 FinOps 근거입니다.**
테넌트별 요청 수·토큰 사용량·지연을 게이트웨이에서 기록하면, 나중에 "이 부서가 AI 비용의 60%를 쓴다"를 증명할 수 있습니다. 나중에 붙이려면 소급이 안 되니 처음부터 설계에 넣습니다.

## 🔄 6. REST vs gRPC vs WebSocket vs SSE: LLM 스트리밍의 정답

**일상 비유**: 네 가지 통신 방식은 네 가지 대화법입니다.

- **REST** = 우편 주문서. 한 번 보내고 한 번 받습니다. 누가 언제 보냈는지 서로 기억하지 않아도 됩니다.
- **gRPC** = 사내 전용 규격 문서. 양식이 엄격하고(protobuf) 빠릅니다.
- **WebSocket** = 전화 통화. 양쪽이 동시에 말할 수 있고, 끊을 때까지 연결이 유지됩니다.
- **SSE** = 라디오 방송. 청취자는 듣기만 하고, 방송은 계속 흘러나옵니다.

| 방식 | 방향 | 전송·포맷 | 쓰는 자리 |
| --- | --- | --- | --- |
| REST | 요청-응답 | HTTP + JSON | 공개 API, CRUD, 대부분의 연동 |
| gRPC | 요청-응답 + 스트리밍 | HTTP/2 + protobuf | 내부 서비스 간, 고성능·강타입 |
| WebSocket | 양방향 | TCP 위 프레임 | 채팅, 실시간 협업, 음성 대화 |
| SSE | 서버 → 클라이언트 단방향 | HTTP `text/event-stream` | **LLM 토큰 스트리밍**, 알림, 진행률 |

### 🧾 REST API 한 장 정리: 자원 경로 + 메서드 + JSON

**일상 비유**: REST는 **식당 메뉴판**입니다. 메뉴 이름은 명사(`/cats`, "고양이")로 두고, "가져오기·만들기·고치기·지우기"는 **동작 방식(메서드)** 으로 구분합니다. `/getCat?id=5`처럼 주소에 동사를 넣는 것은 "고양이 가져오기 버튼"을 동작마다 하나씩 만드는 셈이라, 메뉴판이 금방 지저분해집니다.

| 요소 | 뜻 | 예 |
| --- | --- | --- |
| 자원 경로 | 다루는 대상 (명사, 보통 복수형) | `/cats`, `/cats/5`, `/cats/5/owners` |
| HTTP 메서드 | 무엇을 할지 | `GET`(조회) `POST`(생성) `PUT`(전체 교체) `PATCH`(부분 수정) `DELETE`(삭제) |
| 데이터 형식 | 내용물의 모양 | JSON `{"id": 5, "name": "나비"}` |
| 상태 코드 | 결과 | 200 OK, 201 Created, 204 No Content, 400·401·403·404·409·429, 500·503 |

```text
GET    /cats        → 목록 조회      200
GET    /cats/5      → 5번 한 마리    200 / 404
POST   /cats        → 새로 등록      201 + Location 헤더
PUT    /cats/5      → 전체 교체      200
PATCH  /cats/5      → 이름만 수정    200
DELETE /cats/5      → 삭제           204
```

**핵심 감각 — 멱등성(idempotent)**: `GET`·`PUT`·`DELETE`는 같은 요청을 여러 번 보내도 결과가 같지만, `POST`는 보낼 때마다 새로 생깁니다. 그래서 **주문·결제·LLM 과금이 걸린 POST에는 재시도 방지 장치(idempotency key)** 가 필요합니다. 스트리밍 응답이 중간에 끊겨 클라이언트가 자동 재시도하면 **같은 질문에 요금이 두 번** 나가는 사고가 실제로 납니다.

**JSON의 감각**: `{키: 값}` 트리에 문자열·숫자·불리언·null·배열·객체만 담는 텍스트 형식입니다. 주석이 없고 64비트 정수·날짜·바이너리 타입이 없어서, **ID는 문자열로**, **날짜는 ISO 8601 문자열**로 주고받는 관행이 생겼습니다. 응답이 커지면 페이지네이션(`?limit=20&cursor=...`)과 필드 선택(`?fields=id,name`)을 붙입니다.

**오류 응답의 기본형**: 상태 코드만 주면 클라이언트는 추측해야 합니다. 기계가 읽는 코드 + 사람이 읽는 메시지 + 추적 ID를 함께 줍니다.

```json
{ "error": { "code": "RATE_LIMITED", "message": "분당 60회를 초과했습니다.", "trace_id": "7f3c1a" } }
```

**SSE의 핵심 원리**: 그냥 HTTP 응답을 **끝내지 않고 조금씩 흘려보내는** 것입니다. `Content-Type: text/event-stream`으로 응답하고 `data: {...}` 블록을 하나씩 밀어냅니다. 브라우저 `EventSource`는 끊기면 자동 재연결하며, 마지막 이벤트 ID를 보내 이어받을 수 있습니다.

```text
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"delta":"안녕"}

data: {"delta":"하세요"}

data: [DONE]
```

**왜 LLM 스트리밍은 WebSocket이 아니라 SSE인가?** LLM 응답은 **서버 → 클라이언트 한 방향**입니다. 사용자가 생성 중에 끼어들어 토큰을 보낼 일이 없습니다. WebSocket은 양방향·상태 유지 연결이라 서버가 연결 수만큼 자원을 잡고, 프록시·로드밸런서의 스티키 세션·타임아웃 설정까지 신경 써야 합니다. SSE는 평범한 HTTP라 기존 인프라가 거의 그대로 동작합니다.

### 🎤 면접 30초 답변

> "REST는 무상태 요청-응답으로 범용성이 가장 좋고, gRPC는 HTTP/2와 protobuf로 스키마가 강제되고 다중화·스트리밍이 되어 내부 서비스 간 호출에 유리합니다. WebSocket은 양방향 실시간 통신이 필요할 때, 예를 들어 음성 대화나 협업 편집에 씁니다. LLM 토큰 스트리밍은 서버에서 클라이언트로만 흐르면 되기 때문에 SSE를 씁니다. 평범한 HTTP 응답을 text/event-stream으로 열어 두고 조금씩 흘려보내는 방식이라, 프록시·로드밸런서·인증 체계를 그대로 재사용할 수 있고 연결 상태를 서버가 오래 들고 있지 않아도 됩니다. 다만 중간 프록시가 버퍼링하면 스트리밍이 사라지므로 버퍼링을 끄고 타임아웃을 늘리는 설정이 필요합니다."

### 🎯 SA 실무 포인트

**1) 스트리밍이 안 보이면 90%는 버퍼링입니다.**
NGINX는 `proxy_buffering off;`와 `X-Accel-Buffering: no`, CloudFront/ALB는 압축·버퍼링 설정, 사내 프록시는 응답 버퍼링 해제가 필요합니다. "체감 속도가 느리다"는 CS 문의의 실제 원인이 여기인 경우가 많습니다.

**2) 타임아웃은 "첫 토큰"과 "전체 응답"을 나눠 잡으세요.**
LLM은 첫 토큰까지 수 초, 전체는 수십 초가 걸립니다. 단일 타임아웃으로 잡으면 긴 답변이 잘립니다. 첫 토큰 지연(TTFT)은 별도 지표로 모니터링합니다.

**3) WebSocket을 고르는 순간 운영 비용이 올라갑니다.**
연결 유지, 스티키 라우팅, 배포 시 연결 드레이닝, 연결 수 기반 오토스케일링이 따라옵니다. "실시간 음성"처럼 정말 양방향이 필요할 때만 선택하고, 문서에 그 이유를 남깁니다.

**4) LLM 서비스는 "REST로 열고, 스트리밍만 SSE로" 분기합니다.**
동기 응답(`POST /v1/chat`), 스트리밍(`POST /v1/chat` + `Accept: text/event-stream`), 비동기 대용량(`POST /v1/jobs` → `GET /v1/jobs/{id}` 폴링)을 한 API 세트로 설계하면, 고객사 프록시·게이트웨이가 스트리밍을 막아도 서비스가 멈추지 않습니다. 여기에 **`Idempotency-Key` 요청 헤더**와 **`Retry-After` 응답 헤더**를 넣어 두면 재시도·과금 사고를 설계 단계에서 줄입니다.

## 🏢 7. VPC · 서브넷 · VPN · NAT 게이트웨이: 클라우드에 우리 건물 짓기

**일상 비유**: **VPC는 우리 회사만 쓰는 건물**입니다. **서브넷은 층**이고, **퍼블릭 서브넷은 1층 로비**(외부인 출입 가능), **프라이빗 서브넷은 사무실 층**(직원만). **인터넷 게이트웨이는 정문**, **NAT 게이트웨이는 직원이 밖으로 나가기만 하는 회전문**(밖에서 들어올 수는 없음), **VPN은 본사와 연결된 지하 터널**입니다.

**핵심 원리**: VPC는 CIDR 블록으로 정의된 논리적 격리 네트워크입니다. 서브넷은 가용영역(AZ)에 묶이고, 라우팅 테이블이 트래픽의 방향을 정합니다.

| 구성요소 | 역할 | 주의점 |
| --- | --- | --- |
| 서브넷 | AZ 안의 IP 대역 분할 | AZ별로 나눠야 장애 격리 |
| 라우팅 테이블 | 목적지별 다음 홉 | 퍼블릭/프라이빗의 실제 차이 |
| 인터넷 게이트웨이 | 공인 트래픽 출입 | 퍼블릭 서브넷에만 연결 |
| NAT 게이트웨이 | 사설 → 인터넷 단방향 | 시간당·GB 과금, AZ 종속 |
| VPN / 전용선 | 온프레미스 연결 | IPsec VPN vs Direct Connect |

**CIDR 설계 감각**: VPC를 `/16`(6만 5천 개)으로 잡고 AZ별 `/24` 서브넷을 두는 구성이 흔합니다. AWS는 서브넷마다 IP 5개를 예약하므로 `/24`의 실제 사용 가능 주소는 251개입니다. **온프레미스와 겹치지 않는 대역**을 고르는 것이 첫 단계입니다 — 겹치면 나중에 VPN을 못 뚫습니다.

### 🎤 면접 30초 답변

> "VPC는 클라우드 안에 만드는 논리적 사설 네트워크이고, 서브넷으로 가용영역별 IP 대역을 나눕니다. 퍼블릭 서브넷은 인터넷 게이트웨이로 라우팅되어 공인 IP를 가진 리소스가 외부와 통신하고, 프라이빗 서브넷은 외부에서 직접 접근할 수 없습니다. 프라이빗 서브넷에서 패키지 설치나 외부 API 호출이 필요하면 NAT 게이트웨이를 통해 나가는데, 이건 사설 IP를 공인 IP로 변환하고 들어오는 연결은 허용하지 않습니다. 온프레미스와 연결할 때는 VPN이나 전용선을 쓰고, CIDR이 겹치지 않도록 주소 계획을 먼저 세우는 것이 중요합니다."

### 🎯 SA 실무 포인트

**1) NAT 게이트웨이는 조용한 비용·가용성 함정입니다.**
시간당 요금 + 처리 GB 요금이 붙고, AZ 하나에만 두면 그 AZ가 죽을 때 해당 서브넷의 외부 통신이 끊깁니다. AZ별 NAT를 두고 비용을 감수할지, 외부 호출 자체를 줄일지(Private Link·프록시 집중) 판단해야 합니다.

**2) IP 고갈은 컨테이너 환경에서 먼저 옵니다.**
EKS는 파드마다 VPC IP를 잡는 모드가 있어 `/24` 서브넷이 금방 바닥납니다. 노드·파드 수를 예상해 서브넷 크기를 잡고, 필요하면 보조 CIDR을 붙입니다.

**3) VPC Peering은 전이되지 않습니다.**
A-B, B-C가 피어링돼 있어도 A-C는 통신 불가입니다. 연결할 VPC가 3개를 넘으면 **Transit Gateway** 같은 허브 구조를 검토합니다. 이걸 모르면 "망은 다 연결했는데 왜 안 되죠"로 반나절을 씁니다.

## 🔗 8. Private Link / Private Endpoint: 인터넷을 열지 않고 SaaS 붙이기

**일상 비유**: 담장 밖 상점에 물건을 사러 가야 하는데 정문을 열 수 없습니다. 대신 **우리 건물 지하와 그 상점을 잇는 전용 통로**를 뚫습니다. 통로는 우리 쪽에서만 열 수 있고, 상점은 우리 내부 IP를 알 필요도 없습니다.

**핵심 원리**: 서비스 제공자(VPC)가 자기 서비스를 **엔드포인트 서비스**로 노출하면, 소비자 VPC에 **프라이빗 IP를 가진 네트워크 인터페이스(ENI)** 가 생깁니다. 이 ENI로 가는 트래픽은 AWS 백본 안에서만 이동하고, 인터넷 게이트웨이·NAT를 거치지 않습니다.

| 항목 | VPC Peering | Private Link |
| --- | --- | --- |
| 연결 범위 | VPC 전체 | **특정 서비스 하나** |
| CIDR 겹침 | 불가 | 가능 |
| 방향 | 양방향 | 소비자 → 제공자 단방향 |
| 계정 경계 | 신뢰 필요 | 교차 계정 SaaS에 적합 |

**핵심 감각**: Private Link의 진짜 장점은 **노출 면적**입니다. 피어링은 상대 VPC 전체를 신뢰해야 하지만, Private Link는 "이 서비스 포트 하나"만 연결합니다. 그래서 규제 산업에서 외부 SaaS를 붙일 때 표준 해법이 됩니다.

### 🎤 면접 30초 답변

> "인터넷이 막힌 환경에서 외부 SaaS를 붙이려면 Private Link를 씁니다. 제공자가 엔드포인트 서비스로 노출한 서비스에 대해 소비자 VPC에 프라이빗 IP를 가진 인터페이스 엔드포인트가 생기고, 트래픽은 공용 인터넷을 거치지 않고 클라우드 백본 안에서만 흐릅니다. VPC 피어링과 달리 VPC 전체가 아니라 특정 서비스만 연결되고, CIDR이 겹쳐도 되며, 방향이 소비자에서 제공자로 단방향이라 노출 면적이 최소화됩니다. 사설 DNS로 서비스 이름을 해석하도록 프라이빗 호스팅 존을 연결하는 설정이 함께 필요합니다."

### 🎯 SA 실무 포인트

**1) 폐쇄망 LLM 연동의 정답지입니다.**
Azure OpenAI는 Private Endpoint, AWS Bedrock은 PrivateLink(interface endpoint)로 인터넷 없이 호출합니다. 금융·공공 고객 제안서에서 "외부 API를 호출합니다"는 반려 사유이고, **"프라이빗 엔드포인트로만 나갑니다"** 가 통과 조건입니다. 이때 필요한 것은 ① 엔드포인트 ② 프라이빗 DNS ③ 보안 그룹 443 허용 ④ 심사용 아웃바운드 목록입니다.

**2) S3는 게이트웨이 엔드포인트가 무료입니다.**
S3·DynamoDB는 **게이트웨이 엔드포인트**(라우팅 테이블에 경로 추가)로 비용 없이 프라이빗 접근이 됩니다. 문서 저장소가 S3인 RAG 파이프라인이라면 NAT를 거칠 이유가 없습니다. 반면 interface endpoint는 시간당 과금이 있으니 용도별로 구분합니다.

**3) "연결됐는데 왜 안 되죠"의 대부분은 DNS입니다.**
엔드포인트만 만들고 프라이빗 호스팅 존을 연결하지 않으면, SDK는 여전히 공인 주소를 찾습니다. `nslookup`으로 **사설 IP로 해석되는지**를 첫 진단 항목으로 넣습니다.

## 🧯 마무리: 장애가 나면 어느 계층부터 보는가

면접에서 "API가 안 됩니다"라는 시나리오 질문이 나오면, 이 표를 말로 풀면 됩니다.

| 증상 | 먼저 볼 곳 | 대표 확인 |
| --- | --- | --- |
| 이름을 못 찾음 | DNS | `nslookup`, TTL, 프라이빗 존 |
| 연결 자체가 안 됨 | 포트·방화벽·라우팅 | SG/NACL, 라우팅 테이블, NAT |
| 60초마다 간헐적 502 | keep-alive·타임아웃 | LB 유휴 타임아웃 vs 앱 keep-alive |
| 인증서 오류 | TLS | 만료일, 체인, 사내 프록시 |
| 브라우저만 실패 | CORS | 프리플라이트, Allow-Origin |
| 응답이 한 번에 옴 | 버퍼링 | SSE 버퍼링 해제, 압축 |

> **"네트워크는 '이름 → 연결 → 암호 → 통제' 순서로 쌓이고, 장애는 항상 아래층에서 위층으로 전파된다. 이 사다리를 그릴 수 있는 SA는 장애 대응 시간을 절반으로 줄인다."**
