서비스를 하나로 만들 때는 없던 문제가, 두 개로 나누는 순간 생깁니다.

*"A 서버는 성공했는데 B 서버는 실패하면 어떻게 되나요?"*

이 질문이 분산 시스템의 본질입니다. 네트워크는 언젠가 끊기고, 상대 서비스는 언젠가 느려지고, 같은 요청은 두 번 도착할 수 있습니다. SA 면접에서 안정성 질문은 **"정상일 때 어떻게 동작하나"** 가 아니라 **"망가질 때 무엇이 남는가"** 로 나옵니다.

이 글의 7개 묶음입니다.

1. **동기 vs 비동기 · 메시지 큐(Kafka · SQS)** — 기다릴 것인가, 맡길 것인가
2. **캐싱(Redis · CDN · TTL · 무효화)** — 가장 싼 성능 개선
3. **Rate Limiting · Circuit Breaker · Retry & Backoff** — 과부하를 다루는 세 가지 장치
4. **멱등성(Idempotency)** — 재시도가 중복을 만들지 않게
5. **Scale-Up vs Scale-Out · SPOF · HA & DR** — 죽지 않게, 죽어도 이어지게
6. **Latency vs Throughput · P95 / P99** — 평균은 거짓말을 한다
7. **Observability 3축 & OpenTelemetry** — 보이지 않으면 고칠 수 없다

## 📮 1. 동기 vs 비동기 · 메시지 큐 (Kafka · SQS)

**일상 비유**: **동기 호출은 은행 창구**입니다. 번호표를 뽑고 내 차례가 올 때까지 서 있어야 합니다. **비동기 + 메시지 큐는 식당의 주문서 걸이**입니다. 주문서를 걸어 두면 주방이 순서대로 처리하고, 손님은 자리에 앉아 기다립니다. 주문서가 쌓이면 주방을 늘리면 되고, 주방이 잠깐 멈춰도 주문서는 사라지지 않습니다.

**핵심 원리**: 동기 호출은 **호출자가 응답까지 자원을 붙잡고** 있습니다. 비동기는 **메시지를 큐에 넣고 즉시 반환**한 뒤, 소비자가 자기 속도로 처리합니다.

| 구분 | 동기 (REST 호출) | 비동기 (큐) |
| --- | --- | --- |
| 응답 | 즉시 결과 | 접수 확인(202) 후 나중에 |
| 결합도 | 강함 (상대 장애 = 내 장애) | 약함 (큐가 버퍼) |
| 재시도 | 호출자가 직접 | 큐가 자동 (실패 시 재전달) |
| 쓰는 자리 | 사용자 응답이 필요한 조회 | 문서 인덱싱, 알림, 배치 |

**Kafka vs SQS** — 자주 비교되는 두 가지입니다.

| 항목 | Kafka | SQS |
| --- | --- | --- |
| 모델 | 분산 로그(토픽·파티션) | 관리형 큐 |
| 메시지 보존 | 기간 보관, 재처리 가능 | 소비 후 삭제 |
| 순서 | **파티션 내 순서 보장** | 표준은 미보장, FIFO는 보장 |
| 다수 소비자 | 여러 컨슈머 그룹이 각자 읽기 | 한 메시지는 한 소비자 |
| 쓰는 자리 | 이벤트 스트림, 로그 파이프라인 | 작업 큐, 간단한 팬아웃 |

**핵심 감각**: Kafka의 **파티션 키**가 순서를 결정합니다. 같은 사용자의 이벤트는 같은 키로 보내야 순서가 지켜지고, 키를 안 정하면 순서가 뒤섞여 "수정 이벤트가 생성 이벤트보다 먼저 처리"되는 사고가 납니다.

**RAG에서의 실제 구조**: 문서 업로드 → 큐에 넣기 → 파서·청커·임베딩 워커가 소비 → 벡터 DB 저장. 사용자는 "처리 중"만 보면 되고, 워커가 죽어도 메시지는 남아 재처리됩니다. 이걸 동기로 만들면 업로드 요청이 수 분씩 걸립니다.

### 🎤 면접 30초 답변

> "동기 호출은 호출자가 응답까지 연결과 스레드를 붙잡고 있어서 상대가 느려지면 나도 느려지고, 상대가 죽으면 나도 실패합니다. 비동기는 메시지 큐에 작업을 넣고 즉시 접수 응답을 돌려준 뒤 소비자가 자기 속도로 처리하므로 결합도가 낮아지고 장애가 격리됩니다. 문서 인덱싱이나 알림처럼 사용자가 즉시 결과를 볼 필요가 없는 일은 비동기가 적합합니다. 다만 비동기는 결과를 바로 알 수 없어서 상태 조회 API가 필요하고, 중복 전달이 있을 수 있으므로 소비자를 멱등하게 만들어야 합니다."

### 🎯 SA 실무 포인트

**1) "비동기로 하면 빨라집니다"는 절반만 맞습니다.**
빨라지는 것은 **응답**이지 전체 처리 시간이 아닙니다. 사용자가 결과를 기다려야 하는 일(챗봇 답변)은 동기·스트리밍이 맞습니다. 판단 기준은 **"사용자가 이 순간 결과를 봐야 하는가"** 입니다.

**2) 큐가 있으면 DLQ(Dead Letter Queue)와 재처리 정책이 한 세트입니다.**
실패 메시지가 무한 재시도로 큐를 막으면 전체가 멈춥니다. 재시도 횟수, 백오프, DLQ 보관 기간, 수동 재주입 절차를 문서에 넣습니다.

**3) 순서가 중요한 업무는 파티션 키 설계가 곧 요구사항입니다.**
"주문 상태 변경은 순서대로"라는 요구가 있으면 파티션 키를 주문 ID로 잡아야 합니다. 놓치면 운영 단계에서 데이터 정합성 사고로 돌아옵니다.

## ⚡ 2. 캐싱 (Redis · CDN · TTL · 무효화)

**일상 비유**: **캐시는 책상 위 메모**입니다. 서랍(DB)까지 가는 대신 눈앞의 메모를 봅니다. 문제는 메모가 낡았을 때입니다. 원본이 바뀌었는데 메모를 안 고치면 **틀린 답을 아주 빠르게** 하게 됩니다.

**핵심 원리**: 캐시는 **원본보다 빠르고 가까운 저장소**에 결과를 복제합니다. 성능의 핵심은 속도가 아니라 **적중률(hit ratio)** 입니다.

| 계층 | 무엇을 캐시하나 | 대표 도구 |
| --- | --- | --- |
| 브라우저 | 정적 자원, API 응답 | HTTP 캐시 헤더 |
| CDN 엣지 | 이미지·JS·HTML | CloudFront, Cloudflare |
| 애플리케이션 | 계산 결과, 세션 | Redis, Memcached |
| DB | 쿼리 결과·버퍼 풀 | 내부 버퍼, materialized view |

**대표 패턴 세 가지**

| 패턴 | 흐름 | 특징 |
| --- | --- | --- |
| Cache-Aside | 앱이 캐시 확인 → 없으면 DB → 캐시 저장 | 가장 흔함, 무효화 직접 |
| Write-Through | 쓸 때 캐시와 DB 함께 갱신 | 일관성 좋음, 쓰기 느림 |
| Write-Behind | 캐시에 먼저 쓰고 나중에 DB 반영 | 빠름, 유실 위험 |

**무효화 전략**이 캐시의 진짜 난이도입니다.

- **TTL**: 시간이 지나면 자동 만료. 단순하고 안전하지만 최대 TTL만큼 낡은 데이터가 노출됩니다.
- **이벤트 기반 삭제**: 원본 변경 시 키 삭제. 정확하지만 놓치면 영원히 낡습니다.
- **버전 키**: `doc:123:v7`처럼 버전을 붙여 새 버전을 쓰게 함. 삭제 없이 자연 전환됩니다.

**핵심 함정 — 캐시 스탬피드(Thundering Herd)**: 인기 키가 만료되는 순간 수백 요청이 동시에 DB로 몰립니다. 해법은 **분산 락(한 요청만 채우기)**, **TTL 지터(만료 시각 흩뿌리기)**, **stale-while-revalidate**(일단 낡은 값 주고 뒤에서 갱신)입니다.

### 🎤 면접 30초 답변

> "캐시는 원본보다 가까운 곳에 결과를 복제해 응답 시간과 원본 부하를 줄이는 기법이고, 효과는 적중률로 결정됩니다. 가장 흔한 방식은 cache-aside로, 조회 시 캐시를 먼저 보고 없으면 원본에서 읽어 채웁니다. 문제는 일관성입니다. TTL로 만료시키는 방식이 단순하지만 그 시간만큼 낡은 값이 나가고, 원본 변경 시 이벤트로 삭제하면 정확하지만 놓칠 위험이 있습니다. 또한 인기 키가 동시에 만료되면 요청이 원본으로 몰리는 캐시 스탬피드가 생기므로, TTL에 지터를 주거나 한 요청만 채우도록 락을 걸어 방어합니다."

### 🎯 SA 실무 포인트

**1) LLM 캐싱은 두 층입니다 — 정확 일치와 의미 기반.**
같은 프롬프트의 정확 일치 캐시는 안전합니다. **의미 기반(시맨틱) 캐시**는 유사 질문에 같은 답을 주므로 비용은 줄지만 **틀린 답을 빠르게** 줄 위험이 있습니다. 금액·권한·개인정보가 걸린 질문은 캐시 제외 대상으로 분류해야 합니다.

**2) 캐시는 권한 경계를 넘으면 안 됩니다.**
사용자별 권한이 다른 RAG에서 응답을 전역 캐시하면 A의 답이 B에게 갑니다. **캐시 키에 권한 컨텍스트(부서·역할)를 포함**시키는 것이 원칙입니다. 이 한 줄이 보안 사고를 막습니다.

**3) "캐시 지우면 되죠"가 안 통하는 곳이 CDN입니다.**
엣지 캐시는 지역마다 퍼져 있어 무효화가 전파되는 데 시간이 걸립니다. 배포 직후 옛 화면이 보이는 문제의 원인입니다. 정적 자원은 **파일명에 해시**를 넣어 무효화 자체를 없애는 방식이 표준입니다.

## 🚦 3. Rate Limiting · Circuit Breaker · Retry & Backoff

**일상 비유**: 세 장치는 각각 다른 상황을 막습니다.

- **Rate Limiting = 놀이공원 입장 제한**. 한 번에 너무 많이 들이면 시설이 망가집니다.
- **Circuit Breaker = 과부하 차단기**. 문제가 생기면 스위치를 내려 불이 나는 것을 막고, 안정되면 다시 올립니다.
- **Retry & Backoff = 다시 시도하는 예의**. 바로 다시 걸면 상대는 더 힘들어집니다. 점점 간격을 늘려 재시도합니다.

**핵심 원리**:

**① Rate Limiting** — 핵심은 **알고리즘과 기준 키**입니다.

| 알고리즘 | 동작 | 특징 |
| --- | --- | --- |
| 고정 윈도우 | 1분당 N회 | 단순, 경계에서 몰림 |
| 슬라이딩 윈도우 | 최근 N초 기준 | 정확, 구현 복잡 |
| 토큰 버킷 | 토큰이 차면 허용, 소모 | **버스트 허용** |
| 리키 버킷 | 일정 속도로 누출 | 균일 속도 |

기준 키는 사용자·API 키·IP·테넌트입니다. 초과 시 **429 + `Retry-After`** 를 반환해 클라이언트가 스스로 물러나게 합니다.

**② Circuit Breaker** — 세 상태를 기억합니다.

```text
CLOSED (정상 통과)
   ↓ 실패율 임계 초과
OPEN (즉시 실패 반환 — 상대를 쉬게 함)
   ↓ 일정 시간 경과
HALF-OPEN (일부만 통과시켜 확인)
   ↓ 성공 → CLOSED / 실패 → OPEN
```

**③ Retry & Backoff** — 지수 백오프 + 지터입니다.

```text
1차: 1초  → 2차: 2초 → 3차: 4초 (+ 무작위 지터)
재시도는 멱등한 요청에만, 최대 3회, 전체 타임아웃 안에서
```

**지터가 왜 필요한가**: 모든 클라이언트가 같은 간격으로 재시도하면 **동시에 다시 몰립니다**(retry storm). 무작위 지터를 더하면 부하가 시간축으로 흩어집니다.

### 🎤 면접 30초 답변

> "Rate Limiting은 사용자나 API 키 단위로 허용량을 제한해 과부하와 남용을 막고, 초과 시 429와 Retry-After를 반환해 클라이언트가 물러나게 합니다. Circuit Breaker는 하위 서비스 실패율이 임계치를 넘으면 회로를 열어 즉시 실패를 반환함으로써 장애가 전파되는 것을 막고, 일정 시간 뒤 반열림 상태로 일부 요청만 보내 회복을 확인합니다. Retry는 지수 백오프와 무작위 지터를 더해 재시도 폭주를 막고, 멱등한 요청에만 제한된 횟수로 적용합니다. 이 세 가지는 함께 설계해야 효과가 있고, 특히 AI 게이트웨이에서는 테넌트별 토큰 쿼터와 모델별 폴백을 같은 계층에서 처리합니다."

### 🎯 SA 실무 포인트

**1) LLM 게이트웨이의 진짜 병목은 토큰입니다.**
요청 수 제한만 걸면 **긴 프롬프트 한 방**으로 비용이 터집니다. **요청 수 + 토큰 수 + 동시 요청 수** 세 가지를 함께 제한하고, 모델별로 다른 쿼터를 둡니다.

**2) 공급자 장애 대비가 곧 회로 차단기입니다.**
OpenAI나 Bedrock이 느려질 때 우리 앱이 함께 죽지 않으려면 ① 타임아웃 ② 회로 차단 ③ 대체 모델 폴백 ④ 캐시 응답. "폴백 모델이 있습니다"가 제안서에 한 줄 있는 것과, 실제로 전환되는 것과는 큰 차이입니다 — PoV에서 **강제 장애 주입**으로 증명해 두면 신뢰가 완전히 달라집니다.

**3) 타임아웃은 계층마다 줄어들어야 합니다.**
클라이언트 30초 → 게이트웨이 25초 → 앱 20초 → 하위 호출 15초. 안쪽이 더 길면 바깥이 먼저 끊어 결과를 버리면서 자원은 계속 쓰는 **유령 작업**이 남습니다.

## 🔁 4. 멱등성(Idempotency): 재시도가 중복을 만들지 않게

**일상 비유**: 엘리베이터 버튼은 **여러 번 눌러도 한 번만** 동작합니다. 이게 멱등성입니다. 반대로 **송금 버튼**은 누를 때마다 돈이 나갑니다. 네트워크가 끊겨 "결과를 못 받았다"고 다시 누르면 두 번 나갑니다.

**핵심 원리**: 같은 요청을 여러 번 수행해도 **결과 상태가 한 번 수행한 것과 같은 성질**입니다.

| 메서드 | 멱등? | 이유 |
| --- | --- | --- |
| GET / PUT / DELETE | **예** | 조회·덮어쓰기·삭제는 반복해도 같은 상태 |
| POST | 아니오 | "새로 만든다"는 의미라 반복 시 중복 생성 |
| PATCH | 구현에 따라 | 증분 연산(`+1`)이면 멱등 아님 |

**실무 해법 — 멱등성 키**

1. 클라이언트가 요청마다 고유 키를 만든다 (`Idempotency-Key: uuid`)
2. 서버가 **키 → 처리 결과**를 저장한다 (TTL 24시간 등)
3. 같은 키가 다시 오면 **재처리 없이 저장된 결과를 반환**한다

```text
POST /payments
Idempotency-Key: 7c9e6679-7425-40de-944b-e07fc1f90ae7

[1회차] 처리 → 결과 저장
[2회차] 키 발견 → 200 (이전 응답 그대로)
```

**핵심 감각**: 분산 환경에서 **정확히 한 번(exactly-once)** 은 사실상 불가능합니다. 현실적인 목표는 **최소 한 번 전달(at-least-once) + 멱등한 소비자**입니다. Kafka, SQS 모두 기본이 최소 한 번입니다.

**결제·도구 호출에서 특히 위험한 것**: LLM 에이전트가 "메일 보내기" 같은 도구를 호출했다가 타임아웃으로 재시도하면 메일이 두 번 갑니다. **부작용이 있는 도구 호출에는 반드시 멱등성 키**를 붙입니다.

### 🎤 면접 30초 답변

> "멱등성은 같은 요청을 여러 번 수행해도 최종 상태가 한 번 수행한 것과 같아지는 성질입니다. 불확실한 네트워크에서는 요청이 실패한 것인지 응답만 유실된 것인지 알 수 없어서 재시도가 필수인데, 이때 멱등하지 않으면 중복 결제나 중복 생성이 생깁니다. 실무에서는 클라이언트가 Idempotency-Key를 보내고 서버가 키와 처리 결과를 일정 기간 저장해, 같은 키의 재요청에는 재처리 없이 이전 결과를 반환하는 방식으로 구현합니다. 분산 시스템에서 정확히 한 번은 사실상 불가능하므로 최소 한 번 전달에 멱등한 소비자를 조합하는 것이 표준입니다."

### 🎯 SA 실무 포인트

**1) AI 에이전트는 "부작용 있는 도구"를 반드시 분리하세요.**
조회 도구는 재시도해도 안전하지만 **쓰기 도구**(메일 발송, 티켓 생성, 결제)는 사람 확인 또는 멱등성 키가 필요합니다. 이 구분을 도구 카탈로그에 표시해 두면 승인 흐름 설계가 자연스러워집니다.

**2) 비용도 중복됩니다.**
재시도로 같은 프롬프트를 두 번 보내면 **토큰도 두 번 과금**됩니다. 재시도 정책에 "이미 성공한 요청은 재시도하지 않는다"를 명시하고, 요청 ID를 로그에 남겨 중복 호출을 추적합니다.

**3) 멱등성 저장소는 캐시와 분리하세요.**
키 저장소가 날아가면 중복 결제가 됩니다. TTL이 있는 캐시에 넣더라도 **결제 같은 중요 작업은 영속 저장소**에 둡니다.

## 🏗️ 5. Scale-Up vs Scale-Out · SPOF · HA & DR

**일상 비유**: **Scale-Up은 더 큰 트럭 한 대**를 사는 것, **Scale-Out은 같은 트럭 여러 대**를 사는 것입니다. 큰 트럭은 관리가 쉽지만 한 대가 고장 나면 끝이고, 여러 대는 하나가 고장 나도 계속 갑니다. **SPOF는 다리 하나뿐인 섬**이고, **HA는 다리를 두 개 놓는 것**, **DR은 섬 자체가 침몰했을 때 갈 다른 섬**입니다.

**핵심 원리**:

| 구분 | Scale-Up (수직) | Scale-Out (수평) |
| --- | --- | --- |
| 방법 | CPU·메모리 증설 | 인스턴스 수 증가 |
| 한계 | 하드웨어 상한, 비용 급증 | 애플리케이션이 무상태여야 |
| 장애 영향 | 단일 실패점 | 분산되어 영향 축소 |
| 적합 | DB, 대형 GPU | 웹/API, 워커 |

**SPOF 찾기**: 아키텍처 그림에서 **하나만 있는 것**을 모두 표시합니다 — 로드밸런서 1대, NAT 1대, DB 1대, 인증 서버 1대, 배포 파이프라인 1개. 각각에 대해 ① 이중화 ② 자동 전환 ③ 장애 시 저하 모드(degraded mode)를 결정합니다.

**HA vs DR — 목표 수치가 다릅니다.**

| 지표 | 의미 | 예 |
| --- | --- | --- |
| RTO | 복구 목표 시간 (얼마나 빨리 살아나야) | 30분 |
| RPO | 허용 데이터 손실 (얼마나 잃어도 되나) | 5분 |
| 가용성 | 다운타임 비율 | 99.9% = 월 43분 |

| DR 전략 | 비용 | RTO | RPO |
| --- | --- | --- | --- |
| 백업·복구 | 낮음 | 시간~일 | 시간 |
| 파일럿 라이트 | 중간 | 수십 분~시간 | 분 |
| 웜 스탠바이 | 높음 | 분 | 분 |
| 액티브-액티브 | 매우 높음 | 거의 0 | 거의 0 |

**핵심 감각**: **"멀티 AZ"는 HA이고 "멀티 리전"은 DR입니다.** 고객이 "이중화되어 있나요?"라고 물으면 어느 수준인지 되물어야 합니다. AZ 이중화는 리전 장애를 못 막습니다.

### 🎤 면접 30초 답변

> "Scale-Up은 장비 사양을 키우는 수직 확장이라 관리가 단순하지만 하드웨어 상한과 비용 문제가 있고, Scale-Out은 인스턴스를 늘리는 수평 확장이라 장애 영향이 분산되지만 애플리케이션이 무상태여야 합니다. SPOF는 하나만 존재해서 그것이 죽으면 전체가 멈추는 지점이고, 아키텍처에서 유일한 구성 요소를 모두 찾아 이중화·자동 전환·저하 모드를 설계합니다. HA는 가용영역 수준의 이중화로 짧은 장애를 견디는 것이고, DR은 리전 단위 재해에 대비하는 것으로 RTO와 RPO를 목표로 삼아 백업 복구부터 액티브-액티브까지 비용과 함께 선택합니다."

### 🎯 SA 실무 포인트

**1) RTO/RPO를 먼저 물으세요. 숫자 없이 DR을 설계할 수 없습니다.**
"재해 대비 되어 있나요?"에 "됩니다"라고 답하는 제안은 신뢰를 잃습니다. **"RTO 30분·RPO 5분이면 웜 스탠바이, 이 비용은 월 X입니다"** 가 정답입니다.

**2) 저하 모드(degraded mode)를 설계에 넣으세요.**
LLM 서비스에서 모델 API가 죽으면? ① 캐시 응답 ② 소형 모델 폴백 ③ "지금은 요약만 가능합니다" 안내. 완전 정지보다 **부분 기능 유지**가 고객 만족도가 훨씬 높습니다.

**3) DR 훈련을 계획에 포함하세요.**
문서에 있는 DR은 없는 DR입니다. 분기 1회 페일오버 훈련, 측정된 실제 RTO 기록. 이 항목이 있는 제안서는 유지보수 단계에서 신뢰를 만듭니다.

## ⏱️ 6. Latency vs Throughput · P95 / P99

**일상 비유**: **Latency는 한 손님이 주문에서 음식까지 기다린 시간**, **Throughput은 1시간에 몇 테이블을 돌렸는가**입니다. 주방을 개선해 시간당 처리량을 2배로 늘렸는데, 특정 테이블만 계속 늦는다면 그 손님에게는 여전히 최악의 식당입니다. **P99는 "가장 운 나쁜 1%의 손님이 겪는 시간"** 입니다.

**핵심 원리**:

| 지표 | 의미 | 오해 |
| --- | --- | --- |
| 평균(Avg) | 전체 합 / 건수 | **느린 소수를 숨긴다** |
| P50 | 절반이 이보다 빠름 | "보통"의 경험 |
| P95 | 95%가 이보다 빠름 | 대체로 SLA 기준 |
| P99 | 99%가 이보다 빠름 | **꼬리 지연(tail latency)** |

**핵심 감각**: 평균 100ms인 서비스가 P99 2,000ms일 수 있습니다. 사용자는 랜덤하게 요청하므로, 하루 100번 쓰는 사용자가 1% 확률을 만나면 **며칠에 한 번은 극단적으로 느린 경험**을 합니다. 그래서 SLA는 평균이 아니라 **P95/P99**로 겁니다.

**왜 꼬리가 생기는가**: ① GC pause ② 캐시 미스 ③ 특정 파티션·핫키 ④ 재시도 ⑤ 노이즈 이웃(같은 노드의 다른 워크로드). 꼬리 지연은 **한 요청이 여러 서비스를 거치면 증폭**됩니다 — 10개 서비스가 각각 1% 확률로 느리면 전체의 10%가 느려집니다.

**LLM의 지연 지표는 따로 있습니다.**

| 지표 | 의미 | 목표 감각 |
| --- | --- | --- |
| TTFT | 첫 토큰까지 시간 | 1초 이내 체감 좋음 |
| TPOT | 토큰 간 간격 | 20~50ms |
| 전체 응답 | 완료까지 | 길이에 비례 |
| 대기열 시간 | 큐에서 기다린 시간 | 이게 길면 용량 부족 |

### 🎤 면접 30초 답변

> "Latency는 요청 하나의 처리 시간이고 Throughput은 단위 시간당 처리량입니다. 둘은 트레이드오프가 있어서 배치를 키우면 처리량은 늘지만 개별 지연은 나빠집니다. 지연은 평균으로 보면 안 됩니다. 평균은 느린 소수를 가리기 때문에 사용자 경험과 SLA는 P95나 P99로 측정합니다. 꼬리 지연은 GC, 캐시 미스, 핫 파티션, 재시도 같은 원인으로 생기고, 여러 서비스를 거치면 증폭됩니다. LLM 서비스라면 첫 토큰까지의 시간과 토큰 간 간격, 대기열 시간을 별도 지표로 봐야 체감 품질을 설명할 수 있습니다."

### 🎯 SA 실무 포인트

**1) SLA 문구를 숫자로 바꾸는 것이 SA의 일입니다.**
"빠른 응답" 대신 **"P95 2초 이내, 스트리밍 첫 토큰 1초 이내"**. 측정 지점(어디서 재는가)까지 정해야 나중에 분쟁이 없습니다 — 클라이언트 체감과 서버 로그는 다릅니다.

**2) 동시 사용자 산정은 리틀의 법칙으로.**
동시 요청 ≈ 도착률 × 평균 처리 시간. 평균 3초, 초당 10건이면 30개가 동시에 떠 있습니다. 여기에 여유율을 얹어야 "몇 명까지" 답할 수 있습니다.

**3) 느린 요청 1%를 분리해서 보세요.**
P99가 튀는 요인을 찾으려면 **요청을 느린 순으로 정렬해 공통점**(같은 테넌트, 같은 모델, 긴 프롬프트)을 찾습니다. 이 분석이 있어야 "모델을 바꿀지, 캐시를 넣을지" 결정할 수 있습니다.

## 🔭 7. Observability 3축 & OpenTelemetry

**일상 비유**: **Metrics는 자동차 계기판**(속도·연료·온도 숫자), **Logs는 블랙박스 영상**(무슨 일이 있었는지), **Traces는 내비게이션 경로 기록**(어디서 막혔는지)입니다. 계기판만 보면 "차가 느리다"까지만 알고, 블랙박스와 경로 기록이 있어야 **"어느 구간에서 막혔는지"** 를 압니다.

**핵심 원리**:

| 축 | 무엇 | 답하는 질문 | 대표 도구 |
| --- | --- | --- | --- |
| Metrics | 숫자 시계열 | **얼마나? 언제부터?** | Prometheus, CloudWatch |
| Logs | 사건 기록 | **무슨 일이?** | Loki, ELK |
| Traces | 요청의 서비스 경로 | **어디서 느려졌나?** | Jaeger, Tempo |

**Trace의 구조**: 하나의 요청이 여러 서비스를 지나며 **trace ID**를 공유하고, 각 구간은 **span**입니다. 컨텍스트 전파는 **W3C `traceparent`** 헤더로 이뤄집니다.

```text
trace a3f2...
├─ gateway  (12ms)
├─ auth     (8ms)
├─ retrieval (350ms)  ← 병목
└─ llm       (1,200ms)
```

**OpenTelemetry(OTel)** 는 벤더 중립 계측 표준입니다. SDK로 계측하면 수집기(Collector)를 거쳐 어떤 백엔드로든 보낼 수 있어 **도구 교체 비용**이 줄어듭니다.

**AI 서비스에서 추가로 봐야 할 지표**

| 지표 | 왜 필요한가 |
| --- | --- |
| 토큰 사용량(입출력) | 비용의 직접 원인 |
| 모델별 지연·오류율 | 폴백 판단 근거 |
| 검색 적중률·인용률 | 답변 품질 지표 |
| 캐시 적중률 | 비용 최적화 성과 |
| 프롬프트 버전 | 품질 변화 추적 |

### 🎤 면접 30초 답변

> "관측성은 시스템 외부에서 내부 상태를 추론할 수 있게 하는 것으로, 메트릭·로그·트레이스 세 축으로 구성됩니다. 메트릭은 집계된 숫자 시계열이라 추세와 임계 알림에 강하고, 로그는 개별 사건의 상세 기록이며, 트레이스는 하나의 요청이 여러 서비스를 지나는 경로와 구간별 시간을 보여줍니다. 장애 대응은 보통 메트릭으로 이상을 감지하고, 트레이스로 병목 구간을 찾고, 로그로 원인을 확정하는 순서로 진행됩니다. OpenTelemetry는 이 세 가지를 벤더 중립으로 계측하는 표준이라, 백엔드를 바꿔도 계측 코드를 다시 짜지 않아도 됩니다."

### 🎯 SA 실무 포인트

**1) 상관관계 ID가 없으면 로그는 쓸모없습니다.**
서비스가 3개만 넘어도 "이 요청의 로그"를 모으기 어렵습니다. 요청 시작 시 `request_id`를 만들고 모든 로그·응답 헤더에 넣는 것만으로 장애 대응 시간이 크게 줄어듭니다.

**2) LLM 비용은 관측성의 문제입니다.**
요청별 토큰 사용량과 모델을 기록하지 않으면 "이번 달 AI 비용이 왜 늘었나"에 답할 수 없습니다. 테넌트·기능·모델 3개 축으로 집계하는 것이 FinOps의 시작입니다.

**3) 개인정보와 관측성은 충돌합니다.**
프롬프트를 그대로 로그에 남기면 개인정보가 샙니다. **메타데이터는 남기고 본문은 마스킹/샘플링**하는 정책을 로그 설계 단계에서 정합니다. 나중에 지우는 것은 거의 불가능합니다.

## 🧭 한 줄 정리

> **"분산 시스템의 안정성은 '정상 경로를 빠르게' 만드는 것이 아니라 '비정상 경로를 견디게' 만드는 것이다. 큐로 결합을 끊고, 캐시로 부하를 줄이고, 회로 차단기로 전파를 막고, 멱등성으로 재시도를 안전하게 만들고, 관측성으로 그것이 실제로 동작함을 증명한다."**
