서버 작업을 하다 보면 이런 대화를 자주 듣습니다.

*"터미널 열어서 ssh로 붙어."*

여기서 세 단어가 한 문장에 나옵니다. **터미널**, **SSH**, 그리고 (말하지 않았지만 뒤에서 일하는) **셸**. 취준생 때는 "그냥 검은 창"이었는데, SA 면접에서 "터미널과 셸의 차이가 뭐죠?"라고 물어보면 말문이 막히는 지점이기도 합니다. 실무에서는 이 구분이 **권한·보안·장애 원인**을 가르는 기준이 되기 때문입니다.

이 글은 세 가지를 이렇게 정리합니다.

- **일상 비유**: 식당의 **주문 창구(터미널)** · **점원(셸)** · **주방(커널)**, 그리고 **남의 식당 주방에 들어가는 암호 파이프(SSH)**
- **기술적 정의**: 터미널 에뮬레이터 → PTY → 셸의 `fork`/`execve` → 커널 시스템 콜, SSH의 키 교환·호스트 키·공개키 인증
- **🎤 면접 30초 답변**과 **🎯 SA 실무 포인트** (Bastion, 키 관리, 폐쇄망)

## 🍽️ 1. 터미널 · 셸 · 커널: 식당의 3인방

가게 하나를 떠올려 봅시다. 손님(나)이 있고, 주문을 받는 **창구**가 있고, 그 창구에서 주문을 받아 주방에 전달하는 **점원**이 있고, 실제로 요리를 만드는 **주방**이 있습니다.

| 역할 | 식당 비유 | 컴퓨터에서는 |
| --- | --- | --- |
| 주문 창구 | 내가 말하고 결과를 건네받는 창 | **터미널 (Terminal)** |
| 점원 | 주문을 주방이 알아듣는 말로 바꿔 전달 | **셸 (Shell)** |
| 주방 | 실제로 재료를 손질하고 요리를 만듦 | **커널 (Kernel)** |

### ① 터미널 (Terminal): 주문 창구 = 입출력 창

**일상 비유**: 창구 직원은 요리를 못 합니다. 내 말을 듣고, 결과물을 내미는 역할만 합니다. "김치찌개 하나요"라는 말의 뜻을 해석하지도 않습니다.

**기술적 정의**: 터미널은 **키보드 입력을 글자로 받아 화면에 출력해 주는 UI 프로그램**입니다. 옛날에는 키보드와 모니터가 붙은 하드웨어 단말기(VT100 같은 장비)였는데, 지금은 그걸 소프트웨어로 흉내 낸 **터미널 에뮬레이터(Terminal Emulator)** 를 씁니다.

- macOS: `Terminal.app`, `iTerm2`
- Windows: `Windows Terminal`, `PuTTY`
- Linux: `GNOME Terminal`, `Alacritty`

**핵심**: 터미널은 명령어를 **이해하지 못합니다**. `ls`가 목록을 보여주는 명령이라는 걸 모르고, 그냥 글자를 주고받을 뿐입니다.

여기서 하나 더, **PTY(Pseudo-Terminal, 의사 터미널)** 입니다. SSH로 서버에 붙으면 서버 쪽에 가짜 터미널 장치가 하나 만들어집니다. 그래서 원격인데도 프롬프트가 뜨고, `Ctrl+C`로 프로세스를 끊고, `vim` 같은 전체 화면 프로그램이 정상 동작합니다. (그래서 `ssh -t`로 명령 하나만 실행할 때도 PTY를 강제로 붙입니다.)

### ② 셸 (Shell): 점원 = 명령어 해석기

**일상 비유**: 점원은 손님의 말을 주방이 알아듣는 주문서로 바꿉니다. "김치찌개 하나, 덜 맵게"를 주방 언어로 옮기는 사람입니다.

**기술적 정의**: 셸은 사용자가 입력한 **문자열을 해석(parsing)** 해서 프로그램을 실행하고, 그 결과를 커널에 **시스템 콜(System Call)** 로 요청하는 **인터페이스 프로그램**입니다.

- `bash` (Linux 기본), `zsh` (macOS 기본), `sh`, `fish`, `PowerShell`(Windows)

`ls`를 쳤을 때 실제로 벌어지는 일은 이렇습니다.

1. 셸이 프롬프트(`$`)를 띄우고 입력을 기다린다
2. `ls`를 받으면 환경변수 `PATH`에 적힌 디렉터리들을 뒤져 `/bin/ls` 실행 파일을 찾는다
3. `fork()`로 자기 자신을 복제해 자식 프로세스를 만든다
4. 자식이 `execve("/bin/ls", ...)`로 `ls` 프로그램으로 갈아입는다
5. `ls`가 결과를 표준출력으로 내보내고, 그 출력이 터미널 창에 그려진다

**중요한 감각**: **셸도 그냥 프로그램 하나**입니다. 그래서 `zsh`에서 `bash`를 치면 셸 안에서 다른 셸이 실행되고, `exit`를 치면 그 셸이 끝나면서 창이 닫힙니다.

```bash
echo $SHELL      # 로그인 셸 경로 (/bin/zsh 등)
ps -p $$         # 지금 이 프롬프트를 띄운 프로세스 = 셸
chsh -s /bin/zsh # 로그인 셸 변경
```

이름이 **shell(껍데기)** 인 이유도 여기 있습니다. 커널이라는 **알맹이를 감싼 껍데기** 역할을 하니까요.

### ③ 커널 (Kernel): 주방 = OS 핵심

**일상 비유**: 주방은 손님이 들어올 수 없습니다. 위생과 안전 규칙이 있어서, 주문서(시스템 콜)를 통해서만 요청할 수 있습니다.

**기술적 정의**: 커널은 **프로세스·메모리·파일시스템·네트워크·장치를 실제로 관리하는 OS의 핵심**입니다. 일반 프로그램(유저 공간)은 디스크나 메모리를 직접 만질 수 없고, `open()`, `read()`, `write()`, `fork()`, `execve()` 같은 **시스템 콜**을 통해서만 커널에 요청합니다. 커널은 그 요청마다 **권한을 검사**합니다.

이 계층이 중요한 이유는 **보안 경계**가 여기 있기 때문입니다. "내가 친 `rm` 한 줄이 어떻게 디스크까지 도달하는가"를 계층으로 설명할 수 있으면, 그다음 질문인 최소 권한·컨테이너 격리·`sudo`의 의미로 자연스럽게 이어집니다.

### 🔁 한 줄로 이어 붙이면

```text
[내 키보드]
   ↓ 입력
[터미널 에뮬레이터]        ← 창(UI). 명령어의 뜻은 모름
   ↓ 글자 전달 (PTY)
[셸: bash / zsh]           ← 해석, PATH 탐색, fork + execve
   ↓ 시스템 콜 (open / read / write)
[커널]                     ← 권한 검사 후 실제 실행
   ↓
[하드웨어: CPU · SSD · NIC]
```

> **"터미널을 연다"** = 창을 띄운다. **"셸에서 명령을 친다"** = 그 창 뒤의 프로그램에게 일을 시킨다.

### 🎤 면접 30초 답변 (터미널 / 셸 / 커널)

> "터미널은 키보드 입력을 받아 화면에 출력해 주는 **UI 프로그램**이고, 명령어를 해석하지는 못합니다. 셸은 그 터미널 뒤에서 사용자의 명령을 해석해 프로그램을 실행하고, 커널에 시스템 콜로 요청하는 **인터페이스**입니다. bash나 zsh가 셸이고, 커널은 프로세스·메모리·파일·네트워크를 실제로 관리하며 유저 공간의 접근을 권한 검사하는 **OS 핵심**입니다. 그래서 '터미널을 켠다'는 건 창을 띄우는 것이고, 실제 명령을 수행하는 주체는 셸이라는 프로그램입니다."

30초를 더 줄여야 한다면 한 문장으로:

> **"터미널은 창, 셸은 통역사, 커널은 주방입니다."**

## 🔐 2. SSH (Secure Shell): 남의 식당 주방에 안전하게 들어가는 법

**일상 비유**: 도청당할 수 있는 일반 전화로 주방에 주문하지 않습니다. 양쪽이 **암호 키를 맞춰 본 뒤 전용 비밀 파이프**를 뚫고, 그 파이프로 **먼 서버의 점원(셸)을 내 창구에 직접 불러오는** 기술이 SSH입니다. 기본 출입구는 **22번 포트**입니다.

**기술적 정의**: SSH는 **암호화되지 않은 네트워크를 통해 원격 컴퓨터에 안전하게 접속하기 위한 프로토콜**입니다. 단순히 "암호화한다"가 아니라, 접속 한 번에 네 단계를 순서대로 밟습니다.

### ① 키 교환 (Key Exchange): 이번 대화 전용 열쇠 만들기

TCP 22번으로 연결하면 양쪽이 지원하는 암호화 방식을 협상하고, **Diffie-Hellman 계열(요즘 기본은 `curve25519-sha256`)** 로 **세션마다 새로 쓰는 대칭키**를 만듭니다. 이 키는 네트워크로 전송되지 않고 양쪽에서 각자 계산해 냅니다. 그래서 나중에 대화를 도청당해도 **과거 세션은 복호화할 수 없습니다**(Perfect Forward Secrecy).

### ② 서버 인증: 이 서버가 진짜 그 서버인가

서버는 자기 **호스트 키**로 서명을 보내 자신이 진짜임을 증명합니다. 내 컴퓨터는 그 지문을 `~/.ssh/known_hosts`에 저장해 두고 다음 접속 때 비교합니다. 처음 접속할 때 나오는 이 문구가 바로 이 단계입니다.

```text
The authenticity of host '10.0.1.25' can't be established.
ED25519 key fingerprint is SHA256:...
Are you sure you want to continue connecting (yes/no)?
```

여기서 `yes`를 누르는 건 "이 지문을 신뢰하겠다"는 뜻입니다. **중간자 공격(MITM)** 을 막는 장치이므로, 운영 서버라면 지문을 별도 채널로 확인해야 합니다.

### ③ 사용자 인증: 내가 누구인가

두 가지 방식이 있습니다.

- **비밀번호 인증**: 암호화된 터널 **안에서** 비밀번호를 보냅니다. 도청은 막히지만, **무차별 대입(brute force)** 에 노출되고 자동화에도 불리합니다.
- **공개키 인증(권장)**: 내 컴퓨터에 **개인키**, 서버의 `~/.ssh/authorized_keys`에 **공개키**를 둡니다. 접속할 때 클라이언트가 **개인키로 서명**해 소유를 증명하고, 서버는 등록된 공개키로 그 서명을 검증합니다. **개인키 자체는 네트워크로 나가지 않습니다.**

### ④ 세션 암호화: 이후 모든 통신

협상한 **대칭키**로 전 구간을 암호화(`aes256-gcm`, `chacha20-poly1305`)하고 **무결성(MAC)** 까지 검사합니다. 변조되면 즉시 끊깁니다.

> **비대칭키는 문을 여는 데, 대칭키는 짐을 나르는 데 씁니다.**
> 비대칭키 연산은 느리기 때문에 세션 시작 때 인증·키 교환에만 쓰고, 실제 데이터는 빠른 대칭키로 암호화합니다. TLS도 같은 구조입니다.

### Telnet과 무엇이 다른가

| 항목 | Telnet | SSH |
| --- | --- | --- |
| 기본 포트 | 23 | **22** |
| 전송 내용 | **평문** (아이디·비밀번호 그대로 노출) | 전 구간 암호화 |
| 무결성 검사 | 없음 | 있음 (변조 감지) |
| 서버 신원 확인 | 없음 | 호스트 키로 확인 |
| 현재 용도 | 장비 초기 설정 등 레거시 | 서버 원격 관리의 표준 |

Telnet은 같은 네트워크에서 패킷만 잡아도 계정이 그대로 보입니다. 그래서 **운영 환경에서는 사용하지 않는 것**이 원칙입니다.

### 비밀번호 인증 vs 키 쌍 인증

| 항목 | 비밀번호 인증 | 공개키 인증 |
| --- | --- | --- |
| 서버가 보관하는 것 | 비밀번호 해시 | 공개키 (`authorized_keys`) |
| 네트워크로 오가는 것 | 비밀번호 (암호화 터널 안) | **서명값** (개인키는 로컬에만) |
| 무차별 대입 | 취약 | 사실상 불가능 |
| 자동화·무인 접속 | 어려움 (대화형 입력) | 쉬움 |
| 사고 시 책임 소재 | 공유 비밀번호는 추적 불가 | 키별 발급·회수로 추적 가능 |

### 키 종류: RSA vs Ed25519

- **RSA(2048~4096bit)**: 오래된 장비와의 호환성이 좋아 여전히 널리 쓰입니다.
- **Ed25519**: 키가 짧고(공개키 68자 수준) 서명이 빠르며 보안 강도가 높아 **신규 발급의 기본 권장**입니다.
- 주의: OpenSSH 8.8(2021년)부터 **SHA-1 기반 `ssh-rsa` 서명이 기본 비활성화**되었습니다. "예전에 되던 RSA 키가 갑자기 안 먹는다"는 사고의 대표 원인입니다.

```bash
# 1) 키 쌍 생성 (ed25519 권장)
ssh-keygen -t ed25519 -C "haem@laptop"

# 2) 공개키만 서버에 등록 (개인키 id_ed25519는 절대 공유 금지)
cat ~/.ssh/id_ed25519.pub

# 3) 키로 접속 (클라우드 VM 예시)
ssh -i ~/.ssh/id_ed25519 ec2-user@10.0.1.25
```

점프 서버(Bastion)를 거치는 구성은 `~/.ssh/config`에 적어 두면 명령이 짧아집니다.

```text
Host bastion
  HostName 1.2.3.4
  User ec2-user
  IdentityFile ~/.ssh/id_ed25519

Host app-*
  ProxyJump bastion
  User ec2-user
  IdentityFile ~/.ssh/id_ed25519
```

이제 `ssh app-01`만 쳐도 Bastion을 자동으로 경유합니다.

### 🎤 면접 30초 답변 (SSH)

> "SSH는 암호화되지 않은 네트워크에서 원격 서버의 셸을 안전하게 쓰기 위한 프로토콜이고, 기본 포트는 22번입니다. 접속하면 먼저 키 교환으로 세션마다 새로운 대칭키를 만들고, 서버는 호스트 키로 자신의 신원을 증명해 중간자 공격을 막습니다. 사용자 인증은 비밀번호 대신 공개키 방식을 주로 쓰는데, 클라이언트가 개인키로 서명해 소유를 증명하고 서버는 등록된 공개키로 검증하므로 **개인키 자체는 네트워크로 전송되지 않습니다**. Telnet이 모든 것을 평문으로 보내는 것과 달리 SSH는 인증·암호화·무결성을 모두 제공합니다."

## 📊 3. 한눈에 비교 표

| 구분 | 정체 | 하는 일 | 대표 예시 |
| --- | --- | --- | --- |
| **터미널** | UI 프로그램 | 입력을 받고 출력만 그림 (해석 X) | Terminal.app, iTerm2 |
| **셸** | 명령어 해석기 | 명령 해석 → 실행 → 시스템 콜 | bash, zsh, PowerShell |
| **SSH** | 원격 접속 프로토콜 | 암호화된 원격 셸 세션 | OpenSSH `ssh`, PuTTY |
| **커널** | OS 핵심 | 프로세스·메모리·파일 관리 | Linux kernel, XNU |

어디에 있는지로 보면 더 분명합니다. **터미널과 셸은 내 PC에도, 원격 서버에도** 있습니다(SSH로 붙었을 때 내 창에 뜨는 프롬프트는 **서버 쪽 셸**입니다). **SSH는 그 둘을 잇는 프로토콜**이고, **커널은 서버 OS 안**에서 권한을 검사하며 실제 일을 합니다.

**헷갈릴 때 3문장으로 정리**

1. **터미널**을 열면 그 안에 **셸**이 뜬다. (창 ↔ 프로그램)
2. `ssh server`를 치면 서버의 **셸**이 내 **터미널** 창에 붙는다. (원격 셸 = "Secure Shell"이라는 이름의 이유)
3. 명령은 셸이 해석하고, 실제 실행은 **커널**이 한다. (해석 ↔ 실행)

## 🎯 SA 실무 포인트: 왜 이게 고객 미팅에서 나오는가

**1) 온프레미스·폐쇄망에서는 키 배포가 설계 항목입니다.**
인터넷이 막힌 고객사 망에서는 공개키를 메일로 뿌릴 수도, `ssh-copy-id`를 쓸 수도 없습니다. 그래서 **점프 서버 경유 배포, 오프라인 매체 반입, 발급·회수 절차**를 아키텍처 문서에 넣어야 합니다. "접속이 되게 해 주세요"가 아니라 "누가 어떤 키로 어디까지 들어갈 수 있는가"를 정의하는 일입니다.

**2) 클라우드 VM(EC2, OpenShift 노드)에서 SSH는 최후의 수단입니다.**
노드에 상시 SSH로 들어가는 운영은 감사에서 바로 지적됩니다. 표준 구조는 **22번을 인터넷에 열지 않고**, Bastion(점프 서버)을 통해서만, 또는 **AWS Systems Manager Session Manager**처럼 인바운드 포트 없이 접근하는 방식입니다. 보안 그룹은 `Bastion → 노드`만 허용하고, 나머지는 전부 차단합니다. OpenShift라면 노드 SSH 대신 `oc debug node/<name>` 같은 표준 진단 경로를 먼저 씁니다.

**3) 키 관리가 곧 신원 관리입니다.**
개인키는 **사용자별 발급**, 공유 계정 키 금지, 정기 교체, **퇴사자 키 회수**, 접속·명령 감사 로그(세션 로깅)까지가 한 세트입니다. "누가 언제 들어왔는지 모르는 서버"는 장애 때 원인도, 감사 때 근거도 남기지 못합니다.

**4) 발표 때 자주 나오는 실무 함정 3가지**

| 증상 | 원인 | 조치 |
| --- | --- | --- |
| `WARNING: UNPROTECTED PRIVATE KEY FILE` | 개인키 권한이 너무 열려 있음 | `chmod 600 ~/.ssh/id_ed25519` |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | 서버 재생성 or **중간자 공격 가능성** | 무조건 `known_hosts` 삭제 금지, 지문 먼저 확인 |
| `no mutual signature algorithm` | OpenSSH 8.8+에서 SHA-1 `ssh-rsa` 비활성 | Ed25519 키로 재발급 또는 서버 측 알고리즘 정책 확인 |
