## ⚙️ 1. 프로세스 vs 스레드 · 동시성 vs 병렬성

**일상 비유**: **프로세스는 독립된 사무실**입니다. 각자 문이 있고 서류 캐비닛(메모리)이 따로 있어서, 한 사무실에 불이 나도 옆 사무실은 멀쩡합니다. **스레드는 한 사무실의 직원들**입니다. 같은 캐비닛을 함께 쓰니 대화가 빠르지만, 한 명이 서류를 엉망으로 정리하면 모두가 피해를 봅니다.

**핵심 원리**: 프로세스는 **독립된 주소 공간**을 받고, 스레드는 같은 프로세스의 **힙·코드·파일**을 공유하며 **스택과 레지스터만** 따로 가집니다.

| 구분 | 프로세스 | 스레드 |
| --- | --- | --- |
| 메모리 | 독립 주소 공간 | 힙·코드 공유, 스택만 개별 |
| 생성 비용 | 큼 (새 주소 공간) | 작음 |
| 통신 | IPC(파이프, 소켓, 공유메모리) | 변수 공유 (빠르지만 경쟁) |
| 장애 격리 | 강함 | 약함 (하나 죽으면 전체 위험) |

### 동시성(Concurrency) vs 병렬성(Parallelism)

| 개념 | 뜻 | 비유 |
| --- | --- | --- |
| 동시성 | 여러 일을 **번갈아** 처리해 동시에 진행되는 것처럼 | 한 요리사가 3개 냄비를 번갈아 봄 |
| 병렬성 | 여러 일을 **실제로 같은 순간에** 처리 | 요리사 3명이 각자 냄비 담당 |

**핵심 감각**: 코어가 1개여도 동시성은 가능합니다. 대기는 겹칠 수 있으니까요. **I/O 대기가 많은 작업(LLM API 호출, DB 조회)은 동시성으로 충분**하고, **계산이 많은 작업(임베딩 생성, 이미지 처리)은 병렬성이 필요**합니다.

파이썬이라면 이 감각이 특히 중요합니다. GIL 때문에 CPU 연산은 스레드로 늘지 않으므로, **I/O 대기는 async나 스레드**, **CPU 연산은 멀티프로세스(워커)** 로 나눕니다.

### 🎤 면접 30초 답변

> "프로세스는 독립된 주소 공간을 가진 실행 단위라 장애 격리가 강하고, 스레드는 같은 프로세스의 메모리를 공유하는 실행 단위라 생성이 빠르고 통신이 저렴하지만 하나가 비정상 종료하면 전체에 영향을 줍니다. 동시성은 여러 작업을 번갈아 처리해 동시에 진행되는 것처럼 만드는 것이고, 병렬성은 실제로 여러 코어에서 동시에 실행하는 것입니다. 그래서 I/O 대기가 많은 LLM API 호출이나 DB 조회는 동시성으로 충분하고, 임베딩 생성이나 전처리처럼 CPU를 오래 쓰는 작업은 병렬 처리와 워커 수 조정이 필요합니다."

### 🎯 SA 실무 포인트

**1) "동시 사용자 몇 명"은 스레드 수가 아니라 대기 시간으로 계산합니다.**
리틀의 법칙입니다. **동시 요청 수 ≈ 초당 요청 × 평균 응답 시간(초)**. LLM 응답이 5초이고 초당 4건이면 이미 20개가 동시에 떠 있습니다. 워커 4개로는 부족합니다 — 이 계산을 못 하면 용량 산정이 감이 됩니다.

**2) 워커 수는 코어 수 × (1 + 대기 비율)로 잡습니다.**
I/O 비중이 높으면 워커를 늘리는 게 이득이지만, CPU 사용률이 80%를 넘으면 늘려도 대기만 늘어납니다. 오토스케일링 지표를 CPU만 두면 I/O 바운드 서비스는 영원히 스케일아웃하지 않습니다.

**3) 요청 단위 격리는 비용입니다.**
사용자별로 프로세스를 띄우면 격리는 완벽하지만 메모리가 터집니다. 스레드풀 + 타임아웃 + 큐 길이 제한으로 "느려지되 죽지 않는" 상태를 만드는 것이 실무 해법입니다.

## 🔀 2. 컨텍스트 스위칭: 동시성의 숨은 청구서

**일상 비유**: 한 명의 비서가 세 명의 상사를 번갈아 받습니다. 한 상사 이야기를 하다 다른 상사로 넘어갈 때마다 **어디까지 했는지 메모를 정리하고 다시 펼치는** 시간이 듭니다. 상사가 많아질수록 실제 일하는 시간은 줄어듭니다.

**핵심 원리**: CPU는 한 순간에 한 작업만 실행합니다. 전환할 때 **현재 작업의 레지스터·PC·스택 포인터를 저장하고 다음 작업의 상태를 복원**합니다.

| 전환 종류 | 비용 | 추가 비용 |
| --- | --- | --- |
| 스레드 → 스레드 (같은 프로세스) | 상대적으로 저렴 | 레지스터·스택 교체 |
| 프로세스 → 프로세스 | 더 비쌈 | **주소 공간 전환(TLB flush)** |
| 시스템 콜 | 커널 모드 전환 | 권한 모드 스위치 |
| 인터럽트 | 예측 불가 | 캐시 오염 |

**핵심 감각**: 전환 자체는 마이크로초 단위지만, 진짜 비용은 **캐시가 식는 것**입니다. CPU 캐시에 올려 둔 데이터가 무효화되면 다음 작업이 다시 메모리에서 읽어야 합니다. 그래서 **스레드를 무작정 늘리면 처리량이 오히려 떨어집니다**(스레싱).

### 🎤 면접 30초 답변

> "컨텍스트 스위칭은 실행 중인 작업의 레지스터와 스택 포인터 같은 상태를 저장하고 다음 작업의 상태를 복원하는 과정입니다. 전환 자체도 비용이지만 더 큰 비용은 CPU 캐시가 무효화되는 것이고, 프로세스 간 전환은 주소 공간이 바뀌어 TLB까지 비워야 해서 스레드 전환보다 비쌉니다. 그래서 스레드나 프로세스를 무한정 늘리면 실제 연산보다 전환에 시간을 쓰는 스레싱이 발생합니다. 실무에서는 코어 수와 대기 비율을 고려해 워커 수를 정하고, I/O는 비동기로 처리해 전환 횟수 자체를 줄입니다."

### 🎯 SA 실무 포인트

**1) "파드를 늘렸는데 처리량이 그대로"의 원인입니다.**
노드에 파드가 과밀하면 CPU 스로틀링(throttling)과 전환이 겹칩니다. `requests`를 실제 사용량에 맞게 잡고, 노드당 파드 수 상한을 둡니다. CPU `limits`를 낮게 잡으면 스로틀링으로 p99가 튑니다 — **CPU limit은 신중하게**, memory limit은 반드시.

**2) 노드 사이즈도 전환 비용 문제입니다.**
코어가 많은 큰 노드 하나 vs 작은 노드 여러 개. 큰 노드는 캐시 효율이 좋지만 장애 영향 범위(blast radius)가 큽니다. 32코어 1대보다 8코어 4대가 안전하고, GPU 노드는 반대로 큼이 유리합니다.

**3) LLM 서빙은 배치(batching)로 전환 비용을 상쇄합니다.**
요청을 하나씩 처리하면 GPU가 놉니다. 여러 요청을 묶어 한 번에 처리(continuous batching)하면 처리량이 몇 배로 뜁니다. vLLM 같은 서버가 이걸 자동으로 합니다.

## 🧠 3. 가상 메모리 & OOM: 왜 파드는 항상 죽는가

**일상 비유**: **가상 메모리는 호텔의 룸 넘버**입니다. 투숙객은 자기 방 번호만 알면 되고, 실제로 몇 층 어느 방에 있는지는 프런트(OS)가 압니다. 방이 부족하면 짐을 창고(디스크 스왑)로 옮기고, **창고까지 꽉 차면** 더 이상 받을 수 없어 투숙객을 내보냅니다 — 이게 OOM입니다.

**핵심 원리**: 각 프로세스는 **자기만의 연속된 주소 공간**을 가진 것처럼 보지만, 실제로는 **페이지(page)** 단위로 물리 메모리에 매핑됩니다.

| 개념 | 의미 |
| --- | --- |
| 페이지 테이블 | 가상 주소 → 물리 주소 매핑 |
| 페이지 폴트 | 접근한 페이지가 메모리에 없음 → 디스크에서 로드 |
| 스왑 | 메모리가 부족할 때 디스크로 밀어내기 |
| RSS | 실제로 물리 메모리에 올라간 크기 |
| cgroup limit | 컨테이너에 허용된 메모리 상한 |

**OOMKilled의 정체**: 컨테이너가 cgroup 메모리 limit을 넘으면 **커널이 그 프로세스를 강제 종료**합니다. 쿠버네티스는 이를 `OOMKilled`로 표시하고 **종료 코드 137**(128+9, SIGKILL)로 남깁니다.

```text
Last State: Terminated
  Reason: OOMKilled
  Exit Code: 137
```

### 🎤 면접 30초 답변

> "가상 메모리는 각 프로세스에 독립된 연속 주소 공간을 주고 페이지 테이블로 물리 메모리에 매핑하는 기법입니다. 덕분에 프로세스 간 격리가 되고, 실제 메모리보다 큰 주소 공간을 쓸 수 있습니다. 메모리가 부족하면 덜 쓰는 페이지를 디스크로 내보내는데, 컨테이너 환경에서는 cgroup으로 메모리 상한을 걸기 때문에 그 상한을 넘으면 커널이 프로세스를 강제 종료합니다. 쿠버네티스에서는 이것이 OOMKilled, 종료 코드 137로 나타납니다. 원인은 대개 limit 대비 실제 사용량 급증, 메모리 누수, 또는 캐시를 무제한으로 쌓는 구현입니다."

### 🎯 SA 실무 포인트

**1) OOMKilled를 "메모리 부족"으로만 설명하면 절반입니다.**
limit을 올리면 다음 단계에서 또 죽습니다. ① limit이 실제 피크보다 낮은가 ② 파드가 재시작되며 쌓이는 것 아닌가 ③ JVM·파이썬이 OS에 메모리를 반환하지 않는 구조인가를 순서로 봅니다.

**2) 런타임별 함정이 다릅니다.**

| 런타임 | 흔한 원인 | 대응 |
| --- | --- | --- |
| JVM | 컨테이너 인식 없이 힙을 크게 잡음 | `-XX:MaxRAMPercentage` |
| Python | 객체 해제 후에도 RSS가 안 줄어듦 | 워커 재시작 주기, `MALLOC_ARENA_MAX` |
| Node.js | 기본 힙 상한 초과 | `--max-old-space-size` |
| 벡터 검색 | 인덱스를 메모리에 전부 로드 | mmap, 샤딩, 인덱스 분할 |

**3) RAG 파이프라인은 임베딩 배치에서 터집니다.**
문서 1만 개를 한 번에 임베딩하면 메모리가 순간적으로 치솟습니다. **배치 크기 + 스트리밍 처리 + 체크포인트**를 설계에 넣으면 야간 배치가 새벽에 죽는 사고를 막습니다.

## 🏎️ 4. CPU vs GPU(VRAM) · I/O 바운드 vs CPU 바운드

**일상 비유**: **CPU는 박사급 직원 몇 명**입니다. 복잡한 판단을 순서대로 잘합니다. **GPU는 단순 반복 작업자 수천 명**입니다. 같은 계산을 동시에 하면 압도적으로 빠릅니다. **VRAM은 그 작업자들이 쓰는 작업대 넓이**입니다 — 작업대가 좁으면 재료를 못 올려 일을 못 시작합니다.

**핵심 원리**: CPU는 코어 수가 적고(수십) 복잡한 분기·순차 로직에 강합니다. GPU는 수천 개의 단순 코어로 **행렬 연산(SIMD)** 을 대량 병렬 처리합니다. AI 연산의 대부분이 행렬 곱이라 GPU가 압도적입니다.

| 구분 | CPU | GPU |
| --- | --- | --- |
| 코어 | 수십 개, 복잡 | 수천 개, 단순 |
| 잘하는 일 | 분기·순차 처리, 제어 | 행렬·벡터 병렬 연산 |
| 메모리 | DDR (수십~수백 GB) | **VRAM/HBM (수십~수백 GB, 고대역)** |
| 병목 | 코어 수 | **VRAM 용량과 대역폭** |

**VRAM 감각 (LLM 기준)**: 파라미터 수 × 정밀도 바이트가 기본이고, 여기에 **KV 캐시**(동시 사용자·컨텍스트 길이에 비례)가 더해집니다.

| 모델 규모 | 가중치(fp16) | 실무 감각 |
| --- | --- | --- |
| 7B | 약 14GB | 24GB GPU 1장에 KV 캐시 여유 |
| 13B | 약 26GB | 24GB 1장으로 부족, 양자화 필요 |
| 70B | 약 140GB | 다중 GPU 또는 4bit 양자화 |

**핵심 감각**: LLM 추론은 계산보다 **메모리 대역폭**에 묶이는 경우가 많습니다. "GPU 사용률이 40%인데 느리다"는 대개 연산이 아니라 가중치를 읽어 오는 대역폭이 병목이라는 뜻입니다.

### I/O 바운드 vs CPU 바운드

| 유형 | 특징 | 판별 | 대응 |
| --- | --- | --- | --- |
| CPU 바운드 | CPU 사용률 높음, 대기 적음 | top에서 CPU 100% | 코어 증설, 알고리즘 개선 |
| I/O 바운드 | CPU 낮은데 느림 | 대기·네트워크 지연 큼 | 동시성, 캐시, 배치 |
| 메모리 바운드 | GC·스왑 빈번 | RSS 급증, page fault | 메모리 증설, 구조 개선 |

### 🎤 면접 30초 답변

> "CPU는 코어 수가 적지만 복잡한 분기와 순차 처리를 잘하고, GPU는 수천 개의 단순 코어로 행렬 연산을 대량 병렬 처리합니다. AI 추론은 대부분 행렬 곱이라 GPU가 유리하지만, 병목은 연산량보다 VRAM 용량과 대역폭인 경우가 많습니다. 모델 가중치가 VRAM에 다 올라가야 하고, 동시 사용자가 늘면 KV 캐시가 추가로 필요합니다. 그래서 'GPU 사용률이 낮은데 느리다'는 것은 연산이 아니라 메모리 대역폭 병목일 수 있습니다. I/O 바운드와 CPU 바운드를 구분하는 것도 같은 맥락입니다. 대기가 많으면 동시성과 캐시로, 연산이 많으면 병렬화와 하드웨어 증설로 대응합니다."

### 🎯 SA 실무 포인트

**1) "GPU가 필요한가"를 먼저 반증하세요.**
분류·요약·RAG 답변 생성은 대부분 **API 호출**로 충분합니다. GPU는 ① 파인튜닝 ② 대량 임베딩 ③ 온프레미스/폐쇄망 추론 ④ 지연이 극도로 중요한 경우에만 정당화됩니다. GPU 1장의 월 비용은 API 사용료보다 훨씬 큽니다.

**2) 온프레미스 GPU는 TCO가 아니라 "가동률"로 설계합니다.**
GPU를 사면 24시간 감가상각이 돕니다. API는 쓴 만큼만 냅니다. 사용률이 20% 아래라면 GPU 구매가 거의 항상 손해이고, 이 계산을 표로 보여주는 것이 SA의 몫입니다.

**3) VRAM 산정은 동시 사용자까지 넣어야 맞습니다.**
가중치만 계산하면 "들어가는데 왜 느리고 끊기죠"가 됩니다. **동시 요청 수 × 평균 컨텍스트 길이 × KV 캐시 크기**를 더해 여유율 30%를 얹습니다. 이 숫자가 제안서의 "동시 사용자 N명" 근거가 됩니다.

## 📦 5. VM vs 컨테이너(Docker) vs 베어메탈(BM)

**일상 비유**: **베어메탈은 단독 주택**, **VM은 각 세대에 보일러·주방이 따로 있는 아파트**, **컨테이너는 주방은 공유하되 방은 따로 쓰는 셰어하우스**입니다. 단독주택은 자유롭지만 비싸고, 아파트는 세대별 설비(게스트 OS) 때문에 무겁고, 셰어하우스는 가볍지만 주방(커널) 문제가 생기면 다 같이 영향받습니다.

**핵심 원리**: VM은 **하이퍼바이저** 위에 **게스트 OS를 통째로** 띄웁니다. 컨테이너는 리눅스 커널의 **namespace(격리)** 와 **cgroup(자원 제한)** 으로 프로세스를 격리하고, **이미지 레이어**로 배포합니다.

| 구분 | 베어메탈 | VM | 컨테이너 |
| --- | --- | --- | --- |
| 격리 수준 | 물리 | 강함 (자체 커널) | 중간 (커널 공유) |
| 기동 시간 | 수십 분 | 수십 초~분 | **수백 ms~수 초** |
| 밀도 | 1 | 낮음 | 높음 |
| 쓰는 자리 | GPU, 고성능 DB, 라이선스 | 강한 격리, 이기종 OS | 마이크로서비스, 배포 단위 |

**핵심 감각**: 컨테이너는 "가벼운 VM"이 아닙니다. **커널을 공유**하기 때문에 커널 취약점 하나가 전체에 영향을 줄 수 있습니다. 그래서 멀티테넌트 격리가 중요한 경우(gVisor, Kata)나 규제 환경에서는 VM 경계를 다시 도입합니다.

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### 🎤 면접 30초 답변

> "VM은 하이퍼바이저 위에 게스트 OS를 통째로 올려 강한 격리를 제공하지만 무겁고 기동이 느립니다. 컨테이너는 커널을 공유하고 namespace로 격리, cgroup으로 자원을 제한하기 때문에 기동이 수백 밀리초 수준이고 밀도가 높습니다. 대신 커널을 공유하므로 격리 강도가 VM보다 약하고, 커널 취약점의 영향 범위가 넓습니다. 그래서 마이크로서비스와 배포 단위는 컨테이너로, 강한 격리가 필요한 멀티테넌트나 GPU·고성능 DB는 VM이나 베어메탈로 구성하는 것이 일반적입니다."

### 🎯 SA 실무 포인트

**1) 이미지가 곧 배포 계약입니다.**
"내 PC에서는 되는데"를 없애는 것이 컨테이너의 원래 목적입니다. 태그에 `latest`를 쓰지 말고 **커밋 해시·버전 태그**를 쓰세요. 롤백이 태그 하나로 가능해집니다.

**2) 이미지 크기가 기동 시간과 보안 스캔 시간을 결정합니다.**
`slim`/`alpine` 베이스, 멀티스테이지 빌드, `.dockerignore`로 빌드 컨텍스트 축소. 이미지가 1GB를 넘으면 콜드 스타트와 스캔이 모두 느려집니다. **비밀 파일이 이미지 레이어에 남는 사고**도 여기서 막습니다.

**3) 온프레미스 고객사는 컨테이너를 "허용"하지 않는 경우가 있습니다.**
"우리는 root 권한 컨테이너 금지", "이미지는 우리 레지스트리에서만" 같은 정책이 흔합니다. 비루트 실행, 읽기 전용 루트 파일시스템, 내부 레지스트리 미러링을 **미리 제안서에 넣어 두면** 보안 심사에서 되돌아오지 않습니다.

## ☸️ 6. 쿠버네티스 핵심: Pod · Service · Ingress · HPA

**일상 비유**: **Pod는 한 팀이 쓰는 사무실**, **Service는 대표 전화번호**, **Ingress는 건물 정문 안내데스크**, **HPA는 직원을 늘리고 줄이는 인사팀**입니다. 손님은 대표번호(Service)만 알면 되고, 직원이 바뀌어도(파드 재생성) 번호는 그대로입니다.

**핵심 원리**: 쿠버네티스는 **선언적 상태 관리**입니다. "파드 3개를 유지하라"고 선언하면 컨트롤러가 실제 상태를 맞춥니다.

| 오브젝트 | 역할 | 핵심 포인트 |
| --- | --- | --- |
| Pod | 최소 배포 단위 (1개 이상 컨테이너) | 같은 네트워크·볼륨 공유, 사이드카 패턴 |
| Deployment | 파드 복제·롤링 업데이트 | ReplicaSet을 관리, 롤백 지원 |
| Service | 파드 집합의 고정 접근점 | ClusterIP / NodePort / LoadBalancer |
| Ingress | L7 라우팅 (경로·호스트) | TLS 종료, ingress controller 필요 |
| HPA | 부하에 따른 파드 수 조절 | metrics-server, 목표 사용률 기반 |

**요청과 한도의 차이**는 반드시 구분해야 합니다.

| 항목 | 의미 | 잘못 잡으면 |
| --- | --- | --- |
| requests | 스케줄링 기준 예약량 | 과대: 노드 낭비 / 과소: 과밀 |
| limits (memory) | 초과 시 **OOMKilled** | 과소: 반복 재시작 |
| limits (CPU) | 초과 시 **스로틀링** | 과소: p99 지연 급등 |

**프로브 3종**: `liveness`(죽으면 재시작), `readiness`(준비 안 되면 트래픽 차단), `startup`(초기 기동이 느린 앱 보호). LLM 서버는 모델 로딩에 수십 초가 걸리므로 **startupProbe 없이 livenessProbe만 두면 무한 재시작**에 빠집니다.

```yaml
resources:
  requests: { cpu: "1", memory: "2Gi" }
  limits:   { memory: "3Gi" }      # CPU limit은 신중히
startupProbe:
  httpGet: { path: /healthz, port: 8000 }
  failureThreshold: 30
  periodSeconds: 5
```

### 🎤 면접 30초 답변

> "쿠버네티스에서 Pod는 컨테이너를 감싼 최소 배포 단위로 네트워크와 볼륨을 공유하고, Deployment가 파드 수와 롤링 업데이트를 관리합니다. Pod는 재생성되면 IP가 바뀌기 때문에 Service가 고정 접근점을 제공하고, Ingress가 호스트·경로 기반 L7 라우팅과 TLS 종료를 담당합니다. HPA는 metrics-server가 수집한 CPU·메모리 같은 지표를 목표 사용률과 비교해 파드 수를 조정합니다. 운영에서 중요한 것은 requests와 limits 구분입니다. requests는 스케줄링 예약량, memory limit은 초과 시 OOMKilled, CPU limit은 스로틀링으로 이어지므로, 모델 로딩이 느린 서버에는 startupProbe를 두어야 무한 재시작을 막을 수 있습니다."

### 🎯 SA 실무 포인트

**1) 프로브 설정 실수가 장애의 절반입니다.**
readiness가 없으면 기동 중인 파드로 트래픽이 가 502가 납니다. liveness 임계값이 너무 짧으면 GC로 잠깐 멈춘 파드가 죽습니다. **"startup 길게, liveness 느슨하게, readiness 엄격하게"** 가 원칙입니다.

**2) GPU 노드는 오토스케일링이 다릅니다.**
GPU는 1장 단위로만 할당되고, 노드 프로비저닝에 수 분이 걸립니다. HPA만으로는 급증에 대응이 안 되므로 ① 노드 오토스케일러(cluster autoscaler/Karpenter) ② 최소 노드 유지 ③ 큐 기반 스케일링(KEDA)을 함께 설계합니다.

**3) 멀티테넌트는 namespace + ResourceQuota로 시작하세요.**
한 팀이 GPU를 다 잡아먹는 사고를 막으려면 namespace별 Quota와 LimitRange가 필요합니다. "공용 클러스터"를 제안할 때 이 두 개가 없으면 첫 달에 분쟁이 납니다.

## ⚡ 7. 서버리스 vs 상시 구동 · Cold Start

**일상 비유**: **상시 구동은 24시간 문 연 매장**입니다. 손님이 언제 와도 바로 응대하지만 임대료는 항상 나갑니다. **서버리스는 요청이 오면 출근하는 직원**입니다. 놀 때는 인건비가 0이지만, 호출하면 **출근 준비 시간(Cold Start)** 이 붙습니다.

**핵심 원리**: 서버리스(FaaS)는 요청이 있을 때만 실행 환경을 만들고, 유휴 시 0으로 줄입니다. 대신 ① 콜드 스타트 ② 실행 시간 제한 ③ 상태 없음(stateless) ④ 연결 재사용 불가라는 제약이 따릅니다.

| 구분 | 상시 구동 (컨테이너/VM) | 서버리스 (Lambda, Cloud Run) |
| --- | --- | --- |
| 유휴 비용 | 계속 과금 | 0에 가까움 |
| 첫 응답 | 빠름 | 콜드 스타트 지연 |
| 실행 시간 | 제한 없음 | 최대 15분 (Lambda) |
| 연결 | 커넥션 풀 재사용 | 인스턴스마다 새 연결 |
| 잘 맞는 일 | API 서버, 스트리밍, DB 연결 | 이벤트 처리, 배치, 웹훅 |

**콜드 스타트의 실제 구성**: ① 런타임 초기화 ② 의존성 로딩 ③ 애플리케이션 초기화 ④ (LLM이면) **모델 로딩**. 앞의 셋은 수백 ms지만 모델 로딩은 수십 초입니다.

| 완화책 | 효과 | 비용 |
| --- | --- | --- |
| Provisioned Concurrency | 콜드 스타트 제거 | 유휴에도 과금 |
| 패키지 축소·레이어 분리 | 초기화 단축 | 빌드 관리 |
| 초기화 코드 최소화 | 즉시 효과 | 설계 변경 |
| 워밍 스케줄 | 완화만 | 부분적 |

### 🎤 면접 30초 답변

> "서버리스는 요청이 있을 때만 실행 환경을 만들고 유휴 시 자원을 0으로 줄이는 모델이라 비용 효율이 좋지만, 첫 요청에 콜드 스타트 지연이 붙고 실행 시간과 상태 유지에 제약이 있습니다. 상시 구동 컨테이너는 유휴에도 비용이 나가지만 첫 응답이 빠르고 커넥션 풀을 재사용할 수 있습니다. 그래서 이벤트 처리·배치·웹훅은 서버리스가, 사용자 응답이 중요한 API와 스트리밍, DB 연결이 많은 서비스는 상시 구동이 적합합니다. LLM 서비스는 모델 로딩 때문에 콜드 스타트가 수십 초가 될 수 있어 서버리스에 그대로 올리기 어렵습니다."

### 🎯 SA 실무 포인트

**1) 서버리스 + DB 조합은 커넥션 폭발을 부릅니다.**
인스턴스가 수백 개로 늘면 각각이 DB 연결을 잡아 `max_connections`를 초과합니다. **RDS Proxy·PgBouncer 같은 풀러**를 반드시 함께 설계합니다.

**2) API 게이트웨이 타임아웃을 확인하세요.**
API Gateway의 통합 타임아웃은 최대 29초입니다. LLM 응답이 그보다 길면 잘립니다. 스트리밍 응답이나 비동기(작업 ID 발급 → 폴링) 패턴으로 우회합니다.

**3) 비용은 호출 수가 아니라 "호출 수 × 실행 시간 × 메모리"입니다.**
메모리를 2배로 늘리면 빨라져서 총비용이 줄어드는 경우가 흔합니다. 기본 설정(128MB)으로 두면 오히려 비쌉니다 — 이 계산을 해 주는 것이 SA의 부가가치입니다.

## 🏗️ 8. IaC(Terraform) & CI/CD: 손으로 만든 인프라는 재현되지 않는다

**일상 비유**: **IaC는 인테리어 도면**입니다. 말로 "벽 좀 세워 주세요"라고 하면 다음에 같은 집을 못 짓습니다. 도면이 있으면 같은 집을 몇 번이든, 다른 사람이 지어도 똑같이 짓습니다. **CI/CD는 자동 검수·시공 라인**입니다. 도면이 바뀌면 검사하고, 통과하면 자동으로 짓습니다.

**핵심 원리**: IaC는 인프라를 **코드로 선언**하고, 도구가 실제 상태와 비교해 차이만 적용합니다.

| 도구 | 방식 | 특징 |
| --- | --- | --- |
| Terraform | 선언형, plan/apply | 멀티 클라우드, 상태 파일 관리 |
| CloudFormation | 선언형 (AWS 전용) | 관리형, 롤백 내장 |
| Ansible | 절차형 (서버 구성) | 에이전트리스, 구성 관리 |
| Helm/ArgoCD | 쿠버네티스 매니페스트·GitOps | 클러스터 상태를 Git에 |

**핵심 함정 — 상태 파일(state)**: Terraform은 "무엇이 존재하는가"를 **state**에 기록합니다. 이 파일이 없으면 실제 리소스를 못 찾고, 두 사람이 동시에 apply하면 리소스가 깨집니다. 그래서 **원격 상태 저장소 + 잠금(lock)** 이 필수입니다.

```hcl
terraform {
  backend "s3" {
    bucket         = "company-tfstate"
    key            = "ai-platform/network.tfstate"
    region         = "ap-northeast-2"
    dynamodb_table = "tf-lock"
    encrypt        = true
  }
}
```

**CI/CD 최소 파이프라인**: 코드 푸시 → 빌드 → 테스트 → 이미지 스캔 → 스테이징 배포 → 승인 → 프로덕션. 여기에 **`terraform plan` 결과를 PR에 코멘트로 붙이는 것**만으로도 인프라 변경 사고가 크게 줄어듭니다.

### 🎤 면접 30초 답변

> "IaC는 인프라를 코드로 선언해 재현 가능하고 리뷰 가능한 형태로 관리하는 방식입니다. Terraform은 선언형으로 원하는 상태를 적으면 현재 상태와 비교해 차이만 적용하고, 이때 상태 파일이 기준이 되기 때문에 원격 저장소와 잠금을 반드시 써야 합니다. CI/CD는 빌드·테스트·스캔·배포를 자동화한 파이프라인으로, 인프라 변경도 같은 파이프라인을 통과시켜 리뷰와 승인 없이는 반영되지 않게 합니다. 결과적으로 환경 차이(drift)를 줄이고 롤백과 감사를 가능하게 하는 것이 핵심입니다."

### 🎯 SA 실무 포인트

**1) 고객사가 가장 좋아하는 산출물이 IaC입니다.**
"이 아키텍처를 우리가 운영할 수 있나"라는 질문에 Terraform 모듈과 배포 파이프라인을 보여주면 신뢰가 달라집니다. 그림만 있는 제안서보다 **재현 가능한 코드**가 설득력이 큽니다.

**2) 환경 분리는 디렉터리·워크스페이스로 명확히.**
dev/stg/prod 상태를 한 파일에 섞으면 사고 시 복구가 불가능합니다. 환경별 backend 키를 분리하고, prod는 **수동 승인**을 넣습니다.

**3) drift를 감시하세요.**
콘솔에서 급하게 고친 리소스는 코드에 없습니다. 정기적으로 `terraform plan`을 돌려 **"코드에 없는 변경"** 을 감지하면, 장애 때 "누가 왜 바꿨는지"를 찾는 시간이 줄어듭니다.
