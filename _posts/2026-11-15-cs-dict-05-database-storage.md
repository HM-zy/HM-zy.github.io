RAG 시스템을 설계하면서 가장 많이 바뀌는 결정이 **데이터 저장소**입니다.

*"문서 원본은 어디에 두고, 임베딩은 어디에 넣고, 권한 정보는 어디에 두죠?"*

이 질문은 하나의 DB로 답할 수 없습니다. 보통 **오브젝트 스토리지(S3) + 관계형 DB(메타데이터·권한) + 벡터 DB(임베딩)** 세 개가 함께 갑니다. SA 면접에서는 "왜 그 저장소를 골랐나"와 "규모가 10배가 되면 무엇이 먼저 깨지나"를 봅니다.

이 글의 6개 묶음입니다.

1. **RDB vs NoSQL vs 벡터 DB(HNSW)** — 무엇을 저장하고 어떻게 찾을 것인가
2. **인덱스(B-Tree) · 트랜잭션(ACID)** — 빠르게 찾고, 안전하게 바꾸기
3. **레플리케이션(Read Replica) vs 샤딩(Sharding)** — 읽기 확장과 쓰기 확장
4. **커넥션 풀(Connection Pool)** — DB가 죽는 가장 흔한 이유
5. **CAP 이론 & 최종 일관성** — 분산의 근본 제약
6. **블록 · 파일 · 오브젝트 스토리지(S3)** — 파일은 어디에 두는가

## 🗄️ 1. RDB vs NoSQL vs 벡터 DB

**일상 비유**: 세 저장소는 세 종류의 **서류 보관 방식**입니다.

- **RDB는 엑셀 표**입니다. 열(스키마)이 정해져 있고, 다른 표와 연결(VLOOKUP·관계)해 정확한 답을 냅니다.
- **NoSQL은 서류 봉투**입니다. 봉투마다 내용이 달라도 되고, 필요한 봉투만 빠르게 꺼냅니다.
- **벡터 DB는 "비슷한 냄새 지도"** 입니다. 정확한 단어가 아니라 **의미가 가까운 것**을 찾습니다.

**핵심 원리**:

| 구분 | 구조 | 강점 | 약점 |
| --- | --- | --- | --- |
| RDB | 테이블·스키마·JOIN | 정합성, 복잡한 질의 | 수평 확장 어려움 |
| Key-Value | 키 → 값 | 초고속 단건 조회 | 질의·분석 제한 |
| Document | JSON 문서 | 유연한 스키마 | 조인·중복 관리 |
| Vector | 고차원 벡터 + ANN 인덱스 | 의미 검색 | 정확 일치·집계 약함 |

**벡터 DB의 핵심 — HNSW 인덱스**

임베딩은 수백~수천 차원의 벡터입니다. 전부 비교하면(정확 검색) 데이터가 늘수록 선형으로 느려집니다. 그래서 **근사 최근접 이웃(ANN)** 을 씁니다.

**HNSW(Hierarchical Navigable Small World)** 는 벡터들을 **층이 있는 그래프**로 연결합니다.

```text
3층:  ●───────────●        (아주 성긴 연결, 큰 점프)
2층:  ●───●───●───●        (중간 밀도)
1층:  ●─●─●─●─●─●─●        (촘촘, 실제 이웃)
```

검색은 위층에서 시작해 **가까운 이웃으로 점프**하며 내려옵니다. 지도에서 "이 동네 → 이 블록 → 이 골목"으로 좁히는 방식입니다. 그래서 전체를 비교하지 않고도 가까운 이웃을 찾습니다.

| 파라미터 | 의미 | 영향 |
| --- | --- | --- |
| M | 노드당 연결 수 | 크면 정확·느림, 메모리 증가 |
| efConstruction | 인덱스 구축 시 탐색 폭 | 크면 품질↑, 구축 느림 |
| efSearch | 검색 시 탐색 폭 | 크면 재현율↑, 지연↑ |

**핵심 감각**: ANN은 **틀릴 수 있는 검색**입니다. 재현율(recall)과 지연의 트레이드오프를 반드시 측정해야 하고, "정확히 이 문서를 찾아야 한다"는 요구(사번·계약번호)는 **키워드 검색(BM25)이나 SQL**로 처리해야 합니다.

### 🎤 면접 30초 답변

> "RDB는 스키마와 트랜잭션, 조인으로 정합성이 중요한 업무 데이터에 적합하고, NoSQL은 유연한 스키마와 수평 확장이 필요한 대량 데이터에 적합합니다. 벡터 DB는 임베딩을 저장하고 의미 기반 유사도 검색을 하는데, 정확 검색은 데이터가 늘면 선형으로 느려지므로 HNSW 같은 근사 인덱스를 씁니다. HNSW는 벡터를 여러 층의 그래프로 연결해 위층에서 큰 점프로 후보를 좁히고 아래층에서 정밀하게 찾는 구조입니다. 다만 근사 검색이라 재현율과 지연의 트레이드오프가 있고, 정확 일치가 필요한 검색은 키워드나 SQL로 병행해야 합니다."

### 🎯 SA 실무 포인트

**1) 벡터 DB는 만능이 아닙니다 — 하이브리드가 정답입니다.**
사번·모델명·오류코드 같은 정확 일치 질문은 벡터 검색이 놓칩니다. **BM25 + 벡터 + RRF 결합**이 표준이고, 필터(부서·권한·날짜)는 **검색 전에** 적용해야 합니다.

**2) "벡터 DB를 새로 도입"은 조달 저항을 만납니다.**
이미 PostgreSQL이 있으면 **pgvector**로 시작할 수 있습니다. 새 제품 도입은 보안 심사·운영 교육·백업 정책이 따라붙습니다. 규모가 커지면 전용 DB로 이전하는 단계적 로드맵이 설득력이 큽니다.

**3) 저장소 3분할을 그림으로 보여주세요.**

| 데이터 | 저장소 | 이유 |
| --- | --- | --- |
| 원문 문서(PDF 등) | 오브젝트 스토리지 | 대용량, 불변, 저비용 |
| 메타데이터·권한 | RDB | 정합성, 조인, 트랜잭션 |
| 임베딩·청크 | 벡터 DB | 유사도 검색 |

이 표 한 장이 "아키텍처를 이해하고 있다"는 인상을 만듭니다.

## 🌳 2. 인덱스(B-Tree) · 트랜잭션(ACID)

**일상 비유**: **인덱스는 책 뒤의 찾아보기**입니다. 500페이지를 다 넘기는 대신 "키워드 → 페이지" 표를 봅니다. 대신 찾아보기를 만들고 유지하는 비용이 들고, 내용을 고칠 때마다 찾아보기도 고쳐야 합니다. **트랜잭션은 은행 송금**입니다. 내 계좌에서 빠지고 상대 계좌에 들어가는 두 동작이 **둘 다 되거나 둘 다 안 되거나** 해야 합니다.

**핵심 원리**: 대부분의 RDB 인덱스는 **B-Tree(정확히는 B+Tree)** 입니다. 루트 → 중간 → 리프로 내려가며 범위를 절반씩 줄이므로 **O(log n)** 입니다.

```text
            [ 50 ]
          /        \
     [20,35]       [70,85]
     /  |  \       /  |  \
  리프 리프 리프  리프 리프 리프   ← 실제 데이터 위치
```

| 인덱스 개념 | 의미 | 주의 |
| --- | --- | --- |
| 복합 인덱스 | 여러 컬럼 조합 | **왼쪽 컬럼부터** 써야 탐 |
| 커버링 인덱스 | 인덱스만으로 응답 | 테이블 접근 제거 |
| 선택도 | 값의 다양성 | 낮으면 인덱스 무의미 |
| 부분 인덱스 | 조건부 인덱스 | 로그·삭제 플래그에 유용 |

**핵심 감각**: 인덱스는 **읽기를 빠르게, 쓰기를 느리게** 합니다. INSERT/UPDATE마다 인덱스도 갱신되기 때문입니다. "인덱스를 다 걸면 좋다"는 틀렸고, **"자주 필터·정렬되는 컬럼에 최소한"** 이 맞습니다.

### ACID

| 속성 | 의미 | 예 |
| --- | --- | --- |
| Atomicity | 전부 또는 전무 | 송금 2단계 중 하나만 반영 안 됨 |
| Consistency | 제약을 항상 만족 | 잔액이 음수 불가 |
| Isolation | 동시 트랜잭션 격리 | 중간 상태를 못 봄 |
| Durability | 커밋은 유지 | 장애 후에도 남음 |

**격리 수준**은 성능과 정합성의 맞교환입니다.

| 수준 | 막는 것 | 남는 문제 |
| --- | --- | --- |
| Read Committed | 더티 리드 | 반복 읽기 불일치 |
| Repeatable Read | 반복 읽기 불일치 | 팬텀 리드(구현차) |
| Serializable | 전부 | 동시성 저하 |

**분산 환경에서는 ACID가 깨집니다.** 여러 서비스·DB에 걸친 작업은 **SAGA 패턴**(단계별 보상 트랜잭션)으로 처리합니다. 예: 주문 생성 → 결제 → 재고 차감, 실패 시 역순 보상.

### 🎤 면접 30초 답변

> "인덱스는 검색 대상 컬럼에 대해 정렬된 보조 구조를 만들어 탐색을 O(log n)으로 줄이는 기법이고, 대부분 B-Tree 기반이라 범위 검색에도 강합니다. 대신 쓰기마다 인덱스도 갱신해야 해서 쓰기 비용이 늘고 저장 공간을 씁니다. 복합 인덱스는 왼쪽 컬럼부터 조건에 써야 탐색되고, 인덱스 컬럼만으로 응답하는 커버링 인덱스는 테이블 접근을 없앱니다. 트랜잭션은 ACID로 원자성·일관성·격리성·지속성을 보장하고, 격리 수준이 높을수록 정합성은 좋아지지만 동시성이 떨어집니다. 서비스가 여러 DB에 걸치면 단일 트랜잭션이 불가능해 SAGA 같은 보상 패턴을 씁니다."

### 🎯 SA 실무 포인트

**1) 느린 쿼리는 인덱스보다 "쿼리 모양" 문제인 경우가 많습니다.**
함수로 감싼 컬럼(`WHERE date(created_at) = ...`), 앞에 `%`가 붙은 LIKE, 타입 불일치는 인덱스를 못 씁니다. 실행 계획(`EXPLAIN`)을 읽는 습관이 진단 속도를 바꿉니다.

**2) 벡터 검색에도 필터 인덱스가 필요합니다.**
권한·부서 조건을 붙이는데 메타데이터 인덱스가 없으면 **검색 후 필터**로 떨어져 결과가 비어 버립니다. 파티셔닝된 벡터 인덱스나 사전 필터 가능한 구조를 확인해야 합니다.

**3) 정합성 요구를 문서에 명시하세요.**
"AI 답변에 쓰이는 문서 목록"은 약간 낡아도 되지만, **"삭제된 문서가 검색되면 안 된다"** 는 강한 요구입니다. 삭제 전파 지연(SLA)을 숫자로 합의해 두면 나중에 문제가 되지 않습니다.

## 🔀 3. 레플리케이션(Read Replica) vs 샤딩(Sharding)

**일상 비유**: **레플리케이션은 교과서 복사본**을 여러 개 두는 것입니다. 읽는 사람이 많아도 원본 한 권에 몰리지 않습니다. 대신 복사본은 **조금 낡을 수 있습니다**. **샤딩은 백과사전을 ㄱㄴㄷ·ㄹㅁㅂ·ㅅㅇㅈ으로 나눠 다른 책장에 두는 것**입니다. 한 권에 담을 수 없을 만큼 커졌을 때 나눕니다.

**핵심 원리**:

| 구분 | 레플리케이션 | 샤딩 |
| --- | --- | --- |
| 목적 | **읽기 확장**, 가용성 | **쓰기·저장 확장** |
| 데이터 | 전부 복제 | 키 기준 분할 |
| 복잡도 | 상대적으로 낮음 | 높음(샤드 키·재분배) |
| 문제 | 복제 지연(lag) | 핫 샤드, 리샤딩 |

**복제 방식**: 비동기 복제는 빠르지만 **복제 지연**으로 방금 쓴 데이터가 안 보일 수 있습니다. 동기 복제는 정합성이 좋지만 쓰기 지연이 늘고, 장애 시 대기합니다.

**샤드 키 선택**이 샤딩의 성패를 가릅니다.

| 샤드 키 | 문제 |
| --- | --- |
| 고객 ID | 대형 고객 하나가 한 샤드에 몰림(핫 샤드) |
| 날짜 | 최신 샤드에만 쓰기가 몰림 |
| 해시(사용자ID) | 균등 분산, 범위 조회는 어려움 |

**핵심 감각**: 샤딩은 **마지막 수단**입니다. 앱 코드가 샤드 인식, 크로스 샤드 조인 불가, 재분배 마이그레이션까지 따라옵니다. 순서는 ① 인덱스·쿼리 최적화 → ② 캐시 → ③ 읽기 복제 → ④ 파티셔닝 → ⑤ 샤딩입니다.

### 🎤 면접 30초 답변

> "레플리케이션은 같은 데이터를 여러 노드에 복제해서 읽기 요청을 분산하고 장애 시 대체하는 방식이고, 쓰기는 여전히 원본(프라이머리)으로 가기 때문에 쓰기 확장은 되지 않습니다. 비동기 복제를 쓰면 복제 지연 때문에 방금 쓴 데이터가 읽기 복제본에서 안 보일 수 있어, 읽기 일관성이 필요한 요청은 프라이머리로 보내야 합니다. 샤딩은 데이터를 키 기준으로 나눠 서로 다른 노드에 두는 방식이라 쓰기와 저장 용량을 확장할 수 있지만, 샤드 키 선택에 따라 핫 샤드가 생기고 크로스 샤드 조인과 재분배 비용이 큽니다. 그래서 인덱스·캐시·복제로 해결되지 않을 때 마지막 수단으로 도입합니다."

### 🎯 SA 실무 포인트

**1) 읽기 복제본을 붙이면 "내가 방금 쓴 글이 안 보인다" 문의가 옵니다.**
쓰기 직후 조회는 **프라이머리로 라우팅**하거나, 세션에 "최신 읽기" 플래그를 두는 패턴이 필요합니다. 이걸 모르면 "버그입니다"로 이슈가 올라옵니다.

**2) RAG는 읽기 폭이 압도적입니다 — 하지만 병목은 벡터 인덱스입니다.**
문서 조회는 캐시·복제로 늘릴 수 있지만, 임베딩 인덱스는 메모리 상주·재구축 비용이 큽니다. **인덱스 스냅샷·증분 인덱싱·샤드 단위 재구축** 계획을 아키텍처에 포함합니다.

**3) 장애 조치(failover) 시나리오를 문서화하세요.**
프라이머리가 죽으면 누가 승격하나, 애플리케이션 연결 문자열은 어떻게 바뀌나, 데이터 유실은 얼마나 되나(RPO). 이 세 질문에 답이 없으면 운영 단계에서 사고가 납니다.

## 🔌 4. 커넥션 풀(Connection Pool)

**일상 비유**: **커넥션 풀은 식당의 테이블**입니다. 손님마다 새 테이블을 만들지 않고, 정해진 테이블을 돌려 씁니다. 테이블이 20개인데 손님이 500명이면, 480명은 **문 앞에서 기다리다 돌아갑니다**. 문제는 테이블을 늘리는 게 아니라 **손님이 머무는 시간**인 경우가 많습니다.

**핵심 원리**: DB 연결 하나를 맺는 비용은 생각보다 큽니다 — TCP handshake + 인증 + (TLS면) 핸드셰이크 + 세션 초기화. 요청마다 새로 맺으면 이 비용이 매번 붙습니다. 그래서 **미리 N개를 열어 두고 재사용**합니다.

| 개념 | 의미 | 흔한 오해 |
| --- | --- | --- |
| 풀 크기 | 동시에 유지할 연결 수 | 클수록 좋다? **아니오** |
| 대기 시간 | 풀 고갈 시 큐에서 대기 | 타임아웃 필수 |
| 유휴 회수 | 오래 놀면 닫음 | DB의 유휴 타임아웃보다 짧게 |
| 검증 | 연결 살아있는지 확인 | 죽은 연결 반환 사고 |

**DB가 감당할 수 있는 연결 수는 생각보다 적습니다.** PostgreSQL은 연결마다 프로세스가 붙어(기본) 수백 개에서 메모리가 터집니다. MySQL도 `max_connections`를 넘으면 새 연결을 거부합니다.

**핵심 감각 — 풀 크기 공식**: 대략 **연결 수 ≈ (코어 수 × 2) + 유효 디스크 수**. 풀을 키우면 DB에서 경쟁이 늘어 **처리량이 오히려 떨어집니다**. "커넥션 타임아웃" 장애의 해법은 대개 풀 확대가 아니라 **느린 쿼리 제거와 트랜잭션 길이 단축**입니다.

**서버리스의 함정**: 인스턴스가 100개로 늘면 각각이 풀을 만들려 합니다. 100 × 10 = 1,000 연결 → DB 한계 초과. 해법은 **외부 풀러(PgBouncer, RDS Proxy)** 로 DB 앞에서 연결을 공유하는 것입니다.

### 🎤 면접 30초 답변

> "커넥션 풀은 DB 연결을 미리 만들어 재사용하는 구조입니다. 연결 하나를 맺는 데 TCP·인증·세션 초기화 비용이 들기 때문에 요청마다 새로 맺으면 지연과 DB 부하가 커집니다. 풀 크기는 무작정 키우면 안 됩니다. DB는 연결마다 자원을 쓰기 때문에 연결이 너무 많으면 컨텍스트 스위칭과 락 경쟁으로 처리량이 오히려 떨어집니다. 그래서 코어 수와 디스크 수를 기준으로 작게 잡고, 트랜잭션을 짧게 유지하는 것이 정석입니다. 서버리스 환경에서는 인스턴스마다 풀이 생겨 연결이 폭발하므로 PgBouncer나 RDS Proxy처럼 외부에서 연결을 공유하는 구조가 필요합니다."

### 🎯 SA 실무 포인트

**1) "DB 연결 초과" 장애의 실제 순서는 이렇습니다.**
① 느린 쿼리로 연결 점유 시간 증가 → ② 풀 고갈 → ③ 대기 타임아웃 → ④ 5xx 폭증. 풀만 늘리면 ②가 잠깐 늦춰질 뿐 ④는 다시 옵니다. **원인은 ①**입니다.

**2) AI 서비스는 "긴 트랜잭션"을 만들기 쉽습니다.**
LLM 호출을 트랜잭션 안에서 하면 수 초~수십 초 연결을 붙잡습니다. **LLM 호출은 트랜잭션 밖으로** 빼는 것이 원칙입니다. 이건 코드 리뷰 체크리스트에 넣을 만한 항목입니다.

**3) 풀 크기·타임아웃은 설정 파일이 아니라 설계 문서에 적습니다.**
"최대 연결 40, 대기 3초, 유휴 회수 5분"처럼 숫자를 남겨야 용량 산정 근거가 되고, 다른 팀이 같은 실수를 반복하지 않습니다.

## ⚖️ 5. CAP 이론 & 최종 일관성(Eventual Consistency)

**일상 비유**: 은행 지점이 두 곳인데 **전화가 끊겼습니다**. ① 한 지점이 거래를 거부한다(일관성) ② 두 지점이 각자 처리하고 나중에 맞춘다(가용성). 전화가 끊긴 상태에서 **둘 다 완벽할 수는 없습니다**. 이게 CAP입니다.

**핵심 원리**: 분산 시스템은 **일관성(Consistency) · 가용성(Availability) · 분할 내성(Partition tolerance)** 중 **네트워크 분할 상황에서 두 개만** 만족할 수 있습니다. 네트워크는 반드시 끊기므로(P는 필수), 실제 선택은 **CP vs AP**입니다.

| 선택 | 동작 | 예 |
| --- | --- | --- |
| CP | 분할 시 일부 요청 거부 | ZooKeeper, 강한 정합성 DB |
| AP | 분할 시에도 응답, 나중에 수렴 | Cassandra, DynamoDB(기본) |

**PACELC**는 이를 확장합니다 — 분할(P)이 없을 때도 **지연(L)과 일관성(C) 중 하나를 고른다**. 정합성을 위해 합의를 기다리면 느려집니다.

**최종 일관성(Eventual Consistency)**: 잠시 다를 수 있지만 결국 같아진다. 문제는 **"얼마나 잠시인가"** 와 **"무엇이 보이는가"** 입니다.

| 보장 | 의미 |
| --- | --- |
| Read-your-writes | 내가 쓴 것은 내가 바로 읽는다 |
| Monotonic reads | 한 번 본 최신 값이 뒤로 가지 않는다 |
| Quorum (R+W>N) | 읽기·쓰기 정족수 합이 복제본 수를 넘으면 최신 보장 |

**핵심 감각**: **AI 서비스는 대부분 AP가 맞습니다.** 답변에 쓰는 문서 인덱스가 1초 늦는 것보다, 검색이 아예 실패하는 것이 더 나쁩니다. 반대로 **권한·결제·감사 로그는 CP**가 필요합니다. "무엇을 늦게 반영해도 되는가"를 기준으로 나누는 것이 설계입니다.

### 🎤 면접 30초 답변

> "CAP 이론은 분산 시스템에서 네트워크 분할이 발생했을 때 일관성과 가용성 중 하나를 포기해야 한다는 것입니다. 네트워크 분할은 피할 수 없기 때문에 실제 선택은 CP와 AP 사이입니다. CP는 분할 시 일부 요청을 거부해서 정합성을 지키고, AP는 응답을 우선하고 나중에 상태를 수렴시킵니다. 최종 일관성은 그 수렴을 전제로 한 모델이고, 사용자 경험을 위해 내가 쓴 것은 바로 읽히는 read-your-writes 같은 보장을 추가로 설계합니다. AI 서비스라면 검색 인덱스는 AP로 두어 가용성을 우선하고, 권한이나 감사 로그처럼 정합성이 중요한 데이터는 CP로 분리합니다."

### 🎯 SA 실무 포인트

**1) "일관성"이라는 단어를 고객과 같은 뜻으로 쓰세요.**
고객이 말하는 일관성은 대개 **트랜잭션 정합성**이고, 엔지니어가 말하는 것은 **복제 수렴**입니다. 요구를 "5초 내 반영"처럼 **숫자와 범위**로 바꿔 합의해야 합니다.

**2) 인덱스의 최종 일관성은 답변 품질로 나타납니다.**
문서를 수정했는데 옛 청크가 검색되면 "챗봇이 틀린 답을 한다"는 문의가 됩니다. **재인덱싱 지연 SLA**를 정하고, 삭제는 더 엄격하게(검색 즉시 제외) 처리합니다.

**3) 정합성 요구가 높은 데이터는 별도 저장소로.**
AI 대화 로그(AP, 대량)와 감사 로그(CP, 소량·중요)를 같은 테이블에 두지 않습니다. 요구가 다르면 저장소도 달라야 합니다.

## 🗃️ 6. 블록 · 파일 · 오브젝트 스토리지

**일상 비유**: 세 가지는 **창고 사용 방식**이 다릅니다.

- **블록 스토리지**는 **내 사무실 벽장**입니다. 내가 원하는 대로 칸을 나눠 쓰고, 문을 열면 바로 접근합니다. 다른 사람은 못 씁니다.
- **파일 스토리지는 공용 서류 캐비닛**입니다. 여러 사람이 같은 폴더 구조로 접근합니다.
- **오브젝트 스토리지는 택배 보관소**입니다. 물건마다 번호표(키)가 붙고, **택배기사에게 번호를 주면** 찾아옵니다. 직접 들어가 뒤질 수는 없습니다.

**핵심 원리**:

| 구분 | 접근 방식 | 지연 | 대표 서비스 |
| --- | --- | --- | --- |
| 블록 | 가상 디스크(포맷 후 파일시스템) | 매우 낮음 | EBS, Persistent Disk |
| 파일 | 공유 파일시스템(NFS) | 낮음 | EFS, Filestore |
| 오브젝트 | HTTP API(키 기반) | 중간 | S3, GCS, Azure Blob |

**핵심 감각**: **DB는 블록 스토리지에, 공유 파일은 파일 스토리지에, 대용량 원본·백업·모델 아티팩트는 오브젝트 스토리지에** 둡니다. 오브젝트 스토리지는 파일시스템이 아니라 **HTTP 저장소**라서, "S3를 DB처럼 마운트"하면 지연과 비용이 터집니다.

**오브젝트 스토리지의 실무 기능**은 이 네 가지가 핵심입니다.

| 기능 | 쓰는 자리 |
| --- | --- |
| 버전 관리 | 실수로 덮어쓴 문서 복구 |
| 수명 주기 정책 | 오래된 로그·백업 자동 이관/삭제 |
| 서버 측 암호화 | 저장 데이터 암호화(KMS 연동) |
| 프리사인 URL | 일정 시간만 유효한 다운로드 링크 |

**공유 파일이 필요할 때의 함정**: 여러 파드가 같은 파일을 RWX로 써야 하면 EFS 같은 파일 스토리지가 필요합니다. 하지만 **다수 파드가 같은 파일에 동시에 쓰면 락 경합**으로 지연이 급증합니다. 가능하면 "오브젝트 스토리지 + 메타데이터 DB"로 설계하는 것이 확장에 유리합니다.

### 🎤 면접 30초 답변

> "블록 스토리지는 가상 디스크로 포맷해서 파일시스템을 올리는 형태라 지연이 가장 낮고, 데이터베이스처럼 직접 제어가 필요한 워크로드에 씁니다. 파일 스토리지는 NFS 같은 공유 파일시스템으로 여러 서버가 같은 디렉터리를 보게 해 주고, 공유 파일이 필요한 레거시 앱에 적합합니다. 오브젝트 스토리지는 HTTP API로 키를 지정해 읽고 쓰는 방식이라 대용량·불변 데이터와 백업, 모델 아티팩트에 적합하고, 버전 관리·수명 주기·암호화·프리사인 URL 같은 관리 기능을 제공합니다. 다만 파일시스템이 아니라서 DB 데이터 파일을 두는 용도로는 쓰지 않습니다."

### 🎯 SA 실무 포인트

**1) RAG의 원본 문서는 오브젝트 스토리지 + 메타데이터 DB입니다.**
PDF를 DB에 BLOB으로 넣는 설계는 백업·복구·비용에서 불리합니다. **S3에 원본, DB에 위치·해시·권한**을 두고, 청크와 임베딩은 별도 저장소에 둡니다.

**2) 모델 아티팩트는 버전과 무결성이 핵심입니다.**
모델 파일은 수 GB이고 배포마다 내려받습니다. 버전 태그, 체크섬, 프리사인 URL, 리전 내 캐시를 설계해 **배포 시간과 비용**을 줄입니다.

**3) 삭제 요구가 오면 오브젝트까지 지워야 합니다.**
DB 행만 지우고 S3 원본이 남으면 개인정보 삭제 요구 위반입니다. **수명 주기 정책 + 삭제 파이프라인 + 백업 만료**를 한 세트로 설계합니다.
